## 3. 지금 안 하면 나중에 비용이 커지는 것

판단 기준: 게임을 하나 포팅할 때마다 그 기능을 게임 안에 새로 만들게 되면, 나중에 공용으로 바꿀 때 **포팅한 게임 수만큼 옮기기 + 골든 재확인**이 붙는다. 반대로 게임이 직접 닿지 않는 기능(셸 서비스·렌더러 내부)은 미뤄도 비용이 거의 같다.

| 순위 | 작업 | 미루면 생기는 비용 | 지금 할 최소 범위 |
|---|---|---|---|
| 1 | A1 게임 호스트(`mgscene`) | 예전 GameDef 경로로 만든 게임마다 흐름·결과·설정 연결을 다시 해야 함 | 진행 중 |
| 2 | 결정성 규칙(온라인 대비) | 게임 로직이 `Math.random`·벽시계 dt·DOM 입력·f64 누적을 쓰면, 온라인을 붙일 때 게임마다 로직을 뜯어야 함. 원본은 입력만 동기화하고 각 기기가 같은 계산을 하므로([12_online_sync.md](12_online_sync.md)) 결정성이 깨지면 온라인 자체가 안 됨 | 규칙만 지금 고정: 로직은 고정 스텝·`BexRandModule`(sync/async 구분)·`FrameGate` 경유 입력·f32(`Math.fround`)만 쓴다. 구현(C3)은 나중 |
| 3 | B1 이펙트 런타임 | 거의 모든 게임에 이펙트가 있어 게임마다 `effects.ts` 복사본이 생김 | 공용 런타임(registry·입자·FTRG fx 연결) |
| 4 | A3 actor 입력·이동 계층 | 이동형 게임마다 이동·점프·입력 처리를 따로 만들면, 나중에 공용으로 바꿀 때 조작감이 게임마다 달라지고 골든을 전부 다시 만들어야 함 | actor 입력·이동 계층(접지는 A4 연결 자리만) |
| 5 | A4 충돌 API(백엔드는 나중이어도) | 게임마다 임시 충돌(광장식 순차 push·구-메시 직접 구현)로 만들면, PhysX 이식 뒤 결과가 바뀌어 게임마다 다시 맞춰야 함 | §6 질의 API·수명 규칙을 먼저 고정하고 게임은 그 API만 부른다. 백엔드(P0)는 그 뒤 교체 |
| 6 | B4 게임 에셋 broker | 게임마다 자체 캐시를 쓰면 같은 파일을 두 번 받고 GPU 준비가 안 됨. 나중에 게임마다 로딩 코드 수정 | 게임 에셋 로딩을 broker 경유로 |
| 7 | B2·B3·B7 후처리·카메라·재질 | 게임마다 복사본이 늘수록 원본 식 수정(톤맵 등)을 N곳에 해야 함 | 공용판 하나로 합치고 게임은 파라미터만 |
| 8 | B5 레이아웃 재생기 | 게임 HUD가 늘수록 두 재생기 차이 맞추기 비용 증가 | 하나로 합치기 |

미뤄도 비용이 거의 같은 것: C1 보조 물리·C2 표정(슬롯 자리가 이미 있어 꽂기만 함), C5 LOD 등(렌더러 내부), C6 셸 서비스(미니게임이 직접 닿지 않음), 셰이더 그래프 남은 재질(변환 데이터만 다시 생성), B6 소리 파일 변환(데이터 추가).

### 6.3 경우 B — 미니게임도 같이 넣어야 할 때

보드는 원본에서 미니게임을 추첨해 부른다. 추첨 대상은 리듬(mg18xx)·쿠파(mg14xx) 등 모드 전용을 뺀 **약 70~85종 [추정]** — 정확한 목록은 원본 추첨표(MGList·보드 추첨) 판독이 필요하다.

| # | 일 | 작업일 | 비고 |
|---|---|---|---|
| B1 | 미니게임 공통 선행: 체감 입력(A2 로드맵) 1, actor 계층(A3) 1~2, 충돌 P0·P1(A4) 3~4, 강체 P2 2~3 | 7~10 | 대부분 이동·충돌 게임이라 필수 |
| B2 | 분석된 비리듬 12종 이식 | 12종 × 0.5~2 = 6~24 | 분석 끝 |
| B3 | 미분석 약 60~70종: 분석 0.5~1 + 이식 0.5~2 | 60~70종 × 1~3 = 60~210 | 공용 기반이 갖춰질수록 아래쪽에 가까워진다 |
| | **B 합계** | **약 75~245 작업일** | 3갈래 병렬 **달력 약 5~16주** |
| | **A + B** | | **달력 약 7~19주** |

넓은 범위의 이유: 미분석 게임마다 물리·카메라·특수 입력 비중이 다르다. 공용 기반(actor·충돌·이펙트·사운드)이 다 깔린 뒤의 이식 속도가 실측되면 범위를 좁힌다.

### 6.4 빨리 "돌아가는 보드"를 보는 방법

- 미니게임 **일부만**(예: 20~30종) 이식하고, 보드 추첨을 이식된 것 안에서만 하게 한다(원본과 다른 근사 — 문서에 표시). → **A + 약 4~6주(달력)** 로 보드 한 판을 처음부터 끝까지 돌릴 수 있다.
- 순서 권장: A1(보드 분석)과 B1(미니게임 공통 선행)을 **병렬로** 시작 → A2·A3 → A4와 B2를 병렬 → A5·A6 → B3 는 보드가 돈 뒤 계속 추가.

### 6.5 위험·미확정

- `bd01` 분석량이 실제로 더 클 수 있다(함수 수만으로 본 비례 [추정]).
- 보드 CPU 판단(아이템 사용·경로 선택)이 원본 판독 비중이 크다.
- 보드 온라인(입력 동기)은 이 견적에서 뺐다 — 결정성 계약(DESIGN 3절·minigame_scene §12.12.6)을 지키면 나중에 붙일 수 있다.

## 7. 추가 견적: 보드 없이 "광장에서 파티 → 미니게임 10턴" (2026-10-09)

속도 기준·단위는 6.1 과 같다(오늘 실측, 작업일 = 한 갈래, 달력 = 2~3갈래 병렬, 여유 배수 없음).

### 7.1 필요한 것

| # | 일 | 작업일 | 비고 |
|---|---|---|---|
| P1 | 남은 구조 정리 — `view/` 해체(로드맵 2)·페이지·개발 코드 정리(4)·화면 간 import 끊기(5)·렌더러 통합(6)·장면 계약 + Work(7, DESIGN.md 10.5) | 5~8 | 7번이 핵심: 파티 모드 ↔ 미니게임 Call/Return, 누적 점수를 Work 로 |
| P2 | 미니게임 공통 선행 — 체감 입력 1·actor 계층 1~2·충돌 P0·P1 3~4·강체 P2 2~3 | 7~10 | 이동·충돌 게임용. 리듬 게임만 쓰면 체감 입력만 필요 |
| P3 | "10턴 파티" 모드 `app/scene/mode/party` — 게임 추첨·라운드 진행·점수 누적·중간 순위·최종 시상(`app/minigame/frame/result` 재사용) | 2~3 | 원본 미니게임 모드(mgm02~06) 규칙을 따르려면 분석 +1~2 |
| P4a | 리듬 9종 이식(공용 틀 완성·분석 끝) | 9 × 0.5~1 = 4.5~9 | 가장 빠름 |
| P4b | 분석된 비리듬 10~12종 이식(mg0508·mg0122·mg0107 등) | 10 × 0.5~2 = 5~20 | P2 뒤 |
| P5 | 온라인 파티(광장에서 4명이 각자 기기) — 광장 방 → 모드 시작 연결 1~2, 미니게임 온라인 동기(프레임 입력 버퍼·seed 합의·시작 barrier·결과 합의, 로드맵 C3) 3~5 | 4~7 | 결정성 계약을 지켜 둬서 이 정도. 한 기기 로컬이면 빠짐 |

10턴이면 반복을 줄이려고 최소 15~20종을 권한다.

### 7.2 시나리오별 기간

| 시나리오 | 작업일 | 달력 |
|---|---|---|
| 가장 빠른 판 — 리듬만 10종(mg1801 + 리듬 9종), 로컬. 구조는 P1 의 7번만 | 약 10~15 | 약 1~2주 |
| 보통 판 — 20종(리듬 10 + 비리듬 10), 로컬 | 약 24~50 | 약 2~4주 |
| 보통 판 + 온라인 파티 | 약 28~57 | 약 3~5주 |

보드 1개(6장, 미니게임 포함 달력 약 7~19주)와 비교하면 보드 분석·보드 시스템이 빠지고, 미니게임 수를 우리가 정할 수 있어 적게 시작해 계속 늘릴 수 있다.

### 7.3 권장 순서

1. 장면 계약 + Work(P1 의 7번)와 체감 입력을 동시에 시작.
2. 리듬 9종 이식과 파티 모드(P3)를 병렬로 — 1~2주 안에 리듬 파티가 돈다.
3. actor·충돌 선행(P2) 뒤 비리듬 게임을 하나씩 추가.
4. 로컬 판이 돈 뒤 온라인 파티(P5).

## 8. 추가 견적: dev 화면 빌더 (2026-10-10)

보드가 빠지면 원본에 없는 화면(10턴 파티의 모드 선택·라운드 안내·중간 순위·최종 시상·파티 방 등)이 생긴다. 이것을 코드 대신 **데이터로 조립하는 화면 빌더**를 `/dev` 에 둔다. 대상은 대화상자 수준이 아니라 **게임 선택·캐릭터 선택·항구/광장 선택 같은 화면 전체**다. 3D 는 빌더로 만들지 않고 **3D 가 들어갈 자리(영역)만 잡는다**.

### 8.1 이미 있는 기반

- 글꼴: 원본 FFNT 시트를 통째로 써서 모든 글자가 있다([font_assets.md](font_assets.md) — 새 문구도 변환 없이 보인다).
- 화면은 명세(JSON) 조각을 합치는 구조(`app/common/ui` `mergeSpec`) — 문구·아이콘·효과음 덧씌우기가 쉽다.
- 원본 레이아웃 재생기·공용 UI 부품(메시지 창·대화상자·메뉴), 공용 `sys_` 그림, 사운드 라벨 표(`assets/common/sound/meta.json`), 메시지 태그 파서, 공용 저장.

### 8.2 구성

| # | 구성 | 내용 |
|---|---|---|
| 1 | 원본 UI 부품 목록 | 원본 레이아웃(`Parts.lyt` 등)의 카드·버튼·목록 행·커서·창·배경 세트·아이콘·페이지 표시를 부품으로 정리. 원본 애니(in·out·select·decide) 그대로 |
| 2 | 배치 | 끌어 놓기·정렬(원본 규칙 [../shell/ui2d_alignment.md](../shell/ui2d_alignment.md))·겹침 순서·그룹 |
| 3 | 데이터 연결 | 목록·격자 ↔ 데이터(게임 목록·캐릭터·규칙 옵션), 항목 = 부품 하나, 칸 ↔ 필드(이름·아이콘·NEW·즐겨찾기·잠금) |
| 4 | 커서·이동 | 격자·목록 커서, 끝 돌아가기, 반복 입력, 여러 명 커서 |
| 5 | 동작 | 포커스·결정·취소 → 효과음·진동·텔롭·**Work 값 쓰기·장면 call/return**(DESIGN.md 10.5) |

| 7 | 행동 부품 | 자주 쓰는 복잡한 동작은 코드 부품으로 제공하고 빌더에서는 고르고 설정만: 다인 격자 커서·필터/정렬 목록·랜덤 선택·잠금 표시 등(기존 화면 코드에서 추출) |
| 8 | 편집기 | 캔버스·속성 패널·연결·패드로 바로 미리보기·저장 |
| 9 | 화면 런타임 | 저장된 명세(JSON)를 읽어 실제 화면으로 돌리는 공용 장면 — 게임에서 ID 로 부른다 |

저장: `/dev` 에서 저장 → 개발 서버의 개발 전용 저장 API 가 `assets/custom/<이름>.json` 에 쓴다(배포 서버에는 없음). 형식은 원본 화면 명세와 같은 JSON 조각. 새 아이콘 등은 원본을 고치지 않고 `assets/custom/` 에 새 파일로 추가한다(원본 에셋 그대로 원칙).

### 8.3 기간

| 단계 | 작업일 |
|---|---|
| 원본 UI 부품 목록 정리(레이아웃은 이미 변환됨) | 1~2 |
| 화면 런타임(명세 → 화면: 배치·데이터 연결·커서·동작·3D 자리) | 3~5 |
| 행동 부품(기존 화면 코드에서 추출) | 2~3 |
| 편집기(캔버스·속성·연결·미리보기·저장 API) | 4~6 |
| 검증: 기존 화면 하나(모드 선택 또는 프리 플레이 목록)를 빌더로 똑같이 다시 만들어 지금 코드 화면과 비교 | 1~2 |
| 선행: 장면 계약 + Work(로드맵 7단계) | 1~2 |
| **합계** | **약 12~20 작업일 → 달력 2~3주(2갈래 병렬)** |

참고: 문구·아이콘·효과음만 바꾸는 "고치기 편집기"(덧씌우기)만이면 2~3작업일, 대화상자·메시지 창·선택 메뉴·텔롭·아이콘 팝업·결과 표 템플릿 6종까지 +3~5작업일. 자유 배치·애니 편집기는 수 주이고 원본 그대로 원칙과 멀어져 권하지 않는다.

### 8.4 원칙·한계

- **원본 화면은 지금처럼 코드로 둔다**(원본 로직을 판독대로 옮긴 것이 가장 정확). 빌더는 원본에 없는 화면에 쓰고, 원본 화면 문구·아이콘은 덧씌우기로만 바꾼다. 기존 화면 하나를 빌더로 다시 만드는 것은 검증용이다(교체 여부는 그때 결정).
- 원본에 없는 새 모양(새 그림·새 애니)은 빌더로 만들 수 없다 — 그림 파일을 따로 추가한다.
- 아주 특수한 동작은 행동 부품을 코드로 하나 추가한다. 그 뒤로는 빌더에서 고르기만 한다.
- 빌더·화면 런타임도 공용 원칙을 따른다: 화면 런타임 코어는 mpj 를 모르고(import 0), 원본 부품·데이터 연결은 mpj 쪽에서 꽂는다. app 은 dev(편집기)를 부르지 않는다.

### 8.5 권장 순서

1. 장면 계약 + Work(7단계).
2. 화면 런타임 + 원본 UI 부품 목록.
3. 편집기 + 행동 부품.
4. 10턴 파티(7장)에 필요한 화면을 빌더로 만들면서 검증 — 실제 쓰임과 함께 다듬는다.
[설계] 원본 UI 부품·템플릿 정리본: [ui_parts_catalog.md](ui_parts_catalog.md).
