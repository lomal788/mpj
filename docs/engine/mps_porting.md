## 1. 결론과 범위

[확인] MPS 웹은 이미 게임 로직과 화면을 분리하고 있다. hsmg402의 눈덩이 성장·발사·충돌·넉백·CPU·탈락·순위 계산을 재사용하면서 MPJ 장면·에셋·렌더 서비스에 연결하는 포팅이 가능하다. 양쪽 프로젝트는 `three ^0.180.0`을 사용한다. 같은 의존 버전 범위는 API 적응 부담을 줄이지만 렌더 결과의 호환성을 보증하지 않는다.

[설계 제안] MPJ 공용 기반을 활용하고, MPS의 게임 동작·수치·고유 그래프는 보존한다. MPS 엔진 전체를 MPJ에 옮기는 작업으로 범위를 넓히지 않는다. 확인되지 않은 MPS 동작을 MPJ 기본값으로 채우지 않는다.

첫 포팅 범위는 기존 MPS 웹 구현과 같은 플레이·화면 기능, 현재 변환된 10명 캐릭터, 프리플레이 시작·결과·복귀, 에셋 사전 다운로드·GPU 준비·취소·해제 연결이다. MPJ 선택 목록 22명 전체 지원, 추가 원본 분석, 온라인 동기 연결은 별도 범위다. 기존 10명 밖의 캐릭터가 선택됐을 때 조용히 다른 캐릭터로 대체하는 것은 완료 조건이 아니다. 첫 범위를 적용할 때 게임별 지원 목록과 선택 경로를 연결해야 한다.

## 4. 동작을 보존해야 하는 핵심 차이

### 4.1 난수와 시드

[확인] MPS의 동기 정수 `mod`는 libc++ 비트 마스크 기각 표본을 사용한다. MPJ `syncRandMod`는 `(u·n)>>32`를 사용한다. 같은 MT19937 출력에서도 값과 소비 횟수가 달라질 수 있어 CPU 목표·행동·최종 순위가 변한다.

기존 MPS 웹은 GameSetup.seed로 두 난수 엔진을 초기화한다. MPJ 한 판 호스트는 async를 초기화한 뒤 `SetSyncRandSeed(async.Rand())`로 sync를 초기화한다. MPS 원본의 오프라인 전역 난수 지속과 기존 웹의 주입 시드는 구분한다. 첫 이전은 기존 MPS 웹의 골든 시험을 유지하고, MPJ 장면 난수와 MPS 게임 난수의 소유자·초기화를 문서화한다. MPJ 게임용 난수 동작을 전역에서 바꾸지 않는다.

### 4.2 프레임 순서와 장면 훅

[확인] 기존 기본 순서는 Player.update → Actor 제어·지면·밀기·모션 갱신 → PlEvCol/손 위치 → 장면·GameMgr → 공 갱신 → 겹침 진입 트리거 → SeMgr reset/Player.postPhysics다. 원본의 일부 상대 순서는 미확정이며 `Hsmg402Config`로 가정을 드러낸다.

첫 B가 진입 프레임에 중복 집계되는지에 따라 눈덩이 생성이 9회/10회로 달라질 수 있다. 훅 이전 시 단순히 update를 다른 단계로 옮겨 이 순서를 바꾸지 않는다. 시작·종료 텔롭, BGM, 타이머, 결과 UI의 소유자를 각각 하나로 정해 MPS 자체 흐름과 MPJ 공용 흐름이 중복 실행되지 않도록 한다.

### 4.3 Actor와 지형

[확인] 기존 MPS Actor는 f32(1/60) 적분, 발 y와 지면 높이 비교, 별도 선회·대칭 밀기 근사를 사용한다. MPJ Actor에는 서브스텝·Map 해소·접지 문턱·Ray fallback 정책이 있다. 기존 MPS ground는 48각 지형 단면을 해석식으로 질의한다.

[설계 제안] 첫 포팅에서는 MPS의 확인된 식과 기존 웹 가정을 게임 호환 경로로 보존한다. MPJ 접지 정책을 그대로 적용해서 원본 미확정을 닫지 않는다. 공용 충돌 어댑터를 적용할 경우 가장자리·낙하·공 sweep·트리거 진입의 기존 기대값과 먼저 대조한다. 공은 코드가 적분하므로 PhysX 동적 강체로 바꾸지 않는다.

### 4.4 캐릭터와 눈 자국

[확인] 뼈대·텍스처가 같아도 모션·재질 애니·표시 애니·이벤트 자료 형식의 호환은 별도다. 기존 화면은 로직의 motionFrame을 직접 샘플한다. 공용 캐릭터 연결에서 로직과 화면이 모션 프레임을 각각 증가시키거나 이벤트를 두 번 발생시키지 않도록 한다.

눈 자국은 512² 높이장 두 장, 붓 RT, 노멀 RT, 지면 정점 변위·깊이 재질을 사용한다. 발·몸 붓 메시와 눈덩이 모델이 입력이다. MPJ 캐릭터 메시로 교체할 때 붓 메시가 없으면 뼈 호환만으로 기존 눈 자국을 유지할 수 없다. 기존 `mpsFluidEnv`·active FresLibrary 같은 전역 상태는 장면이 소유하도록 바꾸거나 명시적으로 전달한다.

### 4.5 후처리와 GPU 수명

[확인] MPS와 MPJ는 블룸 첫 패스 식과 톤맵 번호·출력 가정 등이 다르다. 예를 들어 MPS 첫 패스는 밝기 기반 선형 k로 `max(c·k,0)`을 계산하고, MPJ stage 경로는 threshold의 smoothstep과 spread⁵ 보정을 사용한다. 같은 숫자만 주입해서 같은 화면이 되지 않는다.

[설계 제안] renderer는 MPJ 앱 renderer를 빌리고 MPS 고유 패스·설정은 유지한다. 별도 WebGLRenderer는 만들지 않는다. prepare에서는 활성 메뉴의 post·조명·전역 유니폼을 바꾸지 않으며 렌더 타깃·viewport·scissor·clear·toneMapping 등 변경 상태를 성공/실패 모두에서 복원한다. activate에서 post 연결·소리·상시 이펙트·프레임 진행을 시작한다. dispose는 자신이 소유한 자원만 해제한다.

## 6. 사전 다운로드·GPU 준비

[설계 제안] 기존 MPJ 사전 준비 계약을 사용한다. hsmg402만 별도 다운로드 큐나 rAF 루프를 만들지 않는다.

1. GameDef 메타는 정적으로 두고 로직·뷰는 코드 분할로 읽는다.
2. assetKeys는 manifest에서 모델·외부 텍스처·재질 메타·카메라·효과·소리 파형·UI/글꼴·선택 캐릭터 모션과 공용 의존을 전개한다.
3. 캐릭터·자원에 영향을 주는 설정을 preparationKey에 포함한다. 실제 필요한 자원만 우선 받으며 현재 캐릭터 폴더 전체 용량을 한 판 필수량으로 간주하지 않는다.
4. prepare는 AssetManager로 자원을 받아 GPU 큐에서 컴파일·텍스처·RT·눈 높이장 패스를 준비한다. 게임 시계·소리·효과·높이장 누적은 진행하지 않는다.
5. activate는 준비 완료 자원을 활성 장면에 넘기고 post·UI·소리·효과를 연결한다. 메뉴에 표시되는 동안 게임을 한 프레임 실행해서 준비하는 방식과 구분한다.
6. 선택 변경·취소·오류·재시작에서 진행 중 작업을 취소하고 준비 자원만 해제한다. 완료 자원을 활성화했다면 준비 취소가 그 자원을 다시 해제하지 않게 한다.
7. 압축·해시 이름·배포 manifest·캐시 경로에 새 게임 에셋이 포함되는지 검증한다. 실제 전송량은 빌드 결과에서 산출한다.
