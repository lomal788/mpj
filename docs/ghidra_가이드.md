# Ghidra 분석 가이드

분석 흐름: **Ghidra 단일 프로젝트(MCP)로 분석 → 확정된 계약만 MD → .ts 구현 → 진행도(web/progress)로 집계**

| 위치 | 담는 것 | 역할 |
|---|---|---|
| Ghidra 프로젝트 | 주소별 사실: 함수 이름·네임스페이스·시그니처·구조체·enum·주석·태그 | 분석 작업 공간(캐시) |
| git 스냅샷 `analysis/ghidra_db/` | 위 내용을 텍스트로 내보낸 것 + 태그 어휘·기능 목록 | **기준 원본**: 이력·diff·리뷰·grep |
| 기능 MD `web/docs/**` | 기능 단위 계약: 흐름·상태 전이·계산 규칙·웹 설계·기대값·미확정 목록 | 구현 근거. 의사코드·오프셋표는 복사하지 않고 함수 ID로 연결 |
| .ts | 구현 + `@orig` 표시 | 포팅 연결의 기준 원본 |
| 시험 보고서 | 시험 통과 결과 | 검증의 기준 원본 |

## 0. 원칙

1. **사실 하나는 한 곳에만 저장한다.** 같은 내용을 Ghidra·MD·코드에 복사하지 않는다.
2. **계산할 수 있는 것은 저장하지 않는다.** 미니게임 소속, 작은 함수 여부, 포팅 여부, 기능 범위는 스캐너가 계산한다.
3. 사람(또는 AI)이 판단해야만 알 수 있는 것만 Ghidra 태그로 붙인다: 분석 상태, 소유 시스템, 제외 여부.

## 1. 함수 ID

- 형식: **`모듈:주소`** — 소문자 16진수, `0x` 없음.
  - 예: `main:7100123400`, `mg0108:71000041e0`, `mgm02:710001704c`
- 모듈 이름은 파일 이름에서 확장자를 뺀 것이다: `main`(main.nso), `mg0108`(mg0108.nro), `menu00`, `bd01` …
- **모든 NRO가 같은 기준 주소(0x7100000000)에서 시작한다.** 모듈 없는 주소는 어느 함수인지 알 수 없으므로 MD·코드·주석 어디서든 함수 ID 형식으로 쓴다.
- 주소는 함수 시작 주소다. 함수 안쪽 위치를 가리킬 때는 `main:7100123400+0x48`처럼 쓴다.

## 2. 분석 규칙

1. 기능을 다룰 때는 `docs/README.md`(기능 → MD 목록)에서 관련 MD를 먼저 찾는다.
2. 함수 하나를 찾을 때는 스냅샷(`analysis/ghidra_db/`)을 grep하거나 Ghidra MCP로 조회한다.
3. MD나 Ghidra에 이미 확정된 로직이 있으면 다시 분석하지 않고 재사용한다.
4. MD에 내용이 없거나 부족할 때만 Ghidra MCP로 새로 분석한다.
5. 새로 확인된 사실은 Ghidra에 바로 반영한다: 함수명·구조체·타입·enum·주석·상태 태그.
6. 부분 분석 결과도 Ghidra에 남긴다(plate 주석 + `MPJ_ST_PARTIAL`). 검증되지 않은 가설은 확정된 이름이나 타입으로 적용하지 않고 주석에만 적는다.
7. 기능의 계약이 확정되면 MD를 만들거나 고친다. MD 기준은 "100% 완료"가 아니라 "확정된 계약 + 미확정 목록"이다.
8. 기존 분석과 모순되면 이전 결과를 임의로 덮어쓰지 않는다. 근거를 확인한 뒤 고치고, 확인 전에는 `MPJ_ST_RECHECK`로 바꾼다.
9. TypeScript 구현은 MD를 먼저 쓴다. 원본 계산식이나 분기 확인이 필요할 때만 Ghidra MCP를 부른다.
10. 원본 함수를 옮긴 코드에는 `@orig`를 표시한다(§6).
11. 작업이 끝나면 스냅샷을 내보내고 검사를 돌린 뒤 git diff로 확인한다(§10).

## 3. 네임스페이스

- **원본 심볼이 있는 함수의 네임스페이스는 옮기지 않는다.** 예: `mg0108::Camera::SetupGame`, `bq::MinigameModeWork::…`. 원본 이름 자체가 근거다.
- 네임스페이스 정리는 이름 없는 `FUN_…` 함수에만 한다. 예: `SharedEngine::Actor`.
- 소속은 네임스페이스가 아니라 태그(소유 시스템)와 계산(미니게임 소속)으로 나눈다. 공용 함수는 여러 게임에 쓰이는데, 네임스페이스는 하나만 가질 수 있기 때문이다.

## 4. 정보별 저장 위치

| 정보 | 저장 위치 | 정하는 쪽 |
|---|---|---|
| 분석 상태 | Ghidra 태그 `MPJ_ST_*` | 분석자 판단 |
| 소유 시스템 (main 함수만) | Ghidra 태그 `MPJ_SYS_*` | 분석자 판단 |
| 진행도 제외 | Ghidra 태그 `MPJ_EX_*` | 판단 + 자동 일괄 |
| 미니게임 소속 | **계산**: NRO 모듈 = 게임, 공용 함수는 호출 그래프 | 스캐너 |
| 작은 함수 | **계산**: 크기·호출 수(기준은 `tags.json`) | 스캐너 |
| 포팅 여부·파일·수준 | **웹 코드 `@orig`** | 구현자 |
| 시험 통과 | **시험 보고서** | 시험 실행 |
| 기능 범위 | **계산**: `features.json` 시작 함수 → 호출 그래프 | 스캐너 |

파일 경로는 Ghidra에 적지 않는다. 파일을 옮길 때마다 낡기 때문이다. 함수 → 파일 연결은 스캐너가 `@orig`에서 계산한다.

## 5. Ghidra 태그

손으로 붙이는 태그는 함수당 최대 3개다: 상태 1, 소유 1, 제외 0~1. 어휘는 `analysis/ghidra_db/tags.json`에 고정한다(§9).

### 5.1 상태 `MPJ_ST_*` (하나만, 없으면 미착수)

| 태그 | 완료 기준 | 집계 |
|---|---|---|
| (없음) | 손대지 않음 | 미착수 |
| `MPJ_ST_PARTIAL` | 일부 사실 확인. plate 주석 필수 | 부분 |
| `MPJ_ST_ANALYZED` | 모든 분기를 이해했고, 호출하는 함수의 역할이 알려져 있고, 쓰는 필드·상수를 확인함. 함수 안에 미확정이 없음. plate 주석 필수 | **완료** |
| `MPJ_ST_RECHECK` | 모순이 생겨 다시 확인해야 함 | 경고(완료에서 제외) |

- 함수 밖의 미확정(호출자 쪽 사용법 등)은 ANALYZED를 막지 않는다. 그 미확정은 기능 MD에 적는다.
- `VERIFIED`는 쓰지 않는다. 웹 검증은 시험 보고서로 따로 집계한다.

### 5.2 소유 시스템 `MPJ_SYS_*` (main 함수에만, 하나)

NRO 함수는 모듈로 소속이 정해지므로 붙이지 않는다.

| 태그 | 범위 | 관련 문서 |
|---|---|---|
| `MPJ_SYS_CORE` | 엔티티·컴포넌트·파이버·난수·수학·메모리 | engine/01 |
| `MPJ_SYS_SCENE` | 장면 수명·전환·Work·모드 진행 | engine/18, 15 |
| `MPJ_SYS_ACTOR` | ComActor·패드·점프·조건·접지 | engine/17 |
| `MPJ_SYS_COLLISION` | 충돌 질의·물리 연결 | engine/11 |
| `MPJ_SYS_CAMERA` | 카메라·투영·FSNB·흔들림·조명 | engine/07, 20 |
| `MPJ_SYS_CHARACTER` | 캐릭터 모델·모션·표정 | engine/09 |
| `MPJ_SYS_EFFECT` | 이펙트 | engine/08 |
| `MPJ_SYS_SOUND` | SE·BGM·음성·진동 | engine/04 |
| `MPJ_SYS_UI` | 레이아웃·폰트·메시지·대화상자 | engine/05 UI 부분 |
| `MPJ_SYS_INPUT` | 패드·체감 입력 | engine/05 입력 부분, 19 |

| `MPJ_SYS_ASSET` | 리소스 로더·아카이브·장면 데이터 | engine/06, loader_manager |
| `MPJ_SYS_NET` | 온라인·세션·동기화 | engine/12 |
| `MPJ_SYS_SAVE` | 저장 데이터 | engine/16 |

### 5.3 제외 `MPJ_EX_*` (진행도 분모에서 뺌)

| 태그 | 뜻 |
|---|---|
| `MPJ_EX_LIB` | nn SDK·표준 라이브러리·PhysX 등 외부 코드. 심볼 패턴으로 자동 일괄 부여 |
| `MPJ_EX_DEBUG` | 디버그·개발 전용 기능 |

### 5.4 plate 주석 형식

```
[판독] 2026-10-11 / md: docs/minigame/mg0301.md §6.2
본문…
```

- 첫 줄: `[근거 수준] 날짜 / md: 경로 §절` (md가 없으면 생략)
- 근거 수준: `[판독]` 디컴파일 확인, `[추정]` 해석, `[미확정]` 공백
- 날짜는 나중에 RECHECK 대상을 판단하는 데 쓴다.
- 웹 파일 경로는 적지 않는다(§4).

### 5.5 예시

```
ID:    mg0301:7100123400   (UpdateRobot)
Tags:  MPJ_ST_ANALYZED
Plate: [판독] 2026-10-11 / md: docs/minigame/mg0301.md §6.2
```

- 소유 태그가 없는 이유: NRO 함수라서 소속(mg0301)이 모듈로 정해진다.
- 포팅 여부는 코드의 `@orig mg0301:7100123400 full`에서 계산된다.

### 5.6 검사 (스캐너가 오류로 표시)

- `tags.json`에 없는 `MPJ_` 태그
- 상태 태그가 2개 이상
- 소유 태그가 2개 이상, 또는 NRO 함수에 소유 태그
- PARTIAL·ANALYZED인데 plate 주석이 없거나 첫 줄 형식이 다름
- `@orig`가 가리키는 함수 ID가 스냅샷에 없음

## 6. 웹 코드 표시 `@orig`

원본 함수를 옮긴 코드의 문서 주석에 표시한다.

```ts
/** @orig main:7100123400 full */
/** @orig mg0108:71000041e0 partial */
/** @orig main:710000f690 approx */
```

| 수준 | 뜻 |
|---|---|
| `full` | 원본 식·분기를 그대로 옮김 |
| `partial` | 일부 분기만 옮김 |
| `approx` | 근사(원본과 다름을 알고 있음) |

- 한 함수가 원본 여러 개를 옮겼으면 여러 줄을 쓴다. 원본 하나가 여러 파일에 나뉘면 각 파일에 쓴다.
- 줄 끝에 짧은 설명을 붙여도 된다: `/** @orig main:710000f690 approx — 카메라 basis 주입 근사 */`
- 스캐너는 `@orig`만 포팅으로 센다. 기존 자유 형식 참조(`@0x…`, `main FUN_…`)는 "후보"로만 보여 주고, 해당 코드를 고칠 때 `@orig`로 바꾼다.

## 7. 기능 목록 `features.json`

- 전체 서비스 진행도의 단위다. 기능마다 이름, MD, 시작 함수 ID를 적는다.
- 스캐너가 시작 함수에서 호출 그래프를 따라가 범위를 정한다.
- 간접 호출(vtable·콜백·람다)은 호출 그래프에 안 잡히므로 `roots`에 추가로 적는다.
- 미니게임은 기능 목록에 따로 적지 않아도 된다. NRO 모듈 하나가 미니게임 하나다.

## 8. 진행도 (web/progress)

스캐너 입력: 스냅샷(`functions.tsv` 태그·호출 그래프) + 웹 코드 `@orig` + 시험 보고서. MD 문장에서 상태를 추측하지 않는다.

- **분모:** 대상 함수 전체 − `MPJ_EX_*`
- **분석:** 미착수 / 부분 / 완료 / 재확인
- **포팅:** full / partial / approx / 없음
- **시험:** 통과 / 없음
- **작은 함수:** 따로 표시

| 보기 | 대상 함수 |
|---|---|
| 미니게임 고유 | 그 NRO의 함수 |
| 미니게임 공용 의존 | 그 NRO가 (호출 그래프로) 부르는 main 함수 |
| 시스템 | `MPJ_SYS_*`별 main 함수 |
| 기능 | `features.json` 시작 함수에서 닿는 함수 |
| 전체 서비스 | main 전체 + 화면·모드 NRO |

## 9. 정의 파일 형식

### 9.1 `analysis/ghidra_db/tags.json`

```json
{
  "version": 1,
  "trivial": { "maxSize": 32, "maxCalls": 0 },
  "tags": {
    "MPJ_ST_PARTIAL":  { "axis": "status", "label": "부분", "plate": true },
    "MPJ_ST_ANALYZED": { "axis": "status", "label": "완료", "plate": true },
    "MPJ_ST_RECHECK":  { "axis": "status", "label": "재확인" },
    "MPJ_SYS_ACTOR":   { "axis": "system", "label": "actor", "doc": "web/docs/engine/17_actor.md" },
    "MPJ_EX_LIB":      { "axis": "exclude", "label": "외부 라이브러리" }
  }
}
```

### 9.2 `analysis/ghidra_db/features.json`

```json
{
  "version": 1,
  "features": [
    {
      "id": "plaza.move",
      "label": "광장 이동",
      "system": "MPJ_SYS_ACTOR",
      "md": "web/docs/shell/plaza_3d.md#3.5",
      "roots": ["main:71000149e8"]
    }
  ]
}
```

### 9.3 스냅샷 `analysis/ghidra_db/<모듈>/functions.tsv`

| 열 | 예 |
|---|---|
| `id` | `main:7100123400` |
| `size` | `212` |
| `name` | `UpdateRobot` |
| `namespace` | `mg0301::Robot` |
| `signature` | `void UpdateRobot(Robot * this)` |
| `tags` | `MPJ_ST_ANALYZED` (쉼표 구분) |
| `calls` | 호출하는 함수 ID (쉼표 구분) |

같은 폴더에 `comments.jsonl`(함수 ID별 plate 주석)과 `types.h`(구조체·enum)를 둔다. 행은 함수 ID 순으로 정렬해 diff가 작게 나오게 한다.

## 10. 버전 관리

Ghidra DB(`.gpr`/`.rep`)는 바이너리라 git으로 diff·merge가 안 된다. 그래서 두 층으로 관리한다.

1. **기준 원본 = git 텍스트 스냅샷** `analysis/ghidra_db/`
   - 작업이 끝날 때마다 내보내고, 검사(§5.6)를 돌리고, git diff로 확인한다.
   - INDEX.tsv와 C 덤프(`analysis/decomp/*.c`)를 점차 대체한다.
2. **복원 스크립트: 스냅샷 → 새 Ghidra 프로젝트**
   - 원본 바이너리 임포트 → 자동 분석 → 스냅샷 적용(이름·네임스페이스·시그니처·태그·주석·타입).
   - 언제든 DB를 다시 만들 수 있으므로 Ghidra 프로젝트는 지워도 되는 캐시다.
   - 기존 `ghidra_work/` 프로젝트 30여 개의 이름·타입을 하나로 모을 때도 이 스크립트를 쓴다.
3. **동시 작업이 필요할 때만 로컬 Ghidra Server**
   - checkout/checkin으로 여러 에이전트가 같은 프로그램을 다룬다.
   - 서버 이력은 보조이고, 최종 기록은 git 스냅샷이다.
   - 혼자 순서대로 작업하면 서버 없이 단일 프로젝트 + 스냅샷으로 충분하다.
4. **하지 않는다:** `.gpr`/`.rep`를 git이나 LFS에 넣기.

## 11. 프로젝트 구성

- 단일 프로젝트 `ghidra_work/mpj`에 `main.nso` 하나와 필요한 NRO들을 넣는다.
- `main.nso`는 원본 그대로 하나의 프로그램으로 관리한다.
- 원본(`C:/dev/original`)과 `extracted/`는 읽기만 한다. 키 값은 출력·기록하지 않는다.

| 필요한 기능 | 함수 태그 추가·삭제·목록, 이름 일괄 변경, 구조체 생성·수정, 주석 일괄, 호출자·피호출자, 호출 그래프, 디컴파일, Ghidra Server checkout/checkin·이력 |
| 요구 사항 | Ghidra 12.1.4, Java 21, Maven 3.9+, Python 3.10+ |
| 라이선스 | Apache 2.0 (v7.0.0 기준) |

### 도입 전 확인
- **버전:** 지금 Ghidra는 12.1.2이다. 12.1.4로 올리거나, ghidra-mcp를 12.1.2 기준으로 빌드해 본다(미확인).
- **SwitchLoader:** Ghidra 확장은 Ghidra 버전마다 빌드한다. 올린 버전용 SwitchLoader가 없으면 새 NRO 임포트만 12.1.2로 하고, 분석은 새 버전으로 한다. 이미 임포트한 프로그램은 로더 없이 열린다.
- **이름 규칙 강제(7.0):** 자동 수정·경고·거부 단계가 있다. 우리 이름·태그·주석 형식이 거부되지 않게 설정한다.
- **버전 고정:** 변화가 빠른 저장소라 쓰는 버전을 고정한다.
- **도구 노출:** 기능 209개는 필요할 때 불러오는 기본 동작을 그대로 쓴다.
- **스크립트:** 우리 Java 스크립트를 MCP로 돌리려면 `GHIDRA_MCP_ALLOW_SCRIPTS=1`이 필요하다.
- **접속:** localhost 전용으로 쓴다.

## 13. 기존 MD 분석 이전 (1회)

기존 MD의 분석은 이미 끝난 것이라 다시 분석하지 않고 옮겨 적기만 한다. 손이 가는 곳은 모듈 판별·문서 간 충돌·구조체 세 가지다.

### 13.1 기반
1. **단일 프로젝트:** `ghidra_work/mpj`에 `main.nso`와 분석된 NRO를 넣는다.
2. **정의 파일:** `tags.json`(§9.1)을 만들고 Ghidra에 태그를 등록한다. 태그 설명(tag comment)에 완료 기준을 적는다.
3. **스크립트 3개:** 스냅샷 내보내기, 스냅샷 일괄 적용(= 복원, §10), 검사(§5.6). 왕복해서 같은 결과가 나오는지 확인한다.
4. **자동 일괄 반영:**
   - `MPJ_EX_LIB`: 심볼 패턴(nn::, std::, physx:: 등)으로 부여
   - 기존 `ghidra_work/` 프로젝트 30여 개에서 붙인 이름·타입을 모은다

### 13.2 MD → 스냅샷 변환
- 문서 하나(또는 시스템 하나)씩 변환한다. 문서마다 결과 파일이 달라 병렬로 할 수 있다.
- 뽑는 것: 함수 ID, 이름, 상태, plate 주석(MD 절 링크), 소유 시스템, 구조체·enum 후보.
- **확정 수준을 지킨다.**
  - `[판독]`만 이름·타입·구조체로 넣는다.
  - `[추정]`·`[미확정]`은 plate 주석 + `MPJ_ST_PARTIAL`로만 남긴다.
- **모듈 판별:** 모듈 없이 적힌 주소는 문서 맥락으로 모듈을 정한다. 모호하면 적용하지 않고 목록으로 남긴다.
- MD로는 Ghidra에 바로 쓰지 않는다. 변환 결과는 스냅샷 형식(텍스트)으로 git에 남긴다.

### 13.3 병합·검사
- 보고서: 중복, 문서 간 이름 충돌, 모듈 모호, 구조체 필드 겹침·크기 불일치.
- 충돌은 덮어쓰지 않는다. 결정 전에는 `MPJ_ST_RECHECK`로 두고, 사용자가 정한다.
- 구조체는 구조체별로 모아 검사한 뒤 적용한다.

### 13.4 Ghidra 적용·확인
- 일괄 적용 스크립트로 넣는다(MCP로 한 건씩 넣지 않는다).
- 대표 함수 몇 개를 디컴파일해 이름·타입이 제대로 붙었는지 본다.

### 13.5 MD 정리
- 함수 단위로 복사된 내용(의사코드, 오프셋 표, 주소 목록)은 함수 ID로 바꾼다.
- 기능 계약(흐름·상태·계산 규칙·웹 설계·기대값·미확정 목록)만 남긴다.
- 문서별로 병렬로 할 수 있다.

### 13.6 이후
1. **기능 목록:** `features.json`에 기능별 시작 함수를 적고, 호출 그래프로 빠진 간접 호출을 `roots`에 보탠다.
2. **MCP 연결:** ghidra-mcp를 설치하고 SwitchLoader를 확인한다(§12).
3. **progress 스캐너 입력 교체:** MD 추측 → 스냅샷 태그 + `@orig` + 시험 보고서.
4. **`@orig` 전환:** 새 코드는 처음부터 `@orig`를 쓴다. 기존 자유 형식 참조는 해당 파일을 고칠 때 바꾼다.
5. **README 자동 생성:** 함수 주소·복원 이름·역할·MD 링크는 스냅샷에서 생성한다. 손으로 쓰는 README는 기능 → MD 목록만 둔다.
