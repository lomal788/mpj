## 1. 기능 개요와 사용자에게 보이는 동작

4인 서바이벌(VS4) 미니게임이다. 플레이어 4명이 강 위 다리를 따라 오른쪽(+x)으로 이동한다.

- 화면은 카메라 애니메이션(`mg0101_cam_game*`)이 정해진 속도로 +x 방향으로 스크롤한다. **게임의 시계는 이 카메라 애니메이션의 프레임**이다(6.1).
- 화면 왼쪽(뒤)과 오른쪽(앞)에 통나무 벽(log wall)이 있고, 헤이호(NPC) 넷이 벽을 들고 있다. 두 벽의 화면 내 x 위치가 `database.json`의 `barPattern*` 키 프레임대로 움직여 플레이어가 설 수 있는 구간을 좁힌다(6.2).
- 벽은 물리 충돌체(`ActorHitShape` 박스)라서 플레이어를 민다. 발밑이 없어지면 떨어진다(물에 빠짐). 다리 일부 발판은 후반에 뒤 벽이 지나가며 부서진다(6.6).
- 조작은 **왼쪽 스틱 이동뿐**이다(`inst_mg0101_ctrl00` = "이동") [데이터].
- x ≥ 90 에 먼저 닿은 사람은 골인(1위 공동), 떨어진 순서의 역순으로 순위가 정해진다(6.8).

### 3.2 준비 (`Scene::SyncedSetupGame @0x7100022b14`) [판독]

순서가 곧 동기 난수 소비 순서다(9절).

1. `MapMgr::MapMgr` → `MapMgr::Init @0x710000ea84`
   - `courseType = SyncRandMod(6)` (`mov w1,#6`) → `MapMgr+0x08` (0..5).
   - `CreateEnv`, `CreateBG`(→ `LoadMapData`, Bar 0~3, Wall0/1 충돌, 강·절벽·잎 등), `CreateFloors`, `InitLimit`.
2. `CameraMgr::CameraMgr @0x71000035b0`: 엔티티 "Camera"에 `ComMatter(MatterType 1)`, 기본 그래픽 레이어 카메라로 지정. 애니 `op0/op1/result`와 코스별 `game` 등록(6.1).
3. `NPCMgr`, `RankMgr`, `UIMgr` 생성.
4. 엔티티 "PartsActivator" + `ComPartsActivator`.
5. `PlayerMgr::PlayerMgr @0x710001cac0` (플레이어·AI·NaviGrid).
6. `SoundModule::Play("SM_BGM_MG0101")`, `Play("SQ_AMB_MG0101")`. 핸들은 `Scene+0x328`(BGM으로 보임), `+0x310` [추정].
7. `bq::flag::Check(0)`가 거짓이면 오프닝 파이버(`FiberLite`, 람다 → `OpeningProc`)를 `Scene+0x340`에 만든다.

카메라 프레임을 기다리는 파이버다(`Wait()` = 다음 프레임).

```

wait camFrame >= 190 → SE "SQ_SE_MG0101_OP_CAM_PAN"
wait camFrame >= 230 → Map.PlayAnim(2); NPC.PlayAnim(0)

```

[데이터] `StringViewHashPair` 표 `@0x710005a8e8/5a908/5a928/5a948`은 순서대로 `maze_idle00/co_lookout00/co_surprise00/co_run_away00_r`다. [판독] `PlayerMgr::PlayMotion @0x710001dda0`은 네 명 모두에게 같은 모션을 요청하며 두 번째 인자는 **블렌드 프레임 수**다(`MotionArg+0x44 = 인자/60`초). 4·16은 재생 시작 프레임이 아니다.

### 3.5 본편 (`Scene::MainProc @0x7100023860`) — 한 프레임 [판독]

```
PartsActivator.activate = destroy = 1           (ComPartsActivator+0x50 = 0x0101)
PlayerMgr.OnMainProcStandBy()                   (NaviGrid Start, 각 플레이어 SetMotionIdle·ComPlayer::Start·ComAI::Start)
Map.PlayAnim(0); Camera.Play(game); Camera.SetAnimSpeed(Params.CameraSpeedScale)
Map.UpdateBar(); NPC 4명 Idle()                 (Idle 마다 SyncRandRangeF 1회)
attacked = staggered = surprised = false
while (camera 재생 중):
   if !attacked && camFrame > Params.CameraDestructFrames[courseType % 3]:
        ForEachTaggedEntities("destruction") → ComDestruction+0x71 = 0 (파괴 허용)
        NPC 4명 Attack(); attacked = true
   if !staggered && camFrame > Params.NpcAttackStaggerFrame:
        r = SyncRandMod(2); NPC0.Stagger(r==0); NPC1.Stagger(r!=0); staggered = true
   if !surprised && camFrame > Params.PcSurpriseFxTriggerFrame:
        PlaySurpriseVoiseTriggerOnLivingPlayers(); surprised = true
   NPCMgr.UpdateBarNpc()                        (4명 UpdateFrame: 타이머 감소)
   if PlayerMgr.MainProc(): Scene+0x39d = 1; break        (전원 낙하 또는 골인)
   if camFrame > 540: Map.DeleteOPEntity()
   Map.UpdateBar()
   Fiber.Wait()
NPC 4명 Finish(); Map.DeleteOPEntity()
if PlayerMgr.GetExistGoal():                    (골인한 사람이 하나라도 있으면)
   while camera 재생 중: UpdateBarNpc; UpdateBar; Wait
BGM Stop_Time(0.2); Scene+0x39e = 1
t = 0; do { UpdateBarNpc; UpdateBar; Wait; t += GetDeltaTime() } while (t < 1.0)
Scene+0x39d = 1
```

- 디컴파일은 goto로 얽혀 있다. 위 정리는 플래그 3개(`bVar4/5/6`)의 의미로 다시 쓴 것이다. 같은 프레임의 순서(파괴 → 스태거 → 놀람 → NPC → 플레이어 → 바)는 원본 그대로다 [판독].
- `camFrame`은 `CameraMgr::GetFrame` = `ComActorMotion::GetFrame` (f32)이다. 비교는 모두 `>`(엄격)이다.

### 3.6 컴포넌트 틱 [판독]

`ComPlayer`, `ComAI`, `ComNaviGrid`, `ComRankMgr`, `ComPartsActivator`, `ComDestruction`은 Entity 갱신 메시지 `0x5F454E00`을 처리한다. 공용 등록 간선은 **0x0E Scene → Fiber → Entity**, 다음 **0x0F Entity → Physics**, **0x10 Physics → Entity**다 [판독]. 이미 확정된 등록·정렬 근거는 [mg0122.md §3.5](mg0122.md#35-프레임-실행-순서-판독)를 재사용한다. 따라서 본편 파이버의 NPC·플레이어 확인·벽 갱신이 이 프레임 컴포넌트 판정보다 먼저다. Entity 내부 전달 규칙도 main에서 확인했다. `FUN_71008a342c → FUN_71008a17f8 → FUN_710089f6e8`가 `0x5F454E00`을 발송한다. `FUN_710089f9f0`은 업데이트 의존 관계(`FUN_7100899880`)로 그룹을 만들고, `FUN_710089fce0`은 그룹 인덱스·그룹 내 수신 목록 순으로 돈다. 한 엔티티 안에서는 `FUN_7100899450`이 **Entity+0x38..0x40의 컴포넌트 배열 순서**로 해당 메시지 mask가 있는 컴포넌트를 호출한다. 활성화·삭제가 수신 목록을 바꾸므로 전체를 고정된 클래스 나열로 대체하지 않는다.

카메라 슬롯의 프레임 진행은 **0x0B**다 [판독]. AnimationModule 등록 `main FUN_710080c858 @0x710080c918~c930` → thunk `@0x710080d508` → `FUN_710080cd70`(6.1). 프레임 말 9→10→0x0B→0x0C 다음 0x0D/0x0E로 돌아오는 공용 루프는 [mg0122.md §6.10](mg0122.md)을 따른다. 따라서 본편 파이버가 읽는 카메라 프레임은 앞선 0x0B에서 진행된 값이며, 뼈 포즈 완료를 이 슬롯 진행과 같은 단계로 간주하지 않는다(공용 Rigger는 mg0122 §3.5).

## 6. 계산식·조건·상세 의사코드

### 6.1 카메라 애니 = 게임 시계 [판독 + 데이터]

- `CameraMgr::Play(0)`("game")는 코스별 `mg0101_cam_game*`을 재생한다. 길이 4750프레임, 루프 없음 [데이터].
- 카메라 위치 x: 프레임 0 = −90.0005, 4750 = 94.5005. 세 코스 카메라의 x 곡선은 모든 프레임에서 같다. 모든 프레임에서 pos.x == aim.x 다(오른쪽 축 = +x) [재구현 계산, `analysis/mgE_mg0101_calc.json` camera_check].
- **프레임 진행량은 `F(F(delta × 60) × CameraSpeedScale)`** [판독, F=f32 반올림]. main 애니 갱신 `FUN_710080cd70`이 `g_FrameStep+4`의 delta를 읽어 병렬 작업 +0x20에 `delta×60`을 저장한다. 작업 `FUN_710080d890` → Animator `FUN_710081cf30` → 슬롯 `FUN_71008144bc`가 `AnimationSlot+0x50` 속도를 곱해 노드 `FUN_710080fa7c`에 넘긴다. 기본 속도 1.0, delta=1/60일 때만 1.0f/틱이다. 오프라인 비리듬 장면의 가변 delta(상한 0.05초)·온라인 고정 delta는 [01_core.md](../engine/01_core.md)의 기존 판독을 따른다.
- 끝 판정 `IsAnim` = `!ComActorMotion::IsFinished`; 완료는 슬롯 status=3이다 [판독, [09_character.md](../engine/09_character.md)]. 이 카메라의 정방향·비루프 재생은 프레임이 끝에 도달하면서 완료된다. 프레임 수치만으로 모든 actor 모션 완료를 대신하지 않는다.

### 6.2 통나무 벽 위치 `MapMgr::GetBarPosition(f, side) @0x7100015050` [판독: 디스어셈블리]

`side` 0 = 뒤(L), 1 = 앞(R). `f` = 카메라 프레임(f32). 반환은 x 하나(y·z = 0).

```ts
const [fk, pk] = side === 0 ? ['frameL','posL'] : ['frameR','posR'];
const sideOff = side === 0 ? -1.5 : 1.5;
const viewTx = camera.view[3].x;          // Camera+0x70, = -카메라 x [추정, 6.3]
let pf = d[0][fk], p = d[0][pk];
if (pf >= f) {
  if (pf !== 0) return Params.FrontStartX;          // 앞 벽: 첫 키 전에는 -55.5 (월드 x 그대로)
  return F(sideOff + F(p - viewTx));
}
for (let i = 1; i < max(n, 2); i++) {               // n == 1 이면 루프 없이 아래로
  const fi = d[i][fk];
  if (fi <= 0) continue;                            // 키 무시(prev 유지)
  const pi = d[i][pk];
  if (fi < f) { pf = fi; p = pi; continue; }
  const t = F(F(f - pf) / F(fi - pf));
  const np = fmadd(F(pi - p), t, p);                // 한 번 반올림
  const delta = F(np - prevPos[side]);  const prev = prevDelta[side];
  prevPos[side] = np;
  if ((delta !== 0 && prev === 0) || (delta < 0 && prev > 0) || (delta > 0 && prev < 0)) {
    const arg = delta > 0 ? side === 0 : side !== 0;            // 출발·방향 전환
    NPC[2*side].Stagger(arg); NPC[2*side+1].Stagger(arg);
  } else if (delta === 0 && prev !== 0) {
    const arg = prev <= 0 ? side === 0 : side !== 0;            // 정지
    NPC[2*side].Stagger(arg); NPC[2*side+1].Stagger(arg);
  }
  prevDelta[side] = delta;
  return F(sideOff + F(np - viewTx));
}
return F(sideOff + F(p - viewTx));                  // 마지막 키 이후(상태 갱신 없음)
```

- `posL/posR`는 **카메라 기준 상대 x**이고, 화면 폭은 대략 ±9다 [데이터 + 추정].
- 같은 프레임 키가 연달아 있으면(예 380, 380) 두 번째 키는 `fi < f`일 때만 건너간다. 0 나누기는 생기지 않는다(`fi ≥ f > pf`) [판독].
- 첫 본편 프레임에 이전 위치 0과 비교해 출발 → 다음 프레임 반대 방향으로 스태거가 두 번 난다(재구현 계산 프레임 1·2). 원본 특이점으로 보고 그대로 둔다.

- 다섯 레이 [판독·데이터, `@0x7100008e80~9100`]: 칸 중심 `p=(열+0.5−100,0.5,행+0.5−5)`에서 **중심 → (−0.5,0,−0.5) → (−0.5,0,+0.5) → (+0.5,0,−0.5) → (+0.5,0,+0.5)** 오프셋 순서. 방향 `(0,−1,0)`, 길이 **1.0**, 레이어 비트마스크 **4**(`CastRayArg+0x20/+0x24`). 상수 벡터는 `@0x710004fc50/4fc30/4fc40/4fcf0/4fcc0`, 방향은 `@0x710004fca0`이다.

## 8. 다른 기능과의 상호작용

- **카메라 시계 ↔ 프레임 시간**: 애니 진행은 `delta×60×speed`(6.1). 사건은 그 틱에서 `>`를 처음 만족할 때 발생하므로 프레임이 건너뛰면 사건 프레임도 문턱을 넘을 수 있다. delta 상한 때문에 심한 프레임 지연을 실제 경과 시간 그대로 따라잡지는 않는다 [판독].
- **ComAI가 GetBarPosition을 부른다**: CPU 플레이어마다 `ComAI::Start`와 `CalcDirection`(매 틱)이 앞 벽(R)을 다시 계산한다. 이때 `MapMgr+0xCC/0xD4` 상태가 갱신된다 [판독].
  - 같은 카메라 프레임에서 다시 부르면 변화량이 0이 된다. 직전 변화량이 0이 아니었다면 "정지" 분기로 NPC 2·3에 `Stagger`가 걸린다.
  - 다음 프레임 `UpdateBar`에서는 다시 "출발" 분기가 된다. 앞 벽이 움직이는 동안 CPU가 있으면 스태거 호출이 프레임마다 반복될 수 있다 [판독 + 추정].
  - `Stagger`는 `+0x14 > 0`일 때만 막힌다. 모션이 매번 다시 시작되는지는 MotionArg forceRestart 기본값(0, 같은 해시면 무시 — 09_character)에 달렸다.
  - 공용 순서는 본편 `Map.UpdateBar` → Entity의 CPU `CalcDirection`이다(3.6). CPU끼리의 순서와 그 틱에서 참조되는 뼈 포즈는 엔진 전달·포즈 갱신 단계에 따른다. 뼈 위치를 최신 애니 프레임에서 즉시 다시 계산했다고 가정하지 않는다([mg0122.md §3.5](mg0122.md#35-프레임-실행-순서-판독)).
- **입력 차단**: Fall, Goaled 도착, `PlayerMgr ctor`(NOP·입력 끔) → `ComPlayer::Start`(입력 켬, Idle).
- **파이버 → 컴포넌트**: 이 틱의 낙하·골인 기록은 본편 파이버의 다음 확인에서 NPC 반응·종료 판정에 쓰인다(3.6).
- **결과**: `Scene+0x39c`가 켜지면 ComPlayer 판정이 멈춘다.

### 9.4 한 step 순서와 난수

step은 3.6의 **앞선 0x0B 애니 슬롯 진행 → Scene → 본편 Fiber → Entity → Physics**와 수신 목록 규칙을 따른다. 카메라 진행량은 6.1, 뼈 포즈 갱신은 공용 Rigger 참조를 적용한다.

NRO의 명시적 동기 난수 호출 [판독, 엔진 모션의 랜덤 시작 프레임 처리는 별도]:
- `MapMgr::Init`: SyncRandMod(6)
- `BarNPC::Idle`: SyncRandRangeF(3,5)
- `BarNPC::JoyIdle`: SyncRandRange(2,3), 소비 없음
- `BarNPC::Joy(true)`: SyncRandMod(2)
- `MainProc` 스태거: SyncRandMod(2)
- `NPCMgr::PlayAnim(3)`: SyncRandRange(0,3) **9회**(7명 루프 + 2명), 0·1·2는 소비 없음
- `ComAI`: SyncRandRange(10,20), (10,30), (20,80), SyncRandRangeF(레벨별)
- `ComNaviGrid::Target`: SyncRandF

### 9.5 웹 환경 때문에 바꿀 부분

| 원본 | 웹 | 동등성 |
|---|---|---|
| actor::ComActor + PhysX 캐릭터 이동 | 자체 캡슐 컨트롤러 + apx 삼각 메시·박스 | 비트 일치는 불가능. 벽·발판·낙하 판정 순서와 상수는 원본대로 둔다 |
| PhysX `Overlap`(벽-발판), `CastRay`(NaviGrid) | 원본 충돌 메시를 쓰는 겹침·레이 판정 | 박스-박스만 쓰면 삼각 메시 발판을 근사함. 형태·위치 식은 4.4·6.6·6.9 |
| 카메라 애니 `F(F(delta×60)×speed)` | 고정 step의 delta=1/60을 대입 | 기본 속도이면 1.0f/틱. 원본의 가변 delta 프레임과 사건 틱은 달라질 수 있음 |
| 가변 delta (01_core) | 고정 1/60 | 01_core 9.6 |
