CPU overlay 소비 프레임도 이 목록에 연결해야 한다. 공용 모듈 등록·정렬을 다시 분석할 필요는 없다.

## 5. 상태별 입력·종료·결과

`ComPlayer::GameStart @0x710001a270`은 입력을 켜고 위치·방향을 초기화하며 탈락 플래그를 0으로 둔다. 사람은 카메라 기준 스틱, CPU는 overlay 입력을 사용한다. NRO 고유 자이로 처리는 없다 [판독]. 현재 웹 입력은 `script/view/input.ts`의 WASD/방향키·J(A), 게임패드다. [input_web.md](../engine/input_web.md)의 새 키 배치는 **설계**이므로 현재 코드와 구분한다.

### 결과 [판독 `PlayerManager::Update @0x7100018a30`, `GameFinish @0x710001aa40`]

1. Update 시작에서 탈락자 총수 D를 먼저 센다. 새 탈락자 모두에게 **rank = 4−D**를 준다(0이 1위). 같은 갱신에서 탈락한 사람은 공동 순위이며 무작위 섞기를 하지 않는다.
2. 일반 대전 D=3이면 마지막 생존자 rank=0, winLose=1. 전원 새로 탈락한 경우에는 전원 rank=3, winLose=2로 바꾼다. 그 외 탈락자는 winLose=0(단, D=4이면 1을 쓰는 중간 분기가 있으므로 전원 동시 분기와 함께 옮긴다).
3. GameFinish에서 아직 결과가 없는 생존자는 **rank=0, winLose=1**. 시간 종료에 여러 명 살아 있으면 모두 승리한다. 공용 상태 UI/MGMgr로 각 결과를 반영한다.
4. 일반 대전에는 득점 누적이 없다. 엔들리스 `TimeRecord @0x7100019128`은 탈락 순간 또는 생존 종료 시 카운트업 현재값을 `ComUiStatus::SetTime`·`MGRecorder::SetPlayerRecord`로 기록한다. 엔들리스 최종 기록 순위의 공용 정렬은 이 고유 분기와 별개다.

**재구현 계산**(위 rank 식): 첫 1명 탈락 D=1 → rank3(4위), 첫 2명 동시 D=2 → 둘 rank2(3위), 첫 3명 동시 D=3 → 셋 rank1(2위), 생존자 rank0. 이는 실행 결과가 아니라 식의 예시다.

## 6. 핵심 알고리즘·물리·충돌·CPU

### 6.1 회전판 [판독 `UpdateRotate @0x710000f230`, `UpdatePlayer @0x710001c8c0`]

`ω = clamp(ω + dt·accel[phase]·π/180, 0, maxSpeed[phase]·π/180)`, `angle += dt·ω`. angle≥2π이면 **초과분을 버리고 0**, phase는 0→1→2→2다. 속도는 phase 전환 때 리셋하지 않는다.

플레이어 **y≤0**일 때 δ=−ω·dt로 좌표를 `(x cosδ−z sinδ, 0, z cosδ+x sinδ)`에 보정하고 방향도 Y 회전한다. **y>0**이면 이 판 이동을 적용하지 않는다. 점프가 판에 실려가는 시간을 줄이는 이유다. 캐릭터 자체 걷기·가속·A 홀드 점프는 공용 ComActor 책임이며 고유 NRO에 완결된 적분식이 없다.

→ 정리본: [17_actor.md](../engine/17_actor.md) §8.2, 10

**식1 — Boo 밀어냄** [판독 `@0x710001cd0c~0x710001cdd0`]. p는 직전 보정까지 반영한 플레이어 월드 위치, bᵢ는 i번째 Boo 월드 위치다. i 오름차순, 각 i에서 k=0..9 순으로:

`cᵢₖ=(bᵢ.x, bᵢ.y+3.5·0.25−0.5k, bᵢ.z)`, `v=p−cᵢₖ`, `d=√(v·v)`.

`d<1.4`이면 `h=(d>0 ? 1/d : d)`, **`p ← p+v·h·(1.4−d)`**, 즉시 SetPosition. 이때 `bᵢ.y≤JumpThreshold(ComPlayer+0xC0)`이면 +0xD8=1. d=0은 h=0이라 밀림도 0이며, 임의 방향을 만들지 않는다. 다음 샘플은 갱신된 p를 쓴다. dt를 곱하지 않는다. **1.4는 형상 반지름 합으로 대체하지 않는 고유 상수**다.

**식2 — 멍멍 각도 보정** [판독 `@0x710001cf1c~0x710001cf7c`, 적용 `@0x710001ce20~0x710001cea0`]. q는 해당 멍멍 월드 위치, `θ=atan2(p.x,p.z)`, `φ=atan2(q.x,q.z)`, `Δ=θ−φ`(±π 정규화 없음). **`d=‖q−(p.x,0,p.z)‖`**라 플레이어 점프 y는 거리에서 빠지지만 멍멍 y는 남는다. 상태4이며 `d<3` 및 `|Δ|·180/π<3`일 때:

`γ=(Δ<0 ? +1.5 : −1.5)·π/180`, **`p ← (p.x cosγ−p.z sinγ, p.y, p.z cosγ+p.x sinγ)`**, SetPosition. 두 x/z는 대입 전 값을 사용한다. Δ=0은 −1.5° 분기이며 y·캐릭터 방향은 유지한다. 멍멍 인덱스 순으로 즉시 적용하고 dt를 곱하지 않는다.

**식3 — 영역 제한** [판독 `@0x710001cf80~0x710001cff0`]. `r=√(p.x²+p.y²+p.z²)`. `8≤r≤16`이면 그대로, 그 밖이면 **`p ← normalizeOrZero(p)·clamp(r,8,16)`**, SetPosition. r=0의 정규화 결과는 0이며 y도 함께 스케일한다.

세 식은 **판 이동 뒤 식1→식2→식3→FX float→UpdateAnim→UpdateAction→UpdateCom** 순이다. 위치는 원본 거리 단위·Y 위쪽, 각도는 라디안·atan2(x,z) 기준이다. 수식은 원본 판독의 수학적 표기이며 f32 저장과 NEON 정규화의 반올림은 공용 수치 규칙을 따른다. 원본 dt는 GetDeltaTime의 **초**(오프라인 실측, 상한0.05), 웹 고정 1/60초는 DESIGN 3절의 근사다.

**움직이는 충돌체의 원본 연결** [판독]: CreateObj @0x7100009020은 `rotate_floor00 → pos_locator00 → ObjPos(grp05/06/07) → pos_objB/C/DNN → 개별 모델·강체`로 부착한다. B/C/D는 위치 모드(+0x68)=1·회전(+0xF8)=1·스케일(+0x188)=0. 같은 모드의 공용 해석은 완료된 [mg0508 4절](mg0508.md)을 재사용한다. 따라서 소켓 위치·회전은 따라가되 부모 스케일을 자식 스케일로 복사하지 않는다. B/C/D 모델 루트 TRS는 항등이며 각 소켓의 **EulerXYZ 회전도** 충돌 상자의 방향에 반영한다 [데이터].

CreateObjB의 `@0x710000c120~0x710000c2e0`에서 형상 로컬 위치0·회전항등, JSON 크기 벡터 그대로, `RigidBodyCreateArg+0x90/94/98=0.5/0.5/0.9`, **+0xA8=2·+0xB4=0·+0xB8=0**을 확인했다(C/D 동일). 기존 `mgD_main_physics*.c`의 Arg 배치·`FUN_710062ce50`에 따르면 운동종류0은 정적 액터 생성 분기다. **포즈가 바뀌는 엔티티에 연결된 정적 강체**이며 고유 코드에 힘·속도·키네마틱 목표 setter는 없다. layer 인자2와 Route 질의 마스크4는 구분해서 보존한다.

UpdateRotate는 판 엔티티(+0xB8)에 `SetRotation(quatY(angle))`을 쓴다. B/C/D를 고유 Tick에서 따로 적분하지 않고 부착 컴포넌트가 소켓 포즈를 전달한다. 월드 합성은 `pᵢ=Tfloor+Rfloor·sᵢ`, `qᵢ=qY(angle)·qsocketᵢ`(이 게임 항등 부모 조건), shape 월드 포즈는 여기에 shape 로컬 포즈를 합성한다. Boo/멍멍은 추가로 애니 소켓을 따른다. Boo는 UpdateAnim `@0x710000fd00~0x710000fd6c`에서 소켓 위치를 Entity.SetTranslation 후 자체 Rotate한다. 기존 `mgD_main_physics.c`의 ComRigidBody.Create(main @0x7100608b18)는 연결 초기에 Entity.GetTranslation/CalculateRotation→Collision.SetTransform을 호출한다. **공용 Entity/Physics 단계는 3.2절로 해소**됐지만 이 게임의 부착 TR을 강체 질의에 재반영하는 정확한 메시지·시점은 11절에 남는다. 모델 행렬만 움직이는 방식으로 대체할 수 없다.

접촉 응답은 기존 [mg0912 6.4절](mg0912.md)의 **DetectContactsMap→DefaultAdjustCharacterVsMap(침투 벡터)→DefaultFinalizeCharacterVsMap(평균 보정)**을 재사용한다. B/C/D 접촉을 고유 피격·탈락으로 바꾸지 않는다. Boo의 식1과 이 공용 접촉은 서로 다른 경로이며 한쪽을 임의로 지우거나 동일 침투 보정을 두 번 적용하지 않는다.

### 6.3 감전·탈락 [판독 `UpdateAction @0x710001d940`]

입력 활성·생존자에 대해 θ=atan2(player.x, player.z), α=atan2(Bilikyu[0].x,z), β=atan2(Bilikyu[2].x,z)를 읽는다. 안전 조건은 **β < θ < α**다. 경계와 같은 각도도 탈락이며, 점프 높이·NPC와의 구 거리는 이 조건에 없다.

탈락하면 +0xAE=1, 액터 충돌 플래그(+0x28) 해제, `Electric` 액션 호출·입력 끄기·`VB_MG0106_ELEC_WAVE` 중지. `ActionElectric @0x710001c2dc`는 `co_electric00`를 재생한다. 판정·진동의 나머지 연결은 7절과 같다.

**식4 — 퇴장 포물선** [판독 `UpdateAction @0x710001dc14~0x710001dd48`, 감전 초기화 `@0x710001de00~0x710001de18`; 데이터 목표점 `@0x7100048ed0`]. 감전 순간의 월드 위치를 **p₀(+0x60)**에 저장하고 **`D=t−p₀`(+0x70)**로 둔다. **`t=(−8.74227794e−7,0,20)`**이다. **u(+0x80)는 생성자에서 (0,0,0)**이며 감전 진입 코드에서는 재설정하지 않는다.

현재 actor.y<0이면 그 갱신의 퇴장 보정을 건너뛴다. 그렇지 않으면 `L=‖D‖`(y 포함), `n=normalizeOrZero(D)`를 구해 순서대로 **`u.x ← u.x+20·n.x·dt`**, **`u.z ← u.z+20·n.z·dt`**를 f32로 저장한다. u.y는 사용하지 않는다. **`h=√(u.x²+u.z²)`**, **`a=(D.y−tan(45·π/180)·L)/(L²)`**로 놓고:

**`p=(p₀.x+u.x, p₀.y+tan(45·π/180)·h+a·h², p₀.z+u.z)`**, actor.SetPosition.

20의 단위는 원본 거리/초이며 수평 속력은 `20·√(n.x²+n.z²)`다. y 식은 시간 적분·중력9.8 대신 **누적 수평 거리 h**를 쓴다. 분모의 L을 수평 목표 거리로 바꾸거나 도착점에서 멈추지 않는다. L=0의 분모 보호는 없다. 탈락을 세운 **같은 호출에서** 첫 변위를 적용하며 모션 완료를 기다리지 않는다. 이후 +0xAE가 켜져 있으면 플레이 활성(+0xA8)이 꺼져도 이 분기는 계속 처리되고, y<0 검사 또는 GameEndingBefore의 +0xAD Tick 중지로 보정이 멈춘다.

### 6.4 장애물 애니메이션 [판독 `UpdateAnim @0x710000f4e0`]

슬롯의 공용 진행은 [mg0101 6.1절·3.6절](mg0101.md)의 완료된 판독을 참조한다. `main FUN_710080cd70 → 80d890 → 81cf30 → 8144bc`에서 **f32(delta×60)×슬롯 속도**, AnimationModule의 **0x0B** 처리다. 고유 UpdateAnim의 속도 변경과 슬롯 프레임 누적을 이중 적용하지 않는다. 뼈 포즈 완성은 슬롯 진행과 별도이며 [mg0122 3.5절](mg0122.md#35-프레임-실행-순서-판독)의 Rigger/UpdateTiming 규칙을 따른다. 아래 초기 SetFrame 요청의 범위 정규화만 아직 연결되지 않았다.

- Boo: `pos_objA_teresa00` 소켓의 위치를 갱신하고 `ω+2π/period[phase]`에 dt를 곱해 자체 회전한다. 슬롯0/1 속도는 phase별 1.9/2.2/2.5. 주 모션 프레임이 **[0,60] 또는 [150,210]**이면 AnimObj+0x3C의 **f32 경과시간 < (3.5−1)=2.5초** 동안 주 모션 속도0·경과시간+=dt, 이후 phase 속도를 복구한다. 구간 밖에서 경과시간을 0으로 초기화한다. 디컴파일의 `int` 변환은 잘못된 타입 추론이다(`@0x710000fa6c~0x710000fabc`, `ldr/fadd/str s` 확인). 상승 루프 SE는 **20<frame≤150**, 하강은 **170<frame≤300**에서 속도>0일 때 시작하며 **0<frame≤20, 150<frame≤170**에서는 정지한다.
- 멍멍 상태: **0 초기 ObjEInit→1 각도>−60°에서 대기→2 ObjWanwanStart 완료 대기→3 ObjEIn·ObjWanwanIn 시작 및 Mouth 예약→4 충돌 유효 구간→5 마지막 10프레임부터 루프 SE 정지→6 ObjWanwanEnd 후 −90°<각도<−60°에서 0**. 종료를 임의 시간으로 대신하지 않고 클립 프레임/완료를 사용한다.
- 배치 선택은 난수가 아니라 `GameWork::GetGameStage`: 0→grp05, 1→grp06, 2→grp07, 그 밖→grp05다(`ComMap` 생성자 @0x7100008784, CreateObj @0x7100009020).
- Boo 초기 주 모션도 결정적이다(`CreateObjA @0x710000ad20`): grp05/06의 인덱스 **5~9·20~24**, grp07의 **10~14**는 홀수0·짝수150프레임. 나머지는 `i%5==0`일 때 **[40,180,20,180,120,0][min(floor(i/5),5)]**, 그 외는 이전 Boo의 GetFrame+60을 SetFrame에 전달한다. 루프 클립의 범위 처리까지 새 난수나 임의 위상으로 대체하지 않는다.

### 6.5 CPU [판독·데이터]

`UpdateParam @0x710001c5a0`은 CPU 최초 한 번만 초기화한다. 난수 호출 순서는 **JumpInterval+U(0,.2), JumpThreshold+U(0,.2), MoveInterval+U(0,.2), 첫 대기 U(0,1), MoveArea+U(0,10)**이고 JumpLength는 그대로다. 모두 SyncRandRangeF. 이름상 JumpThreshold를 성공 확률로 오해하지 않는다. 실제로는 낮은 Boo 접촉 요청의 **높이 비교**에 쓴다.

`UpdateCom @0x710001d100`은 생존·활성 CPU만 처리한다. 매번 Route.GetTargetRouteData로 목표를 얻는다. θ는 플레이어 각도, β는 Bilikyu[2] 각도, area는 보정 MoveArea다.

| CPU 상태 | 동작·전환 |
|---|---|
| 0 대기 | 스틱 0, 대기시간 +=dt. `(첫 이동 전 && time>첫대기) || time>MoveInterval`이며 **θ>β+(area+10)°**일 때 1로 전환 |
| 1 이동 | 목표−현재를 정규화하여 스틱 **(−dir.z, dir.x)**. θ<β+area°이면 0. 그 밖에서 y≤0이고 +0xD8이면 **A trigger=1, hold=0**, 점프 시간=0, 상태2 |

버튼 1·스틱 축 변환·JumpLength 곱은 AArch64 `@0x710001d480~0x710001d5c4`로 확인했다. CPU가 “잘 뛰는 확률” 하나로 움직이는 방식이 아니다.

Route는 **100×5** 표를 사용한다. Setup @0x7100011360은 Physics.CastShape로 **0 빈 곳 / 1 ObjA / 2 ObjE / 3 기타**를 기록한다. Update @0x71000115ec은 회전 좌표와 Boo 높이를 갱신하고 **내려가면 방향1, 올라가면0, 같은 높이면 이전 방향 유지**다. GetTargetRouteData @0x71000118d0은 현재보다 각도가 작은 가장 가까운 줄 j를 고르고 차이<1°이면 j−1(0이면99)을 사용한다.

`GetTargetRouteNodeID @0x7100011b60`은 같은 반경 인덱스 k=0..4에 대해 j·j+1·j−1·j−2를 검사하고 **아래 단계에서 후보가 하나라도 나오면 다음 단계로 가지 않는다** [판독: 점프 표 `0x7100048f56=[0,10,18,23]`, 분기 `@0x71000128d8~0x7100012958`]. j−2는 j=0·1에서 **98**로 잡는 원본 분기 그대로다.

| 단계 | 필요한 안전 줄 |
|---|---|
| 0 | j, j+1, j−1, j−2 모두 |
| 1 | j, j+1, j−1 |
| 2 | j, j+1 |
| 3 | j만 |

빈 노드는 안전하다. Boo는 **하강 중·높이≤1.5**일 때 j/j−1/j−2에서 안전하지만 j+1은 빈 노드만 허용한다. 어느 반경에든 ObjE가 있는 줄은 해당 후보의 저장 shape로 **위쪽 1.0 거리 CastShape(레이어 인자4)**를 다시 해서 무충돌이면 안전, 충돌이면 위 Boo 조건(j+1 제외)으로 돌아간다. 네 단계 모두 플레이어→j의 후보까지 **CastRay(레이어4)**가 없거나 첫 충돌 태그가 **ObjA**인 후보만 허용한다. 그 단계에서 **벡터 거리 최소**를 선택하며 엄격한 `<` 비교라 동점은 먼저 검사한 k를 유지한다. 모두 실패하면 **SyncRandMod(5)**로 k를 고른다(`@0x71000119ec`). 디컴파일은 네 단계 switch를 하나로 지워 놓았으므로 단일 AND 조건만 옮기면 잘못된다.

### 9.3 움직이는 충돌을 위한 추가 계약 [웹 소스 확인·구현 제안]

현재 `stage3d/types.ts::Collider`는 **groundHeight(x,z,fromY?) / collide(pos,move,radius,height)** 두 질의뿐이다. `MeshCollider`는 생성 때 월드 정점·법선·XZ 격자를 고정하고 obj의 matrixWorld를 질의에 쓰지 않으며 `merge`도 월드 정점을 복사한다. **포즈 갱신, 회전 OBB/캡슐, 임의 방향 CastRay/CastShape, 레이어·태그·침투 목록이 없다.** `Stage3D.setCollider`는 참조만 넣고 update가 충돌 변환을 동기화하지 않는다. `PlazaMover.integrate`는 수평 이동이 0이면 collide를 부르지 않아 가만히 있는 사람에게 상자가 들어오는 접촉도 빠진다. 광장 THREE 기반 이동기·렌더러를 그대로 순수 GameLogic에 넣을 수도 없다. 06_scene_data의 웹 대안은 구현 완료를 뜻하지 않는다.

| 추가할 로직 계약(제안 이름) | 필요한 입력·상태·출력 |
|---|---|
| `registerShape(id,geometry,localPose,layer,tag)` | B/C/D 반폭 상자·A/E 캡슐, 4·6.2절의 소켓/엔티티 ID, 활성 상태. CreateBox 크기를 다시 절반으로 나누지 않음 |
| `beginFrame(frame)`·`setPose(id,pose)`·`commitPoses()` | 순수 숫자 월드 위치·quat, 이전/현재 포즈, 현재 AABB·공간 색인. 모든 소켓 갱신을 같은 스텝에 일괄 반영; 질의 중 서로 다른 프레임 포즈 혼용 금지 |
| `castRay(origin,dir,distance,mask)`·`castShape(shape,pose,dir,distance,mask)` | Route의 마스크4·첫 ObjA 허용·E 위쪽 스윕, 공용 접지 검사. hit의 ID/태그·거리·위치·법선·initialOverlap을 반환 |
| `contacts(actorShape,pose,mask)`·`resolveContacts(contacts)` | 이동 0이어도 수행, 회전 상자/캡슐과의 3D 침투 벡터·개수. 원본 접촉 평균 보정과 고유 식1/2를 분리. 선택한 스윕/침투 근사는 표시 |
| 충돌 상태 수명 | GameInit 초기 포즈 확정 후 Route.Setup; GameEnd는 마지막 포즈를 유지하고 이동·클립만 정지; scene 종료 시 ID·형상·색인을 해제. 판의 명시적 운반(6.1)에 추가 플랫폼 운반을 자동 중복하지 않음 |

부착 포즈는 **로직의 클립 프레임과 원본/변환 데이터의 뼈 샘플**로 계산해 collision/state에 함께 둔다. `getSocket()`·Stage3D.update는 화면 적용용이며 충돌의 시간 기준이 아니다. 이전 포즈를 보관하는 것은 스윕을 선택할 때 필요한 구현 상태로, 원본의 회전 CCD 적용이 확인되었다는 뜻은 아니다.

고정 스텝 연결 **제안**: 3.2절의 **Scene/Fiber 결과·종료 확인→Entity 갱신→Physics→Entity 후처리** 단계를 유지한다. 순위 확인은 앞선 Entity 결과를 읽는다. Entity 안에서는 Map의 회전·속도/상태·Route와 공용 액터·고유 UpdatePlayer(식1→2→3→FX→Anim→Action 식4)→UpdateCom을 각각 보존하고, 부착 TR·형상 포즈·색인 갱신을 실제 수신 관계에 맞춰 배치한다. 클립 진행은 6.4절의 별도 슬롯 단계로 두며 렌더는 state/events만 읽는다. **Map/Actor/Player·부착/강체의 상세 상대 순서는 아직 확보되지 않았으므로 임의의 한 줄 순서로 확정하지 않는다.** 이전 포즈·현재 포즈를 혼용하지 않는 9.3 계약은 구현 요구사항이며 원본 메시지 호출 순서의 증거가 아니다.

### 9.4 구현 우선순위

1. 7절에서 확인한 배치 TRS·충돌 모델·카메라 커브·클립 길이로 data/manifest를 만든다.
2. 9.3절의 움직이는 형상·질의·접촉 보정 계약부터 마련한 뒤 회전→지상 이동→식1~4→순위·종료를 연결한다. 기존 정적 MeshCollider만으로 진행하지 않는다.
3. 6.5절의 Route 네 단계·동점·SyncRandMod(5)와 CPU overlay를 연결한다.
4. 공용 렌더러·에셋 관리자, START/FINISH·기록 UI·FX/SE를 연결한다. 게임 등록은 이후 구현 작업이다.

## 11. 미확정 사항과 추가 분석에 필요한 근거

**mg0106 고유 연결에서 남은 항목**만 아래에 둔다. 공용 단계 순서·Box 반폭·actorparam 로더·점프 계산기·모드 flag1·결과 무대 책임은 8절 참조로 해소했으므로 다시 분석하지 않는다.

| 고유 미확인 연결 | 이미 확인한 범위 / 추가로 필요한 근거 |
|---|---|
| 움직이는 부착/강체와 Map·Actor·Player 판정의 실제 포즈 시점 | Scene→Fiber→Entity 및 물리 단계·컴포넌트 배열 전달은 확정. mg0106의 활성 수신 그룹/목록, 부착 의존 관계, 해당 강체가 TR을 질의에 반영하는 메시지, Rigger UpdateTiming 적용값·접촉 포즈 스냅샷은 없음. 모델 포즈와 물리 포즈를 같은 시점으로 합치지 않음 |
| 게임 ActorParam.json 소비·최종 액터 캡슐/초기 점프 속도 | MatterType2의 공용 로더·이동값·SetupLegacy 연결은 확정. 고유 SetParams는 MapParam·ComParam만 읽고 생성자는 PCIndividualScale을 적용한다. **ModelScale/ColRadius 0.8 파일의 적용 경로와 스케일 이후 충돌 형상**이 확보되지 않아 반지름0.8로 단정하지 않음. 최종 초기 점프 속도는 공용 필드 소비의 미확정까지 연결해야 함 |
| 전기 거리값의 최종 진동 연결 | `bv_mg0106_elec_distance` 설정·VB_MG0106_ELEC_WAVE/Stop·진동 파일/루프/게인은 확정(7절). 이 변수→게인/조건 연결식은 확보되지 않음. FTRG 조건 그래프 또는 해당 변수 소비 근거가 필요하며 선형 감쇠를 임의로 추가하지 않음 |

**공통 분석에 남아 있는 경계**는 고유 분석을 반복해 해소하지 않는다: 접촉 생성/배열 순서·회전 경로 CCD·캐릭터끼리 응답은 [mg0912 6.4절](mg0912.md), 캐릭터별 보이스 자원 선택·모션 0f 이벤트의 첫 처리 시점은 [05_ui_input 7.5절](../engine/05_ui_input.md)·[09_character 8절](../engine/09_character.md), Boo 초기 SetFrame 요청의 300f 초과 정규화는 공용 슬롯 규칙(6.4절)에 속한다. 슬롯 진행량은 확인됐지만 이 직접 SetFrame 처리까지 확인한 것은 아니다.
