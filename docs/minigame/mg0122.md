# mg0122 다 함께 찰칵 (Camera-Ready / みんなでパシャリ)

2026-10-08 갱신. 상태: **사진 판정·카메라 조작·라운드 흐름 판독 및 합성 계산 확인. 공용 웹 기반·목록 자료는 구현 완료, mg0122 전용 게임은 추가 구현 필요. NPC 배치·행동·원본 실행 대조는 미완**. 이번 갱신은 현재 작업 트리의 구현과 원본 코드를 대조한 문서 수정이며 포팅 코드를 작성하지 않았다.
확정 수준 표기: **[실행]** 원본 실행 확인, **[판독]** 원본 코드 판독, **[데이터]** 데이터 확인, **[추정]**, **[미확정]**. 이 문서에 [실행]은 없다. 재구현 계산은 "재구현 계산"이라고 따로 적는다.
**[웹 코드 확인]**은 현재 구현을 읽어 확인했다는 뜻이며 원본과의 동등성이나 브라우저 실행 검증을 뜻하지 않는다. 구현 상태는 **구현 완료 / 부분 구현 / 추가 구현 필요 / 미확인**으로 구분한다(9.7~9.10, 11절).

## 1. 기능 개요와 사용자에게 보이는 동작

4인 대전(VS4) 미니게임이다. 공원 한가운데에서 각자 자기 화면(4분할)의 카메라를 돌리고 당겨, 문제로 제시된 사진과 최대한 비슷한 사진을 찍는다.

- 3라운드로 진행한다. 라운드마다 순서가 같다.
  - 게임이 먼저 "문제 사진"을 찍어 보여준다(특정 NPC 무리가 화면 한가운데 오도록 자동 구도).
  - 플레이어는 30초 안에 한 번만 셔터를 누를 수 있다(4명 모두 찍으면 바로 끝).
  - 점수는 라운드마다 0~100점이고, 3라운드 합계로 순위를 정한다(6.7).
- 점수는 두 부분을 섞는다(6.4~6.6).
  - **카메라 방향·줌이 문제와 얼마나 가까운지**(근접도, 가중 0.7)
  - **사진 속 NPC 구성·위치가 문제와 얼마나 같은지**(NPC 점수, 가중 0.3)
- 조작 [데이터 `mg_inst.json`]:
  - 스틱 = 카메라 움직이기
  - (X)/(ZR로 추정) = 줌 인, (Y)/(ZL로 추정) = 줌 아웃
  - (A) = 사진 찍기

| 근거 | 내용 |
|---|---|
| [데이터] `mgListND.json` | `"Name":"mg0122","GameRule":"VS4","Gyro":-1,"OpeningSkip":1,"StatusFace":"None"` |
| [데이터] `im_mg_inst.json` | "제시된 사진과 최대한 비슷하게 사진을 찍으세요. 3라운드 승부입니다." |
| [데이터] `mg_inst.json` | `inst_mg0122_ctrl00` " 카메라 움직이기", `ctrl01` "() 줌 인", `ctrl02` "() 줌 아웃", `ctrl03` " 사진 찍기" |

## 3. 진입점과 전체 호출 흐름

### 3.1 클래스 구성 [판독]

```
mg0122::Scene : bq::MinigameScene        SyncedSetupGameImpl → GameMgr 생성·Initialize
  GameMgr (singleton)   라운드 상태기계(+0xA0), 매니저 묶음, 옵서버 방송(ObserverBroadcast(id))
    GameParam      config.csv(I[]/F[]), 질문 영역·NPC 추첨·ViewVolume·CPU 표
    QuestionParam  question.csv 27×7
    NpcLotteryTable npc_lottery.csv
    QuestionMgr    라운드별 문제(질문 ID 3개), 문제 사진 촬영, JustTiming, 문제 NPC 목록(+600)
    MapMgr/MapData 맵 엔티티, 기믹(벤치·나무·노점·공중 등 29종) 배치
    NpcMgr         NPC 목록(GetNpcListData) — NpcBase 파생 50여 종
    CameraMgr      Camera×4 (플레이어별, 4분할)
    PlayerMgr      Player×4 (+ CPU), 촬영 비트(+0x1E8)·촬영 수(+0x1F4), 순위
    UIMgr          타이머·점수·문제 사진 표시
    EmitMgr        SE·진동·이펙트 묶음
BaseObject / BaseUpdateObject / GimmickObject : 공통 기반(엔티티, 모션, 타이머 TimeUpdate/IsFinishedTime, Notify)
```

`GameMgr::ObserverBroadcast(id)`는 등록된 모든 객체의 `Notify(id, value)`를 부른다. 라운드 단계가 바뀔 때 id를 방송한다(3.3).

### 3.2 장면 준비 [판독]

- `Scene::SyncedSetupGameImpl @0x710005bad8`이 장면 설정 객체를 만든다.
  - `+0x08` f32 = **30.0**(라운드 제한 시간), `+0x0C` int = **3**(라운드 수) [판독].
  - 이어서 `GameMgr` 생성 → `GameMgr::Initialize`.
- `GameParam::Initialize @0x7100052314`
  - `SetupParam`(config.csv)
  - `+0x50 = (SyncRandMod(100) < 51)`.
  - `+0x54`: r = SyncRandMod(100)을 I[24], I[25], I[26](33, 33, 34) 누적과 비교해 20 / 21 / 22 / −1을 고른다.
  - 디컴파일의 오프셋 0x60/0x64/0x68 = I 배열 24~26번이다 [판독 + 데이터].
  - `SetupAir`, `SetupFreeArea`, `SetupViewVolume`, `SetupCom`.
  - 이 과정에서 동기 난수를 많이 쓴다(9.4).
- `QuestionMgr::InitializeQuestion1 @0x710005a500`: 라운드 0,1,2 문제를 정한다(6.1).
- `CameraMgr::Initialize @0x710001fea0`
  - `Camera(1,0)`, `(2,1)`, `(4,2)`, `(8,3)` 4개를 만든다(레이어 비트, 플레이어 번호).
  - 첫 문제 기믹 방향 + 180°를 첫 라운드 시작 yaw로 저장한다(`+0x200`).
- `Camera::PrepareGame @0x710001a564`
  - 기준점 `base(+0x390) = (0, 카메라 y, 0)`, `baseZoom(+0x3B8) = |카메라 위치의 xz|`, 줌 = baseZoom.
  - 시작 회전 = `CalcViewAngle(전방)`.
  - `mg0122_cam_game.fsnb` 값 pos (0, 2.56, −0.72), aim (0, 2.47, −1.25) → 기준 (0, 2.56, 0), baseZoom 0.72 [데이터 + 추정].

### 3.3 라운드 상태기계 `GameMgr::UpdateGameMainSequence @0x7100027720` [판독]

`GameMgr+0xAC` = 라운드 경과 시간(매 프레임 += dt, 방송 0x2C에서 0). `+0xA8` = 단계 내 타이머.

| 단계(+0xA0) | 동작 | 다음 | 방송 |
|---|---|---|---|
| 1 (방송 0x14로 진입) | 0.1 s 대기 → 라운드 텔롭 | 6 | 0x25 |
| 2 | 페이드아웃 끝 대기 | 3 | 0x26 |
| 3 | 0.1 s → 4개 레이어 갱신 | 4 | 0x27 |
| 4 | 0.2 s 이상 + 문제 촬영 끝 → 페이드인 | 5 | 0x28 |
| 5 | 페이드 끝 → 라운드 텔롭 | 6 | — |
| 6 | 텔롭 끝 (첫 라운드면 0x2C 먼저) | 7 | 0x29 |
| 7 | 시작 연출 끝 → 휘슬 | 8 | **0x2A (조작 시작)** |
| 8 | 타이머 끝 **또는 4명 모두 촬영**(`PlayerMgr+0x1F4 > 3`) | 9 | 0x2B (조작 끝) |
| 9 | 1.0 s + 판정 중인 플레이어 없음 | 10 | — |
| 10 | `PlayerMgr::ScoreIn` | 11 | 0x2E |
| 11 | 점수 발표 완료를 기다린 뒤 2.0 s → `ScoreOut`, `QuestionMgr::NextRound`(이전 round > 2면 끝) | 12(끝) 또는 2 + 페이드아웃 | — |

- 타이머는 `UIMgr::RoundStart @0x710005f500`에서 `ComUiTimer::SetTimer(장면설정+0x08 = 30.0)`로 건다 [판독].
- 오프닝·첫 문제 촬영의 상태 전이는 추가 판독했다(5.5). 실제 카메라·UI 연출 시간 전체의 실행 대조는 **[미확정]**.
- **원본 round는 1~3, 질문 배열 인덱스는 0~2**다. `GameMgr::SetUpGame @0x7100025f90`의 QuestionMgr 초기화는 `+0x1E0=-1, +0x1E4=1`; `QuestionMgr::Notify`는 `round-1`로 배열을 읽는다. `NextRound @0x710005ad08`은 이전 값 > 2를 반환한 뒤 round를 1 증가시킨다(3→4에서 종료). 웹에서 0 기반 round를 쓰면 이 변환을 명시한다.

### 3.4 플레이어 한 라운드 [판독 `Player::Notify @0x7100055c8c`]

- 방송 0x2A
  - `captured(+0x221) = 0`, `roundScore(+0x22C) = 0`, `ComControlConfig()`(CPU 값 추첨), `inputEnabled(+0x220) = 1`.
  - 매 프레임 함수를 `PhoneControl`로 둔다.
- `PhoneControl @0x7100056204` (매 프레임):
  1. 사람이면 패드 → 회전 속도·줌 속도(6.1)를 구한다. CPU면 CPU 함수(`+0x2D0`)가 같은 값을 만든다.
  2. `Camera::CameraMove2(zoomRate, rotRate)`
  3. 셔터
     - 사람: `ComActorPad::GetTrigger() & 1`
     - CPU: `+0x2A8`
     - 셔터가 눌리면 `StartCapture`.
- `StartCapture @0x7100056c30`
  - 방송 0x2D, `ForceCalculateView`, `captured = 1`.
  - `PlayerMgr+0x1E8 |= 1<<idx`, `PlayerMgr+0x1F4++`, 보이스 `SQ_VOI_PC%02d_ETC`.
  - 다음 프레임 함수를 `UpdateCapture`로 둔다.
- `UpdateCapture @0x7100056d30`
  - 1프레임(`GetTimePerFrame`) 뒤 점수를 계산한다(6.6, `CalcScore`와 같은 식).
  - `Camera::GameCapture`(화면 캡처) → `QuestionCheck`.
- `QuestionCheck`: 0.3 s 뒤 판정 중 플래그 해제, 그래픽 레이어 갱신.
- 방송 0x2B: `inputEnabled = 0`. 찍지 않았으면 파인더 숨김.
- 방송 0x2E: 안 찍은 사람 화면 검게.
- 방송 0x34+idx
  - 점수 보이스: ≤ 0 `SAD`, 1~30 `ENVY`, 31~90 `JOY_MID`, > 90 `JOY_HIGH`(`SQ_VOI_PC%02d_*`).

**한 라운드에 한 번만 찍는다**: `StartCapture` 뒤 `PhoneControl`이 다시 걸리지 않는다. 0x2A 방송은 라운드 시작 때만 온다 [판독 + 추정].

### 5.2 문제 선택 [판독 `InitializeQuestion1`, `MapData::FindQuestionPatternGimmick @0x71000368b0`]

- 라운드 i(0~2)마다 `Qtbl[i]`의 질문들을 차례로 본다.
  - 그 질문 기믹 종류의 배치 후보(`MapData+0x238 + 종류·0x18` 목록)를 모은다.
  - 아직 문제로 안 쓴(+0x20 == −1) 것만 넣는다.
  - 두 번째 이후 라운드는 이전 문제 방향과 `CheckPlacement`(배치 각도)가 맞는 것만 넣는다.
- 후보 중 `SyncRandMod(후보 수)`로 하나 고른다(`@0x7100036ad8`). 그 기믹의 질문 ID를 저장하고 +0x24 = 라운드 번호+1로 표시한다.
- **[판독] `CheckPlacement @0x7100036b50`**: 일반 기믹은 이전 문제 방향과 `+0x30` 방향의 `abs(wrap180(diff)) >= 100°`일 때 허용한다. Walk(20~22)는 `GetPlacementPromenadeNumber`의 `n*90°`, Run(23)은 `wrap180(baseAngle + wrap180(n/−3*360°))` 후보 중 조건을 만족하면서 각도 차가 가장 큰 n을 고른다(동률은 먼저 본 후보 유지). 반환 하위 32비트는 허용 여부, 상위 32비트는 선택 n(일반 기믹은 −1).
- **[판독 + 디스어셈블리] `GetQuestionPlacementDeg @0x7100037040`**: Walk는 저장 n(`+0x28`)*90°를 wrap, Run은 baseAngle(`+0x30`)+wrap(n/−3*360°)를 wrap, 나머지는 `+0x30`을 반환한다. 디컴파일이 float 반환을 void로 표시하지만 `mgE_mg0122_dis.txt @0x7100037118`의 `ldr s0,[x1,#0x30]`로 확인된다.
- 각도 규칙은 확인됐으나 산책·달리기 후보 번호 목록의 생성·갱신과 NPC 실제 배치의 전체 난수 순서는 **[미확정]**.

### 5.3 문제 사진 [판독 `QuestionMgr::QuestionCapture @0x710005a810`]

```ts
B = camera0.base;  d = targetPos - B;             // targetPos = 문제 NPC의 GetQuestionPosition
yaw   = wrap180(atan2(dx / |dxz|, dz / |dxz|) * 57.29578)
v     = (0, -(p0 + dy), |dxz|)  (정규화)
pitch = atan2(v.y, v.z) * 57.29578                 // 양수 = 내려다봄
zoom  = sqrt(dx² + (p0 + dy)² + dz²) - p1          // 조준점까지 p1 만큼 남기고 전진
Q.angle = yaw; Q.height = pitch; Q.zoom = zoom; Q.uniqueSuccessPercent = 1.0
camera0.SetCameraDirection(yaw, pitch, zoom)       // 회전 클램프·줌 클램프 적용
1 프레임 뒤: Q.npcs = AddCameraInSightNpcData(camera0); camera0.QuestionCapture()(문제 화면 저장)
```

- p0, p1 = question.csv id0, id1.
- `atan2` 인자 순서와 정규화는 디컴파일(`fVar39`, `fVar20`)에서 읽었다. 0 나누기 보호(벡터 0이면 성분 0)가 있다 [판독].
- **문제의 줌·각도는 클램프된다.** 문제 값이 pitch 범위(−15.3~17.7)나 줌 범위(0.72~17)를 넘으면 문제 사진은 클램프된 구도다. 그러나 `Q.*`는 클램프 전 값이 저장된다(SetCameraDirection 전에 저장) [판독]. 원본 그대로 둔다.

### 5.4 JustTiming [판독 `QuestionMgr::Notify @0x710005a6cc`, 디스어셈블리]

방송 0x26 또는 0x0D를 받으면 다음을 한다.
- `lo, hi = (I7, I8) 또는 (I9, I10)`(질문 id6 > 0)
- `+0x1EC = lo' + SyncRandMod(hi' − lo' + 1)` (lo' = min, hi' = max)

`GetJustTimingRemainingTime = +0x1EC − GameMgr+0xAC`이다. CPU 셔터 판단에서 사용하는 것은 확인했다(6.8). **CPU만 사용한다고 확정할 수 없다.** `NpcBase::Notify @0x710000a620`도 방송 0x0D를 가상 함수 +0x230에 전달한다. 이 방송과 각 NPC 행동·성공 순간의 대응 및 JustTiming getter의 NPC 쪽 전수 사용 여부는 **[미확정]**.

## 6. 계산식·조건·상세 의사코드

### 6.1 카메라 조작 [판독 `Player::PhoneControl`, `PlayerControl @0x7100056a0c`, `Camera::CameraMove2 @0x710001b1c8`]

```ts
// 입력 → 속도
rotRate = { pitch: -stick.y * 30, yaw: -stick.x * 40 }            // F10, F9 (°/s)
if (|rotRate|² <= 0.01) {                                         // 스틱이 거의 0 일 때만 버튼
  if (hold & 0x100) rotRate.yaw = +40; else if (hold & 0x200) rotRate.yaw = -40;
  if (hold & 0x800) rotRate.pitch = -30; else if (hold & 0x400) rotRate.pitch = +30;
}
if (hold & 0xA4)      { zoomRate = +zoomSpeed; zoomSpeed = clamp(zoomSpeed + dt*2, 0, 6) }   // 줌 인
else if (hold & 0x52) { zoomRate = -zoomSpeed; zoomSpeed = clamp(zoomSpeed + dt*2, 0, 6) }   // 줌 아웃
else zoomRate = 0
if ((release & 0xF6) || 방향 반전) { zoomSpeed = 3; zoomRate = sign(zoomRate) * 3 }
lastZoomDir = zoomRate
// 카메라 갱신
cam.rot.pitch += rotRate.pitch * dt; cam.rot.yaw += rotRate.yaw * dt
cam.rot.pitch = clamp(cam.rot.pitch, -15.3, 17.7); cam.rot.yaw = wrap180(cam.rot.yaw)
cam.zoom = clamp(cam.zoom + zoomRate * dt, baseZoom(0.72), 17)
cam.offset = rotate(EulerXYZ(pitch, yaw, 0), (0,0,1)) * cam.zoom   // ComActor 쿼터니언 × UnitZ
cam.pos = base + offset
TestCollision2(); ForceCalculateView()
```

- 버튼 비트(ComActorPad)
  - 0x100/0x200/0x400/0x800은 방향키, 0xA4/0x52는 줌 버튼 묶음, 0x01은 A로 보인다.
  - 비트 ↔ 실제 버튼 대응은 actor 패드 표를 보지 않았다 **[미확정]**. 메시지 글리프 E002(X), E009, E003(Y), E008과 맞춰야 한다.
- "줌"은 렌즈가 아니라 **카메라가 바라보는 방향으로 기준점에서 전진한 거리**다. 화각은 fsnb 고정값(fovy 0.61177 rad ≈ 35.05°)이다 [판독 + 데이터].
- 회전: `rot = (pitch, yaw)` → `SetRotationFromEuler`(bezel EulerXYZ, R = Rz·Ry·Rx — 03_graphics 결론). yaw 0 = +z 방향, pitch 양수 = 아래 [판독 + 추정].
- **[판독] `TestCollision2 @0x710001b7f0`**은 `CollisionShape::SetCapsule(0.3, (zoom+3)*0.5)`로 **캡슐**을 만들고 `PhysicsModule::Overlap` → `Stage` 태그 필터 → `ComputePenetration`으로 관통 보정을 누적한다. 충돌 시 `MoveAim @0x710001fb58`을 호출한다.
- `MoveAim`은 `offset+보정벡터`에서 회전을 다시 계산하여 `+0x200`에 저장하고, 길이에서 **zoom(+0x270)도 다시 계산·클램프**한다. 따라서 단순 위치 이동이 아니며 근접도와 NPC 투영 모두에 영향을 줄 수 있다. PhysX 캡슐/맵 메시 질의의 정확한 웹 대체, 겹침 결과 순서·캡슐 API 길이 정의의 동등성은 **[미확정]**.

### 6.2 시야 판정 (사진 속 NPC) [판독 `GimmickObject::TestCameraWithInSightByViewRect @0x7100009090`, `CalcViewRect`, `ApplyViewVolume @0x7100009a5c`]

- NPC마다 ViewVolume(volume.csv 행, `+600` 포인터)이 있다.
  - 모델 회전을 적용한 상자 8꼭짓점을 만든다(ApplyViewVolume).
  - `CalcViewRect`로 화면(NDC) 사각형 (x0,y0)-(x1,y1)을 구한다. 디컴파일은 최소값만 반환하는 것처럼 보이지만 **실제 반환은 v0=min, v1=max 두 벡터**다(`mgE_mg0122_dis.txt @0x71000090fc~0x7100009108`, `@0x7100009758~0x7100009778`). min 초기값은 (1,1,1), max는 (−1,−1,−1)이며 유효한 꼭짓점마다 갱신한다. 무한대 초기값으로 바꾸면 원본과 달라진다.
  - `GetProjectionPosFrom3DPos @0x710001e75c`는 **w==0만 실패**로 처리한다. w<0인 점을 여기서 일괄 제외하지 않는다. 별도의 객체 표시·시야 선행 조건까지 함께 옮겨야 한다.
- `TestCameraWithInSightByViewRect(player)`
  - 그 플레이어 카메라에서 보이기로 된 객체(+0x1C8+p·0x18 비트 && +0x1BC+p·0x18 > 0)인지 먼저 본다.
  - 판정은 `frac = |clamp(rect, −1..1) 넓이| / |rect 넓이|`이다. `frac ≥ volume.threshold(+0x20)`이면 사진 속에 있다.
- volume.csv 열 [데이터]: 12행.
  - **[판독]** (크기 x, y, z, 로컬 오프셋 x, y, z, 문턱) 순서다. `SetupViewVolume @0x7100053020`은 12행을 0x30 B 간격으로 저장한다: `+0x00..08` 크기, `+0x10..18` 오프셋, `+0x20` 문턱. `ApplyViewVolume @0x7100009a5c`이 크기를 0.5배 하여 회전된 8꼭짓점을 만들고 오프셋도 객체 회전에 따라 옮기는 것을 확인했다.
  - 예: 행0 `1,1.2,1,0,0.6,0,0.5`(문턱 0.5 = 절반 이상 화면 안).
  - `NpcBase::SetupViewVolume @0x710000a524`의 타입 ID→행은 `0x20→0, 0x0B→1, 5→2, 0x2E→3, 0x24→4, 0x1C→5, 0x5B→6, 99→7, 0x1A→8, 0x38→9, 0x39→10`이다. 다른 타입은 이 함수에서 볼륨 포인터를 설정하지 않는다. 타입 ID의 실제 이름·행11의 별도 사용처는 **[미확정]**.
- NPC 기준점: `NpcBase::GetCaptureBasePosition`(가상 +0x328)의 월드 위치를 투영해 화면 위치·깊이를 얻는다.

### 6.4 카메라 근접도 `Player::CalcCameraScore @0x71000570e0` [판독: 디스어셈블리, 반환 s0·s1 두 값]

```ts
dh = |Q.height - cam.pitch|
da = |wrap180(Q.angle - cam.yaw)|
dz = |Q.zoom   - cam.zoom|
// s0: 벌점 배율 (CalcScore 에서 쓰지 않음)
m = 1
if (dh - tolH > 0) m = min(1, (minF - 1) * min((dh - tolH) / rangeH, 1) + 1)
if (da - tolA > 0) m = min(m, (minF - 1) * min((da - tolA) / rangeA, 1) + 1)
if (dz - tolZ > 0) m = min(m, (minF - 1) * min((dz - tolZ) / rangeZ, 1) + 1)
// s1: 근접도
rH = max(dh / (tolH + rangeH), 0); rA = da / (tolA + rangeA); rZ = dz / (tolZ + rangeZ)
r  = max(rH, rA, rZ)                     // fcsel gt 순서: (rH > rA ? rH : rA), 그 결과 > rZ ? 그것 : rZ
close = clamp(1 - r + 0.0099, 0, 1)      // 상수 0x3C22339C = 0.0099
return [m, close]
```

- tol*는 질문 표(4.2)에서, range*·minF는 config(4.1: yaw 5°, pitch 1.5°, 줌 0.5, minF 0.5)에서 온다.
- **허용 오차 안이어도 근접도는 오차에 비례해 깎인다.** r = 오차/(허용+여유)이기 때문이다.
  - 예: Q4(tolA 10°)에서 yaw만 15° 어긋나면 r = 1 → close = 0.0099.
  - 예: pitch만 3° 어긋나면 close = 0.343 [재구현 계산].
- Ghidra 디컴파일은 반환을 float 하나로 보여주고 s1을 잃는다. **디스어셈블리 기준으로 옮길 것.**

### 6.5 NPC 점수 `Camera::CalcQuestionNpcScore @0x710001dcf0` + `CalcSubScoreByMapObject @0x710001e310` [판독]

```ts
// question = QuestionMgr 문제 NPC 목록, photo = 이 카메라 사진 속 NPC 목록 (4.5)
if (!photo.some(p => p.isMain)) return 0                       // 주인공이 안 찍히면 0
main = photo 의 첫 isMain 항목;  [mx, my, mz] = 투영(main.npc.GetCaptureBasePosition())
if (투영 w == 0) return 0
total = 0; matched = 0; pen = 0
for (p of photo) {
  q = question.find(q => q.index === p.index)
  if (q) {
    u = p.isMain ? Q.uniqueSuccessPercent : 1
    s = u * Σk clamp01(1 - |rate_q[k] - rate_p[k]|) * 0.25          // 네 변 거리 비율 비교
    if (question.length > 1) s *= p.isMain ? wMain : (1 - wMain) / (question.length - 1)
    total += s; matched++
  } else {                                                          // 문제에 없던 NPC
    t = dMax == dMin ? 0 : (hypot(mx - p.sx, my - p.sy) - dMin) / (dMax - dMin);  t = clamp(t, 0, 1)
    [A, B] = mz <= p.sz ? [I3, I4] : [I5, I6]                       // 주인공보다 뒤 / 앞
    pen = min(pen, trunc(A + (1 - t) * (B - A)))
  }
}
base = clamp(trunc(maxScore * total + 0.99), 0, maxScore)
diff = question.length !== photo.length ? question.length - photo.length : question.length - matched
if (diff < 0) pen -= I2 * diff;  else if (diff > 0) pen += I1 * diff
npcScore = clamp(base + pen, 0, maxScore)

// 장식물(맵 기믹 4~7 중 사진에 든 것): x 거리만, 주인공보다 뒤면 0
sub = 0
for (o of mapObjects) {
  [A, B] = mz <= o.sz ? [0, 0] : [I5, I6]
  t = dMax == dMin ? (B - A) + A : clamp((|mx - o.sx| - dMin) / (dMax - dMin), 0, 1)

```

- 기본 config에서 wMain = 1.0이다. 그래서 **문제 NPC가 여럿이어도 위치 유사도는 주인공 것만 점수가 된다.** 나머지는 수 차이 벌점(−10/−20)에만 영향을 준다 [판독 + 데이터].
- 낯선 NPC 벌점은 **가장 나쁜 하나만** 적용된다(min). 수 차이 벌점은 따로 더해진다.
- 정수 변환은 모두 0 쪽 절삭(`fcvtzs`)이다. `+0.99`는 올림에 가까운 반올림이다.
- `sub`의 t 계산(dMax==dMin일 때)은 원본 식 그대로다(정의상 쓰이지 않는 분기).

### 6.6 라운드 점수 `Player::CalcScore @0x7100056fb4` (= `UpdateCapture` 안 같은 식) [판독: 디스어셈블리]

### 6.8 CPU [판독 `ComControlConfig`, `ComFuncWait @0x7100057684`, `ComFuncRoughlyMove @0x7100057754`, `ComFuncDetailedMove0/1`]

```
ComControlConfig (라운드 시작, 질문 q, 레벨 L 의 11값 c[]):
  +0x290 = c5
  +0x294 = (c6..c7 사이 SyncRandModF) × (c8 == 0 ? (SyncRandMod(100) < 50 ? -1 : 1) : c8)
  +0x298 = c9..c10 사이 SyncRandModF                  // 줌 목표 오차
  +0x29C = c0..c1 사이 SyncRandModF                   // 대기
  +0x2A0 = c2..c3 사이 SyncRandModF; 특정 순간 문제가 아니면 (c4 == 0 ? 50% 부호 반전 : ×c4)
  상태 = ComFuncWait, 다음 = ComFuncRoughlyMove
ComFuncWait:      +0x29C -= dt; 0 이하면 다음 상태로
ComFuncRoughlyMove:
  ComStickControl(+0x294) 로 문제 방향(+오프셋)으로 스틱
  줌이 baseZoom 보다 크면 줌 아웃, 아니면 줌 속도 초기화
  스틱이 0(도착) && 줌 = baseZoom → 대기 c0..c1 다시 추첨
     특정 순간 문제: +0x2A4 = (SyncRandModF(0.2) + 0.3) / 질문 id5 → DetailedMove1
     아니면 DetailedMove0
ComFuncDetailedMove0/1:
  ComStickControl(-+0x294) (반대 오프셋으로 되돌아오기), |(+0x298) - |Q.zoom - zoom|| > 0.06 이면 줌 버튼
  스틱 0 && 줌 맞음 && 아직 안 찍음:
    Move0: GetJustTimingRemainingTime() + (+0x2A0) <= 0 && 이 상태 0.3 s 이상 → 셔터(+0x2A8)
    Move1: |Q.uniqueSuccessTiming + (+0x2A0)| <= 0.1 이 +0x2A4 초 지속 → 셔터
```

- **[판독] `ComStickControl @0x7100057ab0`**: `dp=wrap180(wrap180(Q.pitch)−wrap180(cam.pitch))`, `dy=wrap180(wrap180(Q.yaw+offset)−wrap180(cam.yaw))`. 각 축은 `abs(diff)>0.1°`일 때 `−sign(diff)*min(abs(diff)/(axisSpeed*dt), c5)`를 쓴다. pitch는 F10=30, yaw는 F9=40을 쓰고, offset은 yaw에만 더한다. 0.1° 이하는 호출자가 0으로 초기화한 출력이 그대로 남는다. c5는 CPU 스틱 크기 상한이며 기존 미확정이 해소됐다.
- CPU는 근접도를 최대로 하려고 문제 yaw/pitch/zoom에 맞춘다. 오차는 c6~c10 범위만큼 남는다 [판독 + 추정].

### 6.9 특정 순간 문제(uniqueSuccessPercent) [판독, 일부]

일부 NPC가 매 프레임 `QuestionData+0x14/0x18`을 갱신한다.

| NPC | percent(+0x14) | timing(+0x18) |
|---|---|---|

## 8. 다른 기능과의 상호작용

- **방송 순서**: 0x2A(시작) → … → 0x2B(끝) → 0x2E(점수). 0x2B 뒤에도 `UpdateCapture`가 남아 있으면 그 프레임에 점수가 계산된다 [추정].
- **타이머 vs 전원 촬영**: 4명이 찍으면 남은 시간과 무관하게 9단계로 간다.
- **NPC 움직임과 점수**: 점수는 찍는 순간 NPC의 위치·방향·uniqueSuccessPercent로 정해진다. NPC 행동(산책·공중·줄넘기)과 그 난수가 결과에 직접 들어간다.
- **카메라 충돌**: `TestCollision2` → `MoveAim`은 회전과 줌을 모두 다시 저장한다(6.1). 근접도는 보정된 값, NPC 점수는 보정된 VP 투영에 의존하므로 충돌 생략을 점수 동등한 처리로 취급하지 않는다.

### 9.8 lib API·렌더러 연결과 수명주기 [웹 코드 확인 + 구현 계획]

근거는 `docs/engine/README.md`의 공용 엔진 구분과 `loader_manager.md` §11~14, 아래 실제 구현이다. **설계 초안보다 현재 메서드 시그니처를 따른다.**

1. **게임 진입**: `main.ts start` → `await def.load?.()` → `def.createLogic(setup)` → `def.createView({renderer,hud,audio,setup,pads}, new Assets(def.assetsDir))` → `await view.load(progress)`. `GameDef.load`는 메타와 본체를 분리하는 코드 import 단계이고 `GameView.load`는 자산·GPU 준비 단계다(`games/mg1801/index.ts`의 body 동적 import 참고).
2. **자산 요청**: `appAssets()`는 앱 공용 AssetManager(논리 키는 `web/assets/` 상대 소스 경로), `get<T>(key,kind,pri?,owner?)`/`want(key,kind,pri,owner?)`/`raise`/`lower`/`drop`/`peek`/`state`/`release(owner)` 및 묶음 API를 제공한다. P0=지금 막음, P1=곧 필요, P2=다음 화면, P3=유휴. kind는 gltf/texture/json/bytes/uiimage. 소유자는 판마다 고유하게 지정하고 종료 시 release한다. `release`는 refs 감소일 뿐 취소·즉시 GPU 해제가 아니며 `drop`도 받기 시작 전 큐에만 적용된다.
3. **캐시와 복제**: `gltfHandler` 결과·texture 원본은 공유 템플릿이다. 모델은 SkeletonUtils clone과 재질 복제, 텍스처는 clone 후 게임별 변경을 적용한다(`stage3d/stage.ts stageTemplate`, `createMpjHandlers`). 압축 모드의 glb 내 KTX2는 managedTextureLoader를 거치지만 src 모드는 GLTFLoader 기본 이미지 경로다. 기존 Assets의 disposeScene/Assets.dispose 패턴을 관리자 공유 자산에 무조건 적용하지 않는다(공유 geometry/texture 해제 가능).
4. **GPU 준비**: `new ScenePreparer({renderer:ctx.renderer.gl,scene,camera:()=>camera,scheduler:manager.scheduler,linear:()=>usesRenderTarget,...})`. `prepare(root,pri)` → PrepJob.promise, `raise(job,pri)`, `isPrepared`, `pending`, `stats`, `dispose`. 텍스처 initTexture → compileAsync → 메시 기본 32개씩 1×1 업로드 렌더 순서다. 준비 전 root를 숨기고 완료 뒤 게임 표시 규칙에 따라 보인다. 예약 layer31과 게임 layer를 겹치지 않게 한다.
5. **완료와 수명**: ScenePreparer의 오류 처리·dispose도 promise를 resolve한다. resolve만으로 준비 성공·뷰 생존을 판단하지 말고, 게임 뷰의 disposed/세대 플래그와 stats.errors를 확인한다. L2의 ST_READY/FlowPrefetch ready는 GPU 업로드 완료가 아니다. 최신 어댑터의 선택 인자 `uploads?: UploadRecord`는 같은 WebGLRenderer의 source version/data 기록을 공유한다(§14.3). 다른 렌더러의 기록을 같이 쓰면 안 된다.
6. **프레임과 사진**: 공용 루프는 `logic.step(pads, sound)` → `view.onStep(state,events)` → rAF `view.render(state)`. 점수·NPC 좌표·셔터/판정 타이머는 로직에서 계산한다. 셔터 후 1스텝의 판정 시점에 사진용 상태 스냅샷과 캡처 사건을 만들고, view가 그 사건의 시점으로 RT를 그린다. rAF가 몇 스텝을 한 번에 처리해도 마지막 상태로 과거 사진을 찍지 않도록 한다.
7. **분할 렌더링**: Renderer 공개 API는 `gl`, `render(scene,camera)`, `setPost(post|null)`, `resize`, `aspect`, `clear`다. 한 번의 render에 4분할 기능은 없다. 신규 mg0122 view의 패스로 `ctx.renderer.gl`의 viewport/scissor/RT를 사용하거나 PostRenderer를 설치할 수 있다. 네 카메라의 각 뷰 16:9를 유지하고 판정 좌표 ±960/±540는 화면 CSS 크기·DPR·분할 픽셀 크기와 분리한다. RT 캡처도 같은 gl을 쓴다. 각 패스의 target·viewport·scissor·autoClear 및 renderer 전역 설정은 저장 후 복원한다.
8. **종료/취소**: 입력 중지 → 미완료 캡처 정산/판정 대기 → 3라운드 합계·rank → 결과 연출 → logic.done/result. view.dispose에서 후처리 분리(`setPost(null)`), 캡처 RT·자기 material/geometry·애니/소리·리스너·GPU 준비기 정리, manager.release(owner). 페이지가 소유한 renderer.gl.dispose는 호출하지 않는다. 비동기 로딩이 끝나도 종료한 view에 다시 attach/show하지 않는다.

`shell/stage3d/Stage3D.create`의 최신 `StageCreateOptions`는 `canvas/assets/manifest/loader`와 **`gpu?: StageGpu`**, `floor?: PriorityFloor`를 받는다. `StageGpu={renderer,uploads}`를 넘기면 생성자는 기존 renderer를 빌리고 `ScenePreparer`에 uploads를 전달한다. dispose는 gpu 모드에서 렌더러·관리자 공유 geometry·관리자 텍스처를 남기고 자기 재질·RT·스켈레톤 등을 정리한다. gpu가 없으면 새 렌더러를 만들고 종료 시 버린다. 따라서 mg0122는 신규 view에서 `ctx.renderer.gl`과 같은 렌더러 전용 UploadRecord를 넘기거나 ScenePreparer를 직접 조합할 수 있으며, **주입을 위해 stage.ts를 수정할 필요는 없다.** 생성 시 색공간·shadow·환경 clearColor 등의 공용 gl 설정을 바꾸므로 view 경계에서 설정도 관리한다.

**최종 대조 중 추가된 광장 연결**: `view/plazaGl.ts`의 `PlazaGl`은 광장 렌더러/캔버스를 앱 수명으로 유지한다. `installPlazaGl`이 FlowPrefetch ready(plaza:p0)를 구독해 `prewarm`을 시작하고, `enter`가 world를 인계·promote한 뒤 `plaza_page.ts`에 붙이며 `leave`가 프로그램 유지 및 부품 정리 뒤 캔버스를 뗀다. `PriorityFloor(P2)`는 앞 화면의 GPU/자산 준비가 P0를 앞지르지 않도록 요청을 낮추고, 진입 시 바닥을 P0로 내려 원래 우선순위로 올린다. FramePacer는 미리 조립할 때 프레임마다 하나씩 허용한다. uploads는 같은 광장 gl 안에서 공유된다. 예산 초과/문맥 손실은 drop→다음 진입 재생성 경로다. 이는 **광장에 연결된 코드 확인**이며 mg0122 연결·브라우저 효과 검증 또는 앱 전체 단일 renderer 완료를 뜻하지 않는다(`loader_manager.md` §14.2~14.6).

### 9.9 상태·입력·판정·종료에서 구현할 계약 [계획]

9.2의 state 초안은 완성 계약이 아니다. 다음을 명시해야 한다.

- phase(loading 외의 opening/prepareQuestion/roundIntro/playing/captureWait/score/ending/result), native stage, stageElapsed, roundElapsed, 플레이 제한 remaining, 원본 round(1~3)와 배열 roundIndex(0~2)를 분리한다. roundElapsed는 CPU JustTiming 기준이고 30초 표시 타이머와 동일 변수로 단정하지 않는다.
- 질문 ID 3개·사용 기믹/배치번호·클램프 전 정답 pose·실제 문제 촬영 pose·문제 NPC 스냅샷을 보관한다. 플레이 카메라 및 충돌 후 pose/VP도 상태에 둔다. NPC identity는 목록 인덱스이며 캐릭터 종 ID가 아니다.
- 플레이어마다 inputEnabled/captured/checking/capturePending, capturedFrame/판정Frame, zoomSpeed/지난 방향, roundScore/totalScore/rank를 보관한다. 전체 capturedMask/count는 라운드 시작에 초기화하고 셔터 1회만 카운트한다.
- CPU별 단계·대기·오프셋·줌 오차·타이밍·셔터 플래그와 동기 난수 호출 순서를 보관한다. 레벨 0~3은 현재 GameSetup.players[].comLevel을 받는다. mg1801의 “CPU 강도 미사용” 규칙을 옮기지 않는다.
- 입력은 Pads.read의 상승 에지 A(키 J), 스틱(lx/ly를 STICK_MAX로 정규화), X/Y(키 U/I)를 우선 연결한다. Joy-Con style의 원본 변환은 `../analysis/decomp/mgB_main_pad.c`의 `GetHold @0x710001e54c` → `FUN_710001e5cc`, `GetStick @0x710001eac4`에 있고 비트·축 회전과 마스크를 적용한다. **원본 hold 0x100 등의 의미를 NPAD.ZL 등으로 직결하지 않는다.** ZR/ZL 대체 조합·실제 글리프 대응과 데드존/스타일 조건은 아직 미확정이다.
- 플레이어 갱신 안에서는 카메라 이동→셔터, StartCapture→다음 스텝 점수/캡처→0.3초 checking 해제 순서를 보존한다. NPC 갱신과 Question unique 갱신·플레이어·GameMgr의 전체 같은 프레임 순서는 mg0122의 fiber 등록/가상 함수까지 검증할 필요가 있다. mg1801의 실행 순서를 그대로 가정하지 않는다.
- 시간 종료에서 미촬영자는 0점, 입력은 비활성, 네 사람이 모두 찍으면 즉시 playing을 종료하되 pending 판정은 끝낸다. 그 뒤 최소 1초와 checking 없음→ScoreIn→점수 발표 완료 후 2초→다음 문제/종료 순서다.
- 순위는 0 기반 경쟁 순위(예: 100/100/90/80이면 0/0/2/3), 전원 0점은 rank3·패배, 전원 같은 양수면 rank0·승리다. 현재 `main.ts playFromList`는 `describeResult().rows`의 rank0을 승리 1로 전달한다. 모든 종료 경로에서 quit/ranks/frames/result 및 rows를 채워야 한다.
- 화면 렌더의 성공/실패 또는 fps가 점수를 바꾸지 않게 한다. 원본 화면 캡처는 표시용이며 점수는 pose·NPC 구성·투영·unique 값의 수학 계산이다.

**기존 파일 수정이 필요한 최소 연결**: `script/games/index.ts`의 GAMES에 mg0122Game을 import·추가해야 일반 페이지와 mgm01 목록에서 실행된다. 현재 자동 디렉터리 검색/런타임 플러그인 등록은 없다. **신규 게임 파일만 만들면 기존 앱에 자동 연결된다는 계획은 성립하지 않는다.** 별도 신규 페이지 엔트리로 격리 실행하는 대안은 가능하지만 기존 메뉴 연결 완료가 아니다.

**조건부 추가 연결**: 전체 게임 자산까지 앞 화면에서 예측하려면 `script/view/flowCatalog.ts`의 game 분기(manifest 한 개) 확장 또는 신규 게임 측의 명시적 묶음 등록이 필요하다. Stage3D의 공용 gl 주입·소유권 구분은 최신 `gpu: StageGpu` API로 이미 지원된다. 신규 mg0122 view가 이를 이용할 수 있으므로 그 목적의 stage.ts 수정은 필요 없다. 앱 전체 한 렌더러 요구는 `view/renderer.ts`, main과 각 `*_page.ts`/Preview3D/2D 레이아웃의 생성·정리 경계도 검토해야 한다. 이는 mg0122만의 점수 포팅과 별도 공용 작업이다. **이번 수정은 이 문서 한 파일에만 한정한다.**
