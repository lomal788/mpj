# mg0122 다 함께 찰칵 (Camera-Ready / みんなでパシャリ)

확정 수준 표기: **[실행]** 원본 실행 확인, **[판독]** 원본 코드 판독, **[데이터]** 데이터 확인, **[추정]**, **[미확정]**. 이 문서에 [실행]은 없다. 재구현 계산은 "재구현 계산"이라고 따로 적는다.

## 1. 기능 개요

4인 VS4, 3라운드×30초, 라운드당 셔터1회. 문제 사진의 카메라 구도와 NPC 구성/위치를 재현해 0~100점을 얻고 합계로 순위를 정한다. 조작은6.10, 점수 가중치는6.6.

| [데이터] `im_mg_inst.json` | "제시된 사진과 최대한 비슷하게 사진을 찍으세요. 3라운드 승부입니다." |
| [데이터] `mg_inst.json` | `inst_mg0122_ctrl00` " 카메라 움직이기", `ctrl01` "() 줌 인", `ctrl02` "() 줌 아웃", `ctrl03` " 사진 찍기" |

## 3. 진입점과 전체 호출 흐름

### 3.1 클래스 구성 [판독]

```
mg0122::Scene : bq::MinigameScene        SyncedSetupGameImpl → GameMgr 생성·Initialize
  GameMgr (singleton)   라운드 상태기계(+0xA0), 매니저 묶음, 옵서버 방송(ObserverBroadcast(id))
    GameParam      config.csv(I[]/F[]), 질문 영역·NPC 추첨·ViewVolume·CPU 표
    QuestionParam  question.csv 27×7
    NpcLotteryTable npc_lottery.csv
    QuestionMgr    라운드별 문제(질문 ID 3개), 문제 사진 촬영, JustTiming, 문제 NPC 목록(+600)
    MapMgr/MapData 맵 엔티티, 기믹(벤치·나무·노점·공중 등 29종) 배치
    NpcMgr         NPC 목록(GetNpcListData) — NpcBase 파생 50여 종
    CameraMgr      Camera×4 (플레이어별, 4분할)
    PlayerMgr      Player×4 (+ CPU), 촬영 비트(+0x1E8)·촬영 수(+0x1F4), 순위
    UIMgr          타이머·점수·문제 사진 표시
    EmitMgr        SE·진동·이펙트 묶음
BaseObject / BaseUpdateObject / GimmickObject : 공통 기반(엔티티, 모션, 타이머 TimeUpdate/IsFinishedTime, Notify)
```

`GameMgr::ObserverBroadcast(id)`는 등록된 모든 객체의 `Notify(id, value)`를 부른다. 라운드 단계가 바뀔 때 id를 방송한다(3.3).

### 3.2 장면 준비 [판독]

- `Scene::SyncedSetupGameImpl @0x710005bad8`이 장면 설정 객체를 만든다.
  - `+0x08` f32 = **30.0**(라운드 제한 시간), `+0x0C` int = **3**(라운드 수) [판독].
  - 이어서 `GameMgr` 생성 → `GameMgr::Initialize`.
- `GameParam::Initialize @0x7100052314`
  - `SetupParam`(config.csv)
  - `+0x50 = (SyncRandMod(100) < 51)`.
  - `+0x54`: r = SyncRandMod(100)을 I[24], I[25], I[26](33, 33, 34) 누적과 비교해 20 / 21 / 22 / −1을 고른다.
  - 디컴파일의 오프셋 0x60/0x64/0x68 = I 배열 24~26번이다 [판독 + 데이터].
  - `SetupAir`, `SetupFreeArea`, `SetupViewVolume`, `SetupCom`.
  - 배치/RNG 상세는5.6.
- `QuestionMgr::InitializeQuestion1 @0x710005a500`: 라운드 0,1,2 문제를 정한다(6.1).
- `CameraMgr::Initialize @0x710001fea0`
  - `Camera(1,0)`, `(2,1)`, `(4,2)`, `(8,3)` 4개를 만든다(레이어 비트, 플레이어 번호).
  - 첫 문제 기믹 방향 + 180°를 첫 라운드 시작 yaw로 저장한다(`+0x200`).
- `Camera::PrepareGame @0x710001a564`
  - 기준점 `base(+0x390) = (0, 카메라 y, 0)`, `baseZoom(+0x3B8) = |카메라 위치의 xz|`, 줌 = baseZoom.
  - 시작 회전 = `CalcViewAngle(전방)`.
  - `mg0122_cam_game.fsnb` 값 pos (0, 2.56, −0.72), aim (0, 2.47, −1.25) → 기준 (0, 2.56, 0), baseZoom 0.72 [데이터 + 추정].

### 3.3 라운드 상태기계 `GameMgr::UpdateGameMainSequence @0x7100027720` [판독]

`GameMgr+0xAC` = 라운드 경과 시간(매 프레임 += dt, 방송 0x2C에서 0). `+0xA8` = 단계 내 타이머.

| 단계(+0xA0) | 동작 | 다음 | 방송 |
|---|---|---|---|
| 1 (방송 0x14로 진입) | 0.1 s 대기 → 라운드 텔롭 | 6 | 0x25 |
| 2 | 페이드아웃 끝 대기 | 3 | 0x26 |
| 3 | 0.1 s → 4개 레이어 갱신 | 4 | 0x27 |
| 4 | 0.2 s 이상 + 문제 촬영 끝 → 페이드인 | 5 | 0x28 |
| 5 | 페이드 끝 → 라운드 텔롭 | 6 | — |
| 6 | 텔롭 끝 (첫 라운드면 0x2C 먼저) | 7 | 0x29 |
| 7 | 시작 연출 끝 → 휘슬 | 8 | **0x2A (조작 시작)** |
| 8 | 타이머 끝 **또는 4명 모두 촬영**(`PlayerMgr+0x1F4 > 3`) | 9 | 0x2B (조작 끝) |
| 9 | 1.0 s + 판정 중인 플레이어 없음 | 10 | — |
| 10 | `PlayerMgr::ScoreIn` | 11 | 0x2E |
| 11 | 점수 발표 완료를 기다린 뒤 2.0 s → `ScoreOut`, `QuestionMgr::NextRound`(이전 round > 2면 끝) | 12(끝) 또는 2 + 페이드아웃 | — |

- 타이머는 `UIMgr::RoundStart @0x710005f500`에서 `ComUiTimer::SetTimer(장면설정+0x08 = 30.0)`로 건다 [판독].
- **원본 round는 1~3, 질문 배열 인덱스는 0~2**다. `GameMgr::SetUpGame @0x7100025f90`의 QuestionMgr 초기화는 `+0x1E0=-1, +0x1E4=1`; `QuestionMgr::Notify`는 `round-1`로 배열을 읽는다. `NextRound @0x710005ad08`은 이전 값 > 2를 반환한 뒤 round를 1 증가시킨다(3→4에서 종료). 웹에서 0 기반 round를 쓰면 이 변환을 명시한다.

### 3.4 플레이어 한 라운드 [판독 `Player::Notify @0x7100055c8c`]

- 방송 0x2A
  - `captured(+0x221) = 0`, `roundScore(+0x22C) = 0`, `ComControlConfig()`(CPU 값 추첨), `inputEnabled(+0x220) = 1`.
  - 매 프레임 함수를 `PhoneControl`로 둔다.
- `PhoneControl @0x7100056204` (매 프레임):
  1. 사람이면 패드 → 회전 속도·줌 속도(6.1)를 구한다. CPU면 CPU 함수(`+0x2D0`)가 같은 값을 만든다.
  2. `Camera::CameraMove2(zoomRate, rotRate)`
  3. 셔터
     - 사람: `ComActorPad::GetTrigger() & 1`
     - CPU: `+0x2A8`
     - 셔터가 눌리면 `StartCapture`.
- `StartCapture @0x7100056c30`
  - 방송 0x2D, `ForceCalculateView`, `captured = 1`.
  - `PlayerMgr+0x1E8 |= 1<<idx`, `PlayerMgr+0x1F4++`, 보이스 `SQ_VOI_PC%02d_ETC`.
  - 다음 프레임 함수를 `UpdateCapture`로 둔다.
- `UpdateCapture @0x7100056d30`
  - 1프레임(`GetTimePerFrame`) 뒤 점수를 계산한다(6.6, `CalcScore`와 같은 식).
  - `Camera::GameCapture`(화면 캡처) → `QuestionCheck`.
- `QuestionCheck`: 0.3 s 뒤 판정 중 플래그 해제, 그래픽 레이어 갱신.
- 방송 0x2B: `inputEnabled = 0`. 찍지 않았으면 파인더 숨김.
- 방송 0x2E: 안 찍은 사람 화면 검게.
- 방송 0x34+idx
  - 점수 보이스: ≤ 0 `SAD`, 1~30 `ENVY`, 31~90 `JOY_MID`, > 90 `JOY_HIGH`(`SQ_VOI_PC%02d_*`).

**한 라운드에 한 번만 찍는다**: `StartCapture` 뒤 `PhoneControl`이 다시 걸리지 않는다. 0x2A 방송은 라운드 시작 때만 온다 [판독 + 추정].

### 3.5 프레임 실행 순서 [판독]

main 0x0E에서 SceneModule→FiberModule 순서다. BaseUpdateObject::Update @0x71000061b0: enable인 동안 가상 Run(+0x28) → Fiber::Wait 반복. Camera secondary Fiber vtable은 thunk @0x7100006200을 거쳐 이 함수로 간다. GameMgr 자체는 Fiber를 만들지 않는다.

SetUpGame @0x7100025f90의 fiber 생성 및 manager Initialize/PostInitialize 리스트는 **MapMgr → QuestionMgr → CameraMgr → PlayerMgr → UIMgr → EmitMgr → NpcMgr → GimmickMgr**다. priority는 모두0. manager 전부를 먼저 생성하고 Initialize 한 패스, PostInitialize 다음 패스다. CameraMgr Initialize에서 Camera0~3, PlayerMgr Initialize에서 Player0~3 fiber를 추가한다. NPC별 fiber 없이 NpcMgr::Run @0x710004fd00이 목록 순서로 NPC Run을 호출한다.

| 상대 순서 | 실행 내용 |
|---|---|
| MapMgr → QuestionMgr | 맵·질문 콜백; 질문 촬영 대기/완료 포함 |
| CameraMgr → PlayerMgr → UIMgr → EmitMgr | CameraMgr/EmitMgr Run은 빈 함수. PlayerMgr는 BaseObject 콜백, UIMgr는 콜백 뒤 점수 UI |
| NpcMgr → GimmickMgr | NPC 목록의 콜백·행동·unique·시야/회피 후 기믹 목록 Run |
| Camera0→1→2→3 | BaseObject::Run의 +0xF0/+0x150 콜백. Camera Run이 빈 함수라는 해석은 잘못 |
| Player0→1→2→3 | 카메라 이동→셔터, pending capture 판정 등 |
| 공용 오류 감시 → 장면 흐름 | 정상 흐름에서 아래 main 근거로 연결 |

main Fiber @0x710018c9b0 등록, FUN_710018f400 pending 처리, FUN_710018f740 priority 안정 정렬을 대조했다. 같은 priority는 등록 순서다. Scene::SyncedSetupGameImpl @0x710005bad8에서 manager들을 만든 뒤 main SceneBase::UpdateMain이 흐름 FiberLite(priority0)를 생성한다. Scene::OnGameMainImpl @0x710005bc68은 GameMgr::UpdateGameMainSequence를 호출한다. **NPC/기믹 → 카메라 콜백 → 플레이어 → GameMgr 종료 판단**순서다.

공용 추가 fiber 생성 main @0x71002d16fc의 이름은 **FiberWatchNetError**다. vtable Update @0x71002d1b20 정상 경로는 Sleep(.25)→Net::IsLeftError 검사이며 오류 시 pause/UI를 처리한다.

CoreSystem @0x7100984460은0x0D→0x0E→0x0F(설정된 서브스텝 횟수)→0x10…0x19→0x1B, 다음 프레임 스텝 계산 순서다. 등록 @0x7100984a20, 의존 @0x7100984a58(t,A,B)는 **B→A**. Kahn @0x71009891a0의 무진입 노드 임시 vector는 **끝에서 꺼내는 LIFO**여서 동률을 FIFO나 Fiber의 안정 정렬과 같다고 취급하지 않는다.

0x0E의 판독 간선: Scene(token0x7101C0E508)→Fiber(0x7101C0B438)→Entity(0x7101C436F8)→PhysicalAnimation(0x7101C31930) 및 Model(0x7101C3FD10). Model은 Graphic(0x7101C421B8)·token0x7101C41EA8 뒤에도 놓인다. **Model의0x0E 처리기 @0x71006bda60은 ret**이고 실제 다른 처리는0x15 @0x71006bda68,0x16 @0x71006bda80,0x18 @0x71006bdac0이다. 물리는0x0F Entity→Physics(@0x7100614624),0x10 Physics→Entity. Graphic은0x11 @0x710084d620·0x17 @0x710084d660·0x18 @0x710084d674. 따라서 Model의0x0E를 뼈 갱신 완료로 해석하지 않는다.

그 밖0x0E 처리기/token(주소는 main): @0x7100004ef0/0x7101BFBEA0, @0x710013bee0/0x7101C0A888, @0x71001cc85c/0x7101C100C8, @0x7100226eb4/0x7101C152A0, @0x71002c86ac/0x7101C20D78, Movie @0x710078cc0c/0x7101C41010, Font @0x7100807820/0x7101C41C18. @0x710013b9a4는token0x7101C34690→0x7101C0A888 간선을 추가한다. 이 목록은 정적 등록 지점이며 활성 모듈/등록 vector·부품 timing 선택이 없는 상태에서 독립 노드의 실행 총순서나 capture 시점의 뼈 pose를 확정하지 않는다.

### 5.2 문제 선택 [판독 `InitializeQuestion1`, `MapData::FindQuestionPatternGimmick @0x71000368b0`]

- 라운드 i(0~2)마다 `Qtbl[i]`의 질문들을 차례로 본다.
  - 그 질문 기믹 종류의 배치 후보(`MapData+0x238 + 종류·0x18` 목록)를 모은다.
  - 아직 문제로 안 쓴(+0x20 == −1) 것만 넣는다.
  - 두 번째 이후 라운드는 이전 문제 방향과 `CheckPlacement`(배치 각도)가 맞는 것만 넣는다.
- 후보 중 `SyncRandMod(후보 수)`로 하나 고른다(`@0x7100036ad8`). 그 기믹의 질문 ID를 저장하고 +0x24 = 라운드 번호+1로 표시한다.
- **[판독] `CheckPlacement @0x7100036b50`**: 일반 기믹은 이전 문제 방향과 `+0x30` 방향의 `abs(wrap180(diff)) >= 100°`일 때 허용한다. Walk(20~22)는 `GetPlacementPromenadeNumber`의 `n*90°`, Run(23)은 `wrap180(baseAngle + wrap180(n/−3*360°))` 후보 중 조건을 만족하면서 각도 차가 가장 큰 n을 고른다(동률은 먼저 본 후보 유지). 반환 하위 32비트는 허용 여부, 상위 32비트는 선택 n(일반 기믹은 −1).
- **[판독 + 디스어셈블리] `GetQuestionPlacementDeg @0x7100037040`**: Walk는 저장 n(`+0x28`)*90°를 wrap, Run은 baseAngle(`+0x30`)+wrap(n/−3*360°)를 wrap, 나머지는 `+0x30`을 반환한다. 디컴파일이 float 반환을 void로 표시하지만 `mgE_mg0122_dis.txt @0x7100037118`의 `ldr s0,[x1,#0x30]`로 확인된다.
- 각도 규칙은 확인됐으나 산책·달리기 후보 번호 목록의 생성·갱신과 NPC 실제 배치의 전체 난수 순서는 **[미확정]**.

### 5.3 문제 사진 [판독 `QuestionMgr::QuestionCapture @0x710005a810`]

```ts
B = camera0.base;  d = targetPos - B;             // targetPos = 문제 NPC의 GetQuestionPosition
yaw   = wrap180(atan2(dx / |dxz|, dz / |dxz|) * 57.29578)
v     = (0, -(p0 + dy), |dxz|)  (정규화)
pitch = atan2(v.y, v.z) * 57.29578                 // 양수 = 내려다봄
zoom  = sqrt(dx² + (p0 + dy)² + dz²) - p1          // 조준점까지 p1 만큼 남기고 전진
Q.angle = yaw; Q.height = pitch; Q.zoom = zoom; Q.uniqueSuccessPercent = 1.0
camera0.SetCameraDirection(yaw, pitch, zoom)       // 회전 클램프·줌 클램프 적용
1 프레임 뒤: Q.npcs = AddCameraInSightNpcData(camera0); camera0.QuestionCapture()(문제 화면 저장)
```

- p0, p1 = question.csv id0, id1.
- `atan2` 인자 순서와 정규화는 디컴파일(`fVar39`, `fVar20`)에서 읽었다. 0 나누기 보호(벡터 0이면 성분 0)가 있다 [판독].
- **문제의 줌·각도는 클램프된다.** 문제 값이 pitch 범위(−15.3~17.7)나 줌 범위(0.72~17)를 넘으면 문제 사진은 클램프된 구도다. 그러나 `Q.*`는 클램프 전 값이 저장된다(SetCameraDirection 전에 저장) [판독]. 원본 그대로 둔다.

### 5.4 JustTiming [판독 `QuestionMgr::Notify @0x710005a6cc`, 디스어셈블리]

방송 0x26 또는 0x0D를 받으면 다음을 한다.

### 6.4 카메라 근접도 `Player::CalcCameraScore @0x71000570e0` [판독: 디스어셈블리, 반환 s0·s1 두 값]

```ts
dh = |Q.height - cam.pitch|
da = |wrap180(Q.angle - cam.yaw)|
dz = |Q.zoom   - cam.zoom|
// s0: 벌점 배율 (CalcScore 에서 쓰지 않음)
m = 1
if (dh - tolH > 0) m = min(1, (minF - 1) * min((dh - tolH) / rangeH, 1) + 1)
if (da - tolA > 0) m = min(m, (minF - 1) * min((da - tolA) / rangeA, 1) + 1)
if (dz - tolZ > 0) m = min(m, (minF - 1) * min((dz - tolZ) / rangeZ, 1) + 1)
// s1: 근접도
rH = max(dh / (tolH + rangeH), 0); rA = da / (tolA + rangeA); rZ = dz / (tolZ + rangeZ)
r  = max(rH, rA, rZ)                     // fcsel gt 순서: (rH > rA ? rH : rA), 그 결과 > rZ ? 그것 : rZ
close = clamp(1 - r + 0.0099, 0, 1)      // 상수 0x3C22339C = 0.0099
return [m, close]
```

- tol*는 질문 표(4.2)에서, range*·minF는 config(4.1: yaw 5°, pitch 1.5°, 줌 0.5, minF 0.5)에서 온다.
- **허용 오차 안이어도 근접도는 오차에 비례해 깎인다.** r = 오차/(허용+여유)이기 때문이다.
  - 예: Q4(tolA 10°)에서 yaw만 15° 어긋나면 r = 1 → close = 0.0099.
  - 예: pitch만 3° 어긋나면 close = 0.343 [재구현 계산].
- Ghidra 디컴파일은 반환을 float 하나로 보여주고 s1을 잃는다. **디스어셈블리 기준으로 옮길 것.**

```ts
    s = u * Σk clamp01(1 - |rate_q[k] - rate_p[k]|) * 0.25          // 네 변 거리 비율 비교
    if (question.length > 1) s *= p.isMain ? wMain : (1 - wMain) / (question.length - 1)
    total += s; matched++
  } else {                                                          // 문제에 없던 NPC
    t = dMax == dMin ? 0 : (hypot(mx - p.sx, my - p.sy) - dMin) / (dMax - dMin);  t = clamp(t, 0, 1)
    [A, B] = mz <= p.sz ? [I3, I4] : [I5, I6]                       // 주인공보다 뒤 / 앞
    pen = min(pen, trunc(A + (1 - t) * (B - A)))
  }
}
base = clamp(trunc(maxScore * total + 0.99), 0, maxScore)
diff = question.length !== photo.length ? question.length - photo.length : question.length - matched
if (diff < 0) pen -= I2 * diff;  else if (diff > 0) pen += I1 * diff
npcScore = clamp(base + pen, 0, maxScore)

// 장식물(맵 기믹 4~7 중 사진에 든 것): x 거리만, 주인공보다 뒤면 0
sub = 0
for (o of mapObjects) {
  [A, B] = mz <= o.sz ? [0, 0] : [I5, I6]
  t = dMax == dMin ? (B - A) + A : clamp((|mx - o.sx| - dMin) / (dMax - dMin), 0, 1)
  sub = min(sub, trunc(A + (1 - t) * (B - A)))
}
percent = photo.length ? max(0, npcScore + sub) : 0             // GetQuestionSuccessPercent @0x710001dc90
```

- 기본 config에서 wMain = 1.0이다. 그래서 **문제 NPC가 여럿이어도 위치 유사도는 주인공 것만 점수가 된다.** 나머지는 수 차이 벌점(−10/−20)에만 영향을 준다 [판독 + 데이터].
- 낯선 NPC 벌점은 **가장 나쁜 하나만** 적용된다(min). 수 차이 벌점은 따로 더해진다.
- 정수 변환은 모두 0 쪽 절삭(`fcvtzs`)이다. `+0.99`는 올림에 가까운 반올림이다.
- `sub`의 t 계산(dMax==dMin일 때)은 원본 식 그대로다(정의상 쓰이지 않는 분기).

재구현 계산(Q 2명: 주인공 (0,0,z .95), 다른 NPC (300,−50,z .96)) [`analysis/mgE_mg0122_calc.json`]:

### 6.6 라운드 점수 `Player::CalcScore @0x7100056fb4` (= `UpdateCapture` 안 같은 식) [판독: 디스어셈블리]

- f32 순서: `fmul s3 = w*close; s0 = s3*100.0 → fcvtzs`, `(1-w)*float(percent) → fcvtzs`, 정수 합.

### 6.8 CPU [판독 `ComControlConfig`, `ComFuncWait @0x7100057684`, `ComFuncRoughlyMove @0x7100057754`, `ComFuncDetailedMove0/1`]

```
ComControlConfig (라운드 시작, 질문 q, 레벨 L 의 11값 c[]):
  +0x290 = c5
  +0x294 = (c6..c7 사이 SyncRandModF) × (c8 == 0 ? (SyncRandMod(100) < 50 ? -1 : 1) : c8)
  +0x298 = c9..c10 사이 SyncRandModF                  // 줌 목표 오차
  +0x29C = c0..c1 사이 SyncRandModF                   // 대기
  +0x2A0 = c2..c3 사이 SyncRandModF; 특정 순간 문제가 아니면 (c4 == 0 ? 50% 부호 반전 : ×c4)
  상태 = ComFuncWait, 다음 = ComFuncRoughlyMove
ComFuncWait:      +0x29C -= dt; 0 이하면 다음 상태로
ComFuncRoughlyMove:
  ComStickControl(+0x294) 로 문제 방향(+오프셋)으로 스틱
  줌이 baseZoom 보다 크면 줌 아웃, 아니면 줌 속도 초기화
  스틱이 0(도착) && 줌 = baseZoom → 대기 c0..c1 다시 추첨
     특정 순간 문제: +0x2A4 = (SyncRandModF(0.2) + 0.3) / 질문 id5 → DetailedMove1
     아니면 DetailedMove0
ComFuncDetailedMove0/1:
  ComStickControl(-+0x294) (반대 오프셋으로 되돌아오기), |(+0x298) - |Q.zoom - zoom|| > 0.06 이면 줌 버튼
  스틱 0 && 줌 맞음 && 아직 안 찍음:
    Move0: GetJustTimingRemainingTime() + (+0x2A0) <= 0 && 이 상태 0.3 s 이상 → 셔터(+0x2A8)
    Move1: |Q.uniqueSuccessTiming + (+0x2A0)| <= 0.1 이 +0x2A4 초 지속 → 셔터
```

- **[판독] `ComStickControl @0x7100057ab0`**: `dp=wrap180(wrap180(Q.pitch)−wrap180(cam.pitch))`, `dy=wrap180(wrap180(Q.yaw+offset)−wrap180(cam.yaw))`. 각 축은 `abs(diff)>0.1°`일 때 `−sign(diff)*min(abs(diff)/(axisSpeed*dt), c5)`를 쓴다. pitch는 F10=30, yaw는 F9=40을 쓰고, offset은 yaw에만 더한다. 0.1° 이하는 호출자가 0으로 초기화한 출력이 그대로 남는다. c5는 CPU 스틱 크기 상한이다.
- CPU는 근접도를 최대로 하려고 문제 yaw/pitch/zoom에 맞춘다. 오차는 c6~c10 범위만큼 남는다 [판독 + 추정].

### 6.9 NPC 고유 성공·행동 [판독]

가상 +0x370은 아래 다섯 구현과 base no-op. F7=.5를 TreeBase::ActionConfig @0x710003b0b0/Wanwan @0x710003bdcc→+0x394, BenchReadBook @0x71000499dc→+0x390에 저장한다.

|---|---|---|
| TreeBase @0x710003bc40 | a=abs(wrap(angle(+0x320)−orbitAngle(+0x38C))); a≥90이면 base(+0x394), 아니면 base+(1−a/90)*(1−base) | 방향 검사 true면1, 아니면1−percent |

NpcBase::ActionUpdate @0x710000b05c: questionID≠−1이고 현재 round 대상일 때 unique 갱신 → 카메라0~3 시야 → 카메라0~3 회피/불투명도 → dirty bit 제거. **TreeBase::ActionUpdate @0x710003b760과 BenchReadBook::ActionUpdate @0x7100049f58는 base를 먼저 호출**한다. 이후 각도/위치가 움직이므로 unique가 행동 갱신 전 상태를 반영할 수 있다.

- 나무는 freeze bit가 꺼져 있을 때 orbitAngle += dt*speed(+0x318), wrap180한 뒤 궤도 위치/회전을 갱신한다.
- ActionBenchReadBook @0x7100049f7c는 TimeUpdate 후 목표 대기가 끝나면 angle += dt*speed한다. **<0 또는 >90으로 넘어갔을 때만** 끝점으로 clamp하고 speed를 반전, 시간 초기화·RandomData+0x34 대기를 설정한다. 경계와 같을 때 즉시 반전하지 않는다. 애니 블렌드는 cos(angle·rad)를 사용한다.

### 6.10 입력 어댑터 [판독]

S=InputModule controller style, A=ComActorPad+0x30, M=monitor가 반환한 GameController+0x10. **M=2 FullKey,3 Handheld,4 JoyDual,5 JoyLeft,6 JoyRight**다(main style 분기 @0x71007dde50→setter @0x71007da7dc). backend NpadState+0x10의0/1은 별도 방향 설정이므로 M과 혼동하지 않는다. S=3의 정책 분기는 main @0x71007e685c의0~4 switch로 확인되며 인간용 enum 이름은 확보하지 못했다. 표는 입력 bit→출력 bit다.

| 조건 | face 입력 bit0,1,2,3 | dpad 입력 bit8,9,10,11 | stick 입력 bit16,17,18,19 | 축 |
|---|---|---|---|---|
| (S==3,A==1,M≠5) 또는 (S≠3,A==2,M==5) | 1,3,0,2 | 11,10,8,9 | 17,18,19,16 | (x,y)→(y,−x) |
| (S==3,A==1,M==5) 또는 (S≠3,A==2,M≠5) | 2,0,3,1 | 10,11,9,8 | 19,16,17,18 | (x,y)→(−y,x) |
| 그 밖 | 그대로 | 그대로 | 그대로 | 그대로 |

GetHold(main @0x710001e54c)→FUN_710001e5cc. 다른 bit는 유지하고 +0x34/+0x38 mask를 AND한다. disable(+0x28==0)면0, override(+0x29)면 +0x40/+0x3C를 쓰고 일반 변환을 건너뛴다. main GetTrigger @0x710001e74c도 일반 경로에서 이미 계산된 edge에 동일 변환 함수를 적용한다. 근거는 mgB_main_pad.c와 main 바이너리다.

GetStick @0x710001eac4는 회전 후 크기가 +0x50 문턱 미만이면 zero, 경계 이상이면 그대로다. 재정규화하지 않는다. ComActorPad 생성 @0x710001e0b4는 문턱 **f32 .1(0x3DCCCCCD)**, A=0, enabled=1/override=0, mask=FFFFFFFF로 초기화한다. 확보한 mg0122 NRO에는 이 문턱을 변경하는 직접 호출이 없다.

HID NPAD→bex는 main @0x71007e4e70: FullKey/Handheld/JoyDual의 raw bit0~3→0~3,4/5→14/15,6/7/8/9→4/5/6/7,10/11→12/13,12/13/14/15→8/11/9/10. JoyDual만24~27→26~29도 옮긴다. 좌우 아날로그는 int/32767, 이 단계에서 radial deadzone 없이 저장한다. JoyRight @0x71007e5250은 방향0이면 face0~3 유지, 방향1이면1/3/0/2; raw5→14,26/27→4/5,7/9→24/25,10→12. JoyLeft @0x71007e53c8은 방향0에서 raw12/13/14/15→3/2/0/1, 방향1에서1/3/2/0; raw4→14,24/25→4/5,6/8→24/25,11→13. 방향1 스틱은 (y,−x), 방향0은(x,y); Right는 raw right-stick, Left는 left-stick을 논리 left-stick에 넣는다.

HID 방향 비트 생성 @0x71007deb2c의 기본 문턱은 **.5**(설정 @0x71007e4e20). 일반 모드는 x≤−.5/y≥.5/x≥.5/y≤−.5를 bit16/17/18/19, right는20/21/22/23으로 OR한다. 옵션 모드는 크기>.5일 때 atan2의 ±π/4·±3π/4 구간으로 한 방향만 선택한다. 이후 InputModule edge→위 actor 회전/마스크→PhoneControl이다. 버튼의 물리 글리프 이름은 웹 매핑과 별도다.

PhoneControl @0x7100056204의 줌은 변환 완료된 bex hold **+0xA4(bit2/5/7), −0x52(bit1/4/6)**이며 양쪽이면+가 우선이다. release&0xF6은 다른 줌 버튼이 눌려 있어도 가속을 초기화한다. shutter=trigger&0x01. 6.1의 pitch/yaw/dpad 부호도 이 함수로 대조했다.

현재 core/pad.ts·view/input.ts는 NPAD를 쓴다. J=A,K=B,U=X,I=Y,Q=L,E=R, Gamepad0=B/1=A/2=Y/3=X, y축은 위=양수다. axis는 반올림·clamp만 하고 radial deadzone은 없다. shell/mgmcommon/input.ts의 bex X=4/Y=8은 판독된 값이나 bit0x10~0x80의 L/R/ZL/ZR 이름은 여전히 추정이다.

**[계획]** 신규 mg0122 어댑터에서 NPAD→확인된 논리 동작을 연결하고 hold/down/up·스타일 회전·문턱을 명시한다. 기본 face 대응이면 **+줌=X(U), −줌=B(K)**다. Y(I)를−줌으로 연결할 근거는 없다. 실제 Joy-Con 재현은 enum/HID 변환 추가 확인이 필요하며 NPAD 숫자를 bex mask에 직접 넣지 않는다.

Stage3D.create({canvas,assets,manifest?,antialias?,loader?,gpu?,floor?}), StageGpu={renderer,uploads,keep:Map<string,unknown>}. gpu가 있으면 renderer를 빌리고 keep에 post/sky/IBL을 보관한다. dispose는 공유 geometry/관리 texture·renderer/keep을 남기고 준비 RT·스켈레톤·장면 재질을 정리한다. gpu가 없으면 renderer도 자체 생성/해제한다.

- PlazaGl은 광장 전용 앱 수명 gl/canvas. ready(plaza:p0)→prewarm, enter→world 인계/promote, leave→program usedTimes+1 유지·부품 정리·canvas 분리. PriorityFloor(P2)는 진입 시P0로 내리고 FramePacer는 조립을1개/frame으로 제한한다. KEEP_RATIO=.6, GPU 예산 PC2e9/mobile6e8 초과 또는 context loss면 drop→재생성. 전체 화면 renderer 통합은 아직 없다.
