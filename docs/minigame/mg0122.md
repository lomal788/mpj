## 3. 진입점과 전체 호출 흐름

### 3.1 클래스 구성 [판독]


### 3.2 장면 준비 [판독]

- `Scene::SyncedSetupGameImpl @0x710005bad8`이 장면 설정 객체를 만든다.
  - `+0x08` f32 = **30.0**(라운드 제한 시간), `+0x0C` int = **3**(라운드 수) [판독].
  - 이어서 `GameMgr` 생성 → `GameMgr::Initialize`.
- `GameParam::Initialize @0x7100052314`
  - `SetupParam`(config.csv)
  - `+0x50 = (SyncRandMod(100) < 51)`.
  - `+0x54`: r = SyncRandMod(100)을 I[24], I[25], I[26](33, 33, 34) 누적과 비교해 20 / 21 / 22 / −1을 고른다.
  - 디컴파일의 오프셋 0x60/0x64/0x68 = I 배열 24~26번이다 [판독 + 데이터].
  - `SetupAir`, `SetupFreeArea`, `SetupViewVolume`, `SetupCom`.
  - 배치/RNG 상세는5.6.
- `QuestionMgr::InitializeQuestion1 @0x710005a500`: 라운드 0,1,2 문제를 정한다(6.1).
- `CameraMgr::Initialize @0x710001fea0`
  - `Camera(1,0)`, `(2,1)`, `(4,2)`, `(8,3)` 4개를 만든다(레이어 비트, 플레이어 번호).
  - 첫 문제 기믹 방향 + 180°를 첫 라운드 시작 yaw로 저장한다(`+0x200`).
- `Camera::PrepareGame @0x710001a564`
  - 기준점 `base(+0x390) = (0, 카메라 y, 0)`, `baseZoom(+0x3B8) = |카메라 위치의 xz|`, 줌 = baseZoom.
  - 시작 회전 = `CalcViewAngle(전방)`.
  - `mg0122_cam_game.fsnb` 값 pos (0, 2.56, −0.72), aim (0, 2.47, −1.25) → 기준 (0, 2.56, 0), baseZoom 0.72 [데이터 + 판독].

### 3.3 라운드 상태기계 `GameMgr::UpdateGameMainSequence @0x7100027720` [판독]

`GameMgr+0xAC` = 라운드 경과 시간(매 프레임 += dt, 방송 0x2C에서 0). `+0xA8` = 단계 내 타이머.

| 단계(+0xA0) | 동작 | 다음 | 방송 |
|---|---|---|---|
| 1 (방송 0x14로 진입) | 0.1 s 대기 → 라운드 텔롭 | 6 | 0x25 |
| 2 | 페이드아웃 끝 대기 | 3 | 0x26 |
| 3 | 0.1 s → 4개 레이어 갱신 | 4 | 0x27 |
| 4 | 0.2 s 이상 + 문제 촬영 끝 → 페이드인 | 5 | 0x28 |
| 5 | 페이드 끝 → 라운드 텔롭 | 6 | — |
| 6 | 텔롭 끝 (첫 라운드면 0x2C 먼저) | 7 | 0x29 |
| 7 | 시작 연출 끝 → 휘슬 | 8 | **0x2A (조작 시작)** |
| 8 | 타이머 끝 **또는 4명 모두 촬영**(`PlayerMgr+0x1F4 > 3`) | 9 | 0x2B (조작 끝) |
| 9 | 1.0 s + 판정 중인 플레이어 없음 | 10 | — |
| 10 | `PlayerMgr::ScoreIn` | 11 | 0x2E |
| 11 | 점수 발표 완료를 기다린 뒤 2.0 s → `ScoreOut`, `QuestionMgr::NextRound`(이전 round > 2면 끝) | 12(끝) 또는 2 + 페이드아웃 | — |

- 타이머는 `UIMgr::RoundStart @0x710005f500`에서 `ComUiTimer::SetTimer(장면설정+0x08 = 30.0)`로 건다 [판독].
- **원본 round는 1~3, 질문 배열 인덱스는 0~2**다. `GameMgr::SetUpGame @0x7100025f90`의 QuestionMgr 초기화는 `+0x1E0=-1, +0x1E4=1`; `QuestionMgr::Notify`는 `round-1`로 배열을 읽는다. `NextRound @0x710005ad08`은 이전 값 > 2를 반환한 뒤 round를 1 증가시킨다(3→4에서 종료). 웹에서 0 기반 round를 쓰면 이 변환을 명시한다.


- 분할 단계는 [10_split_screen.md §1·2·3](../engine/10_split_screen.md)를 재사용한다. 시작 전 QuestionCapture의 호출@0x7100027644는 **StartSplitScreen(-1,0)**(focus,초)→SplitTo(2,2,−1,0), 화면0~3 균등 배치다. 이후0x29도 균등4분할을 설정하고, 라운드 FadedOut은 focus0 전체 화면으로 돌아간다. 첫 문제 준비의 상세 상태는5.5.
### 3.4 플레이어 한 라운드 [판독 `Player::Notify @0x7100055c8c`]

- 방송 0x2A
  - `captured(+0x221) = 0`, `roundScore(+0x22C) = 0`, `ComControlConfig()`(CPU 값 추첨), `inputEnabled(+0x220) = 1`.
  - 매 프레임 함수를 `PhoneControl`로 둔다.
- `PhoneControl @0x7100056204` (매 프레임):
  1. 사람이면 패드 → 회전 속도·줌 속도(6.1)를 구한다. CPU면 CPU 함수(`+0x2D0`)가 같은 값을 만든다.
  2. `Camera::CameraMove2(zoomRate, rotRate)`
  3. 셔터
     - 사람: `ComActorPad::GetTrigger() & 1`
     - CPU: `+0x2A8`
     - 셔터가 눌리면 `StartCapture`.
- `StartCapture @0x7100056c30`
  - 방송 0x2D, `ForceCalculateView`, `captured = 1`.
  - `PlayerMgr+0x1E8 |= 1<<idx`, `PlayerMgr+0x1F4++`, 보이스 `SQ_VOI_PC%02d_ETC`.
  - 다음 프레임 함수를 `UpdateCapture`로 둔다.
- `UpdateCapture @0x7100056d30`
  - 1프레임(`GetTimePerFrame`) 뒤 점수를 계산한다(6.6, `CalcScore`와 같은 식).
  - `Camera::GameCapture`(화면 캡처) → `QuestionCheck`.
- `QuestionCheck`: 0.3 s 뒤 판정 중 플래그 해제, 그래픽 레이어 갱신.
- 방송 0x2B: `inputEnabled = 0`. 찍지 않았으면 파인더 숨김.
- 방송 0x2E: 안 찍은 사람 화면 검게.
- 방송 0x34+idx
  - 점수 보이스: ≤ 0 `SAD`, 1~30 `ENVY`, 31~90 `JOY_MID`, > 90 `JOY_HIGH`(`SQ_VOI_PC%02d_*`).

**한 라운드에 한 번만 찍는다**: `StartCapture` 뒤 `PhoneControl`이 다시 걸리지 않는다. 0x2A 방송은 라운드 시작 때만 온다 [판독].

### 3.5 프레임 실행 순서 [판독]

main 0x0E에서 SceneModule→FiberModule 순서다. BaseUpdateObject::Update @0x71000061b0: enable인 동안 가상 Run(+0x28) → Fiber::Wait 반복. Camera secondary Fiber vtable은 thunk @0x7100006200을 거쳐 이 함수로 간다. GameMgr 자체는 Fiber를 만들지 않는다.

SetUpGame @0x7100025f90의 fiber 생성 및 manager Initialize/PostInitialize 리스트는 **MapMgr → QuestionMgr → CameraMgr → PlayerMgr → UIMgr → EmitMgr → NpcMgr → GimmickMgr**다. priority는 모두0. manager 전부를 먼저 생성하고 Initialize 한 패스, PostInitialize 다음 패스다. CameraMgr Initialize에서 Camera0~3, PlayerMgr Initialize에서 Player0~3 fiber를 추가한다. NPC별 fiber 없이 NpcMgr::Run @0x710004fd00이 목록 순서로 NPC Run을 호출한다.

| 상대 순서 | 실행 내용 |
|---|---|
| MapMgr → QuestionMgr | 맵·질문 콜백; 질문 촬영 대기/완료 포함 |
| CameraMgr → PlayerMgr → UIMgr → EmitMgr | CameraMgr/EmitMgr Run은 빈 함수. PlayerMgr는 BaseObject 콜백, UIMgr는 콜백 뒤 점수 UI |
| NpcMgr → GimmickMgr | NPC 목록의 콜백·행동·unique·시야/회피 후 기믹 목록 Run |
| Camera0→1→2→3 | BaseObject::Run의 +0xF0/+0x150 콜백. Camera Run이 빈 함수라는 해석은 잘못 |
| Player0→1→2→3 | 카메라 이동→셔터, pending capture 판정 등 |
| 공용 오류 감시 → 장면 흐름 | 정상 흐름에서 아래 main 근거로 연결 |

main Fiber @0x710018c9b0 등록, FUN_710018f400 pending 처리, FUN_710018f740 priority 안정 정렬을 대조했다. 같은 priority는 등록 순서다. Scene::SyncedSetupGameImpl @0x710005bad8에서 manager들을 만든 뒤 main SceneBase::UpdateMain이 흐름 FiberLite(priority0)를 생성한다. Scene::OnGameMainImpl @0x710005bc68은 GameMgr::UpdateGameMainSequence를 호출한다. **NPC/기믹 → 카메라 콜백 → 플레이어 → GameMgr 종료 판단**순서다.

공용 추가 fiber 생성 main @0x71002d16fc의 이름은 **FiberWatchNetError**다. vtable Update @0x71002d1b20 정상 경로는 Sleep(.25)→Net::IsLeftError 검사이며 오류 시 pause/UI를 처리한다.

공용 프레임 단계·Fiber 스케줄은 [01_core.md §3·파이버](../engine/01_core.md)를 재사용한다. 아래는 mg0122의 판정 시점에 필요한 연결부다. main 등록 @0x7100984a20, 의존 @0x7100984a58(t,A,B)는 **B→A**; Kahn @0x71009891a0의 무진입 임시 vector는 **LIFO**여서 Fiber의 안정 정렬과 혼동하지 않는다.

0x0E의 판독 간선: Scene(token0x7101C0E508)→Fiber(0x7101C0B438)→Entity(0x7101C436F8)→PhysicalAnimation(0x7101C31930) 및 Model(0x7101C3FD10). Model은 Graphic(0x7101C421B8)·token0x7101C41EA8 뒤에도 놓인다. **Model의0x0E 처리기 @0x71006bda60은 ret**이고 실제 다른 처리는0x15 @0x71006bda68,0x16 @0x71006bda80,0x18 @0x71006bdac0이다. 물리는0x0F Entity→Physics(@0x7100614624),0x10 Physics→Entity. Graphic은0x11 @0x710084d620·0x17 @0x710084d660·0x18 @0x710084d674. 따라서 Model의0x0E를 뼈 갱신 완료로 해석하지 않는다.

그 밖0x0E 처리기/token(주소는 main): @0x7100004ef0/0x7101BFBEA0, @0x710013bee0/0x7101C0A888, @0x71001cc85c/0x7101C100C8, @0x7100226eb4/0x7101C152A0, @0x71002c86ac/0x7101C20D78, Movie @0x710078cc0c/0x7101C41010, Font @0x7100807820/0x7101C41C18. @0x710013b9a4는token0x7101C34690→0x7101C0A888 간선을 추가한다. 독립 노드의 순서는 등록 vector와 위 Kahn 규칙으로 계산한다. mg0122 판정에 필요한 Scene→Fiber→Entity 관계는 확정이며, 관계가 없는 노드에 임의의 간선을 추가하지 않는다.

뼈 갱신 [판독, main]: Rigger 생성 @0x71006b05e4은 enabled=1, **UpdateTiming(+0x38)=0**. 메시지 처리 @0x71006b0b60은 timing0이면 Entity 메시지0x5F454E09, timing1이면 애니 계산 완료 메시지0x5F414E03에서 @0x71006b0cc0을 호출한다. timing0 경로는 같은 Entity의 ComAnimator+0x23C가 비영이면 건너뛴다. ComAnimator 계산 @0x710081c6e0은 애니 슬롯 적용 뒤0x5F414E03을 전송한다. RTTS UpdateTiming 속성 적용 @0x710070dea0→6b0808은 선택적으로 기본값을 덮어쓴다. 게임 Fiber는 Entity보다 앞이므로 판정에 쓰는 기존 뼈 transform과 뒤의 애니/렌더 pose를 같은 시점으로 합치지 않는다. 강제 갱신은 Camera::ForceCalculateView 경로이며, NPC 모델 전체를 강제 갱신한다는 호출은 확보한 촬영 경로에 없다.

### 5.2 문제 선택 [판독 `InitializeQuestion1`, `MapData::FindQuestionPatternGimmick @0x71000368b0`]

- 라운드 i(0~2)마다 `Qtbl[i]`의 질문들을 차례로 본다.
  - 그 질문 기믹 종류의 배치 후보(`MapData+0x238 + 종류·0x18` 목록)를 모은다.
  - 아직 문제로 안 쓴(+0x20 == −1) 것만 넣는다.
  - 두 번째 이후 라운드는 이전 문제 방향과 `CheckPlacement`(배치 각도)가 맞는 것만 넣는다.
- 후보 중 `SyncRandMod(후보 수)`로 하나 고른다(`@0x7100036ad8`). 그 기믹의 질문 ID를 저장하고 +0x24 = 라운드 번호+1로 표시한다.
- **[판독] `CheckPlacement @0x7100036b50`**: 일반 기믹은 이전 문제 방향과 `+0x30` 방향의 `abs(wrap180(diff)) >= 100°`일 때 허용한다. Walk(20~22)는 `GetPlacementPromenadeNumber`의 `n*90°`, Run(23)은 `wrap180(baseAngle + wrap180(n/−3*360°))` 후보 중 조건을 만족하면서 각도 차가 가장 큰 n을 고른다(동률은 먼저 본 후보 유지). 반환 하위 32비트는 허용 여부, 상위 32비트는 선택 n(일반 기믹은 −1).
- **[판독 + 디스어셈블리] `GetQuestionPlacementDeg @0x7100037040`**: Walk는 저장 n(`+0x28`)*90°를 wrap, Run은 baseAngle(`+0x30`)+wrap(n/−3*360°)를 wrap, 나머지는 `+0x30`을 반환한다. 디컴파일이 float 반환을 void로 표시하지만 `mgE_mg0122_dis.txt @0x7100037118`의 `ldr s0,[x1,#0x30]`로 확인된다.
- 후보 생성은5.6의 고정 목록·MapNpcPut 순서와 연결한다. 특정 실행의 최종 배치/RNG 출력은 초기 seed와 이후 입력·dt에 따라 결정된다.

### 5.3 문제 사진 [판독 `QuestionMgr::QuestionCapture @0x710005a810`]

```ts
B = camera0.base;  d = targetPos - B;             // targetPos = 문제 NPC의 GetQuestionPosition
yaw   = wrap180(atan2(dx / |dxz|, dz / |dxz|) * 57.29578)
v     = (0, -(p0 + dy), |dxz|)  (정규화)
pitch = atan2(v.y, v.z) * 57.29578                 // 양수 = 내려다봄
zoom  = sqrt(dx² + (p0 + dy)² + dz²) - p1          // 조준점까지 p1 만큼 남기고 전진
Q.angle = yaw; Q.height = pitch; Q.zoom = zoom; Q.uniqueSuccessPercent = 1.0
camera0.SetCameraDirection(yaw, pitch, zoom)       // 회전 클램프·줌 클램프 적용
1 프레임 뒤: Q.npcs = AddCameraInSightNpcData(camera0); camera0.QuestionCapture()(문제 화면 저장)
```

- p0, p1 = question.csv id0, id1.
- `atan2` 인자 순서와 정규화는 디컴파일(`fVar39`, `fVar20`)에서 읽었다. 0 나누기 보호(벡터 0이면 성분 0)가 있다 [판독].
- **문제의 줌·각도는 클램프된다.** 문제 값이 pitch 범위(−15.3~17.7)나 줌 범위(0.72~17)를 넘으면 문제 사진은 클램프된 구도다. 그러나 `Q.*`는 클램프 전 값이 저장된다(SetCameraDirection 전에 저장) [판독]. 원본 그대로 둔다.

### 5.4 JustTiming [판독 `QuestionMgr::Notify @0x710005a6cc`, 디스어셈블리]

방송 0x26 또는 0x0D를 받으면 다음을 한다.
- `lo, hi = (I7, I8) 또는 (I9, I10)`(질문 id6 > 0)
- `+0x1EC = lo' + SyncRandMod(hi' − lo' + 1)` (lo' = min, hi' = max)

`GetJustTimingRemainingTime = +0x1EC − GameMgr+0xAC`이다. `NpcBase::Notify @0x710000a620`의 방송0x0D를 대조했다. getter 직접 호출자는 Player::ComFuncDetailedMove0 @0x710005835c다. NPC 방송0x0D의 +0x230은 GimmickObject::GameFirstFade @0x7100008bf0(표시 설정). NPC 고유 timing(6.9)과 카운트다운을 구분한다.

### 5.5 오프닝과 첫 문제 준비

근거: `analysis/decomp/mg0122.nro.c`의 `UpdateGameOpeningSequence @0x71000270c0`, `UpdateGameStartBeforeSequence @0x7100027370`, `GameStartBefore_Prepare @0x71000274d0`, `GameStartBefore_QuestionCapture @0x71000275b0`.

- 오프닝 상태(+0x98): 0에서 0x1F 방송 → 1에서 카메라0의 오프닝 완료 대기 → 1.0초 FadeOut → 2에서 페이드 완료 후 0x20 방송·상태6 → 완료 반환.
- 시작 전 상태(+0x9C): 0에서 0x23 방송·상태1 → 0.1초 후 네 그래픽 레이어 활성화·0x21 방송·상태2 → 최소 0.2초와 문제 촬영 완료를 모두 기다림 → 분할 화면 즉시 시작(`StartSplitScreen(-1,0)`)·0x24 방송·상태3.
- 상태3은 페이드 완료 후 roundElapsed(+0xAC)=0·상태4다. 첫 문제 준비의 FadeIn 요청은 GameMgr+8의 플래그 하위 2비트가 모두 0일 때 1.0초로 걸린다. GameMgr 생성 @0x7100025b84은 +8=0; SetInst @0x710002709c는 bit0을 켜고, Notify @0x7100028450의 방송0x0F(OpeningSkip, Scene @0x710005bc48)는 bit1을 켠다. 따라서 설명 모드나 오프닝 생략이면 이 FadeIn 요청을 건너뛴다.
- 웹은 loading과 게임 prepare를 분리한다.

### 6.1 카메라 조작 [판독 `Player::PhoneControl`, `PlayerControl @0x7100056a0c`, `Camera::CameraMove2 @0x710001b1c8`]

- "줌"은 렌즈가 아니라 **카메라가 바라보는 방향으로 기준점에서 전진한 거리**다. 화각은 fsnb 고정값(fovy 0.61177 rad ≈ 35.05°)이다 [판독 + 데이터].
- 회전 [판독]: `rot = (pitch, yaw)` → `SetRotationFromEuler`(bezel EulerXYZ, R = Rz·Ry·Rx). CameraMove @0x710001b1c8의 방향은 `d=R·(0,0,1)=(sin(yaw)cos(pitch),−sin(pitch),cos(yaw)cos(pitch))`; yaw0은 +Z, pitch 양수는 아래다.
- VP [판독, main `camera_core.c`/바이너리]: GfxUtil::CalculateViewFromTransform @0x710084b358은 X/Z 기저를 반전하여 `V=diag(−1,1,−1)·Rᵀ·translate(−pos)`를 만든다. ComCamera::_internalCalculateView @0x7100849250은 엔티티 transform과 애니메이션 view의 역변환(@0x710084b4a0)을 합성한다. PrepareGame의 애니 view 초기화는 추가 pose가 없는 상태다. 따라서 원본 actor의 광학 전방은 +Z이며 three camera는 `qThree=qActor·qY(π)`가 필요하다.
- 투영식은 이미 확정된 [07_camera_lighting.md §4.4](../engine/07_camera_lighting.md)의 SetProjectionPerspectiveFovy(main @0x7100846b04)를 재사용한다. mg0122는 fovy .61177/aspect16:9/near1/far1000, native 깊이 near0/far1이다. three/WebGL과는 `zThree=2·zNative−1`; 판정 trace에는 native 깊이를 보존한다. 게임 actor의 +Z 시선 연결은 위 view 변환으로 대조했다. 삼각함수 근사·NEON 정규화의 bit 단위 결과는 JS Math/일반 정규화와 별도 대조 대상이다.

### 6.4 카메라 근접도 `Player::CalcCameraScore @0x71000570e0` [판독: 디스어셈블리, 반환 s0·s1 두 값]

```ts
dh = |Q.height - cam.pitch|
da = |wrap180(Q.angle - cam.yaw)|
dz = |Q.zoom   - cam.zoom|
// s0: 벌점 배율 (CalcScore 에서 쓰지 않음)
m = 1
if (dh - tolH > 0) m = min(1, (minF - 1) * min((dh - tolH) / rangeH, 1) + 1)
if (da - tolA > 0) m = min(m, (minF - 1) * min((da - tolA) / rangeA, 1) + 1)
if (dz - tolZ > 0) m = min(m, (minF - 1) * min((dz - tolZ) / rangeZ, 1) + 1)
// s1: 근접도
rH = max(dh / (tolH + rangeH), 0); rA = da / (tolA + rangeA); rZ = dz / (tolZ + rangeZ)
r  = max(rH, rA, rZ)                     // fcsel gt 순서: (rH > rA ? rH : rA), 그 결과 > rZ ? 그것 : rZ
close = clamp(1 - r + 0.0099, 0, 1)      // 상수 0x3C22339C = 0.0099
return [m, close]
```

- tol*는 질문 표(4.2)에서, range*·minF는 config(4.1: yaw 5°, pitch 1.5°, 줌 0.5, minF 0.5)에서 온다.
- **허용 오차 안이어도 근접도는 오차에 비례해 깎인다.** r = 오차/(허용+여유)이기 때문이다.
  - 예: Q4(tolA 10°)에서 yaw만 15° 어긋나면 r = 1 → close = 0.0099.
  - 예: pitch만 3° 어긋나면 close = 0.343 [재구현 계산].
- Ghidra 디컴파일은 반환을 float 하나로 보여주고 s1을 잃는다. **디스어셈블리 기준으로 옮길 것.**

[05 §7.8](../engine/05_ui_input.md)의 `SetFrame @0x7100813730 → 080f86c` 노드별 경로는 **같은 노드의 FTRG 재등록·first 초기화를 하지 않는다**. 이전 frame/loop 문맥을 유지하며, 수집 `@0x71005f3ccc`에는 speed=0 억제 gate가 없다. 활성 정방향 트랙·wrap 없음이면20/22f key는 각각 **p<e≤f 또는 최초 e=f** 조건으로 평가된다. 반복 SetFrame을 매번 최초 평가로 만들거나 `floor(frame)==20/22`만으로 재생하지 않는다. 실제 loop 통과 횟수는 공용 §7.5의 슬롯별 식을 사용한다.

[미확정] 자동 부착·SetFrame 문맥 보존과 **모델별 트랙 등록 소스/그룹·조건 그래프의 최종 활성 상태**는 구분한다([05 §7.9](../engine/05_ui_input.md)). 정상 frame 직접 설정과5.10의 명시적 SE가 같은 frame에 함께 발화하는지, 실제 재생 횟수는 해당 슬롯/트랙 활성 상태·callback trace로 대조해야 한다. 현재 근거로 중복 없음·매 프레임 발화·임의 dedup을 확정하지 않는다. 20f Hit00/22f SE 데이터와 명시적 재생 경로는 각각 보존한다.

Stage3D의 공용 gl 주입·소유권 구분은 최신 `gpu: StageGpu` API로 이미 지원된다. 신규 mg0122 view가 이를 이용할 수 있으므로 그 목적의 stage.ts 수정은 필요 없다. 앱 전체 한 렌더러 요구는 `view/renderer.ts`, main과 각 `*_page.ts`/Preview3D/2D 레이아웃의 생성·정리 경계도 검토해야 한다. 이는 mg0122만의 점수 포팅과 별도 공용 작업이다.

구현 순서: 점수 합성 대조 → 카메라/입력 → 진행/UI → NPC/기믹 → CPU.

### 10.2 게임 고유 연결의 정적 경계 [판독·데이터]

두 UpdateHead의 진입/인라인 연결과 JumpRope 보조 callback·bit 쓰기는2절 NRO·C·ASM·재배치 데이터의 기존 판독이다. 독립 함수 미참조와 정상 메서드 인라인 실행을 구분한다.

**UpdateHead 독립 함수.** `Npc_TreeEscaper::UpdateHead @0x710003e7ac`(880B), `Npc_PromenadeEscaper::UpdateHead @0x71000434bc`(232B)는 NRO text `0x7100003000~0x7100065ffc`에서 해당 주소로의 B/BL·PLT 연결, ADR/ADRP+ADD 함수 포인터 구성, RELA/JMPREL·vtable 등록·재배치된 함수 포인터를 찾지 못했다. 원본 offset 값은 dynsym `st_value`의 `@0x71000bd7c0 / @0x71000c1228`에만 있다. **동적 심볼 정의만으로 정상 callback 등록을 뜻하지 않는다.** 다만 독립 주소 미참조와 몸체의 인라인 실행은 별개다.

| 타입 | 정상 수명 메서드와의 연결 | 포팅 판단 |
|---|---|---|
| PromenadeEscaper | PostConfig `@433dc`, 촬영 준비 `@436bc`, 종료 `@437e8`, ActionUpdate `@439e4`는 실제 vtable `+300/+378/+380/+358`에 연결. 이들의 head 계산 블록 시작 `@43420/@4374c/@43850/@43a3c`와 독립 helper 안 `@43504`는 **29명령·116B가 완전히 동일**. 파트너 target 설정은5.9의 기존 명세대로 도달한다 | 기존 정상 메서드의 head 목표/즉시보기 조건을 유지한다. 별도 helper의 추가 호출은 하지 않는다 |
| TreeEscaper | PostConfig `@3dee4`는 빈 함수. 기존 촬영/종료·ActionUpdate 경로에는 helper의 `SetTargetLookAtDirection(+1D8)/LookImmediately(+1E0)` 연결이 없다. 전용 각도 `+3A4` 읽기는 전체 text에서 `@3e8c0`, 독립 helper 안 한 곳뿐이다 | 각도 초기화만으로 해당 head helper 실행을 추가하지 않는다. 공통 ComHeading 수명주기와는 구분한다 |

위 표의 짧은 주소도2절 베이스를 더한 NRO 주소다. 기존5.9의 산책 target 식·latch와 나무의 몸 이동 명세는 그대로 재사용한다. **Tree helper의 정상 진입은 미확인**이며, 원본 실행에서 해당 PC/target 변경이 관측되면 외부 진입과 호출자를 함께 확보해야 한다.

**JumpRope 보조 FSM.** `JumpStart @0x71000451c0`(228B) 역시 위 text 범위의 직접 분기·포인터 구성·재배치/vtable 진입을 찾지 못했다. offset 값은 dynsym `st_value @0x71000bb5a0`만 있다. 다음은5.10에서 이미 판독한 운동식이 아니라 **초기 진입과 쓰기 연결**이다.

| 연결 | 확인한 코드·데이터 |
|---|---|
| 실제 생성의 초기값 | GimmickFreeJumpRope::Setup `@2f500`이 해당 생성자를 호출. ctor `@449b8`의 `@449d0/449dc`는 내부 wrapper `+3B0=0`, flags `+3C0=0`을 쓴다 |
| 정상 설정/갱신 | ActionConfig `@44a9c`는 main function `+D0`에 virtual `+358=ActionUpdate`만 등록; 내부 function `+390`을 채우지 않는다. ActionUpdate `@45188`는 base 뒤 `+3B0≠0`일 때만 내부 callback 실행 |
| 내부 순환 | GOT `@126348/126350`은 GLOB_DAT로 FuncJump/FuncReadyToJump를 가리킨다. FuncJump pointer 읽기는 JumpStart `@4522c`와 Ready `@45498`, Ready pointer 읽기는 FuncJump `@4537c`. Ready 안에는 JumpStart와 같은 초기화가 인라인되어 있지만 **그 Ready 자체의 초기 등록 경로가 없다** |

따라서 **현재 NRO에서 확보한 정상 생성·설정 경로는 내부 Jump↔Ready 순환을 활성화하지 않는다**. 보조 FSM을 매 프레임 강제로 호출하거나 bit1을 켜면 원본에서 확보하지 못한 운동/난수 소비가 생긴다. 정상 rope phase·broadcast0x33/frame 동기·모션 규칙은5.10을 그대로 사용한다. 외부 동적 호출·메모리 쓰기까지 존재하지 않는다고 증명한 것은 아니며, 이를 주장하려면 JumpStart/Ready 진입 PC와 `+390/+3B0/+3C0`의 최초 변경·호출자가 필요하다.

## 11. 사용자 확인 필요

[미확정] 원본 골든·사진·동일 pose의 PhysX hit 기록이 없어 원본 실행·픽셀 동등성은 확인되지 않았다. 확인 자료의 최소 항목은10.3이다. Tree helper·JumpRope 보조 FSM의 외부 진입 관측도10.2의 정적 경계와 분리한다.

현재 구현을 시작하기 위한 추가 사용자 선택은 없다. 원본 동등성을 유지할 범위에서 남은 공용 shader/FTRG/Effect 입력 계약은 담당 문서의 미확정으로 보존한다.
