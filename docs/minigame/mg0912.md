## 1. 기능 개요와 사용자에게 보이는 동작

4인 대결(GameRule "Chara")이다. 각자 요시를 타고 4분할 화면으로 산길 코스를 올라가 정상의 골에 먼저 닿는 사람이 이긴다.

- 조작 [데이터 `extracted/message/koKR/mg_inst.json`]:
  - 스틱: 이동(`inst_mg0912_ctrl00`)
  - A: 점프(`ctrl01`)
  - A 길게 누르기: 버티기 점프(`ctrl02`, 요시의 버둥 점프)
- 규칙 문구 [데이터 `im_mg_inst.json`]: "요시에 타고 산 위의 골인 지점을 향해 나아가세요. 과일을 먹으면 몇 초 동안 대시합니다."
- 어드밴티지 [데이터]: "스타트 시, 눈앞에 과일이 놓입니다." 코드에서는 어드밴티지 플레이어 앞에 과일 3개가 떨어진다(6.10.1).
- 끝: 기본 판정에서는 **3명이 골에 들어간 다음 프레임**에 끝난다(6.9). 시간 제한(300 s)으로도 끝난다 [추정: 프레임워크].
- 방해물: 굴러 내려오는 바위, 고정 바위, 텐텐(돌아다니는 적), 뻐끔플라워, 낭떠러지·물. 이동 보조: 트램펄린 13개, 움직이는 상자 리프트 2개, 과일(대시).

### 3.4 오프닝 = 어드밴티지 연출 (UpdateOpening) [판독]

+0x2b0을 u64로 0으로 써서 +0x2b4 타이머도 같이 0이 된다.

| 상태 | 처리 | 넘어가는 조건 |
|---|---|---|
| 0 | `IsMinigameAdvantage`인 사람이 없으면 **바로 return 1**. 있으면 `AdvantagePlayerExplainStart` + 이펙트 | → 1 |
| 1 | `CheckAdvantagePlayerExplainEnd` | → 2, `MapManager::SetAdvantagFallNut()` |
| 2 | 매 프레임 `MapManager::UpdateOp`(Stage::Update + 모든 `Nut::UpdateOp`) | 타이머 > 2.0 → 3 |
| 3 | 이펙트 끄고 return 1 | |

매 프레임 +0x2b4 += dt. `GetAdvantagPlayerOrder` = 0..3 중 처음 `IsMinigameAdvantage`인 순번, 없으면 −1.

### 3.5 GameMgr::Update (게임 본편, 매 프레임) [판독: 판독자 C + 디컴파일 대조]

```ts
if (!this.firstUpdated /*+0x1c0*/) {           // 첫 호출만
  this.firstUpdated = 1;
  playerMgr.setInputEnableControl(true); playerMgr.setState(0); ui.uiIn();
}
const judge = GameWork.GetGameJudgeType();
if (judge === 0) {
  if (this.goalCount /*+0x294*/ > 2) {          // 골 번호 3개(0,1,2)를 다 나눠 준 뒤
    this.finalRankDone /*+0x2b8*/ = 1;
    if (playerMgr.checkGoalPlayer() !== -1) {   // 상태 5 인 플레이어가 있으면
      playerMgr.updatePlayer();
      for (i of 0..3) { MGMgr.SetPlayerWinLose(id_i, P[i].rank === 0); MGMgr.SetPlayerRank(id_i, P[i].rank /*+0x178*/, 0); }
      playerMgr.setRank();
      return 1;                                  // 게임 끝
    }
  }
} else {
  if (playerMgr.checkGoalPlayer() !== -1) return 1;   // 첫 골인 즉시 끝. 순위 처리는 OnGameFinish 가 한다(+0x2b8 = 0)
}

playerMgr.updatePlayer();                        // Player::Update ×4 → 순위 계산 (6.9)

```

- `PlayerManager::CheckGoalPlayer @0x710006fc70` = 처음으로 `Player+0x118 == 5`(골 자동 이동)인 플레이어 ID, 없으면 −1.
- 골 번호 발급은 `Player::CastRayCheckGoal`(6.9.2)이 `PlayerManager::UpdatePlayer` 안에서 한다. 그래서 **3번째 골인 프레임 다음 프레임**의 Update 머리에서 끝난다 [판독, 순서에서 유도].
- **정정**: 판독자 C 노트는 "CheckGoalPlayer로 찾으면 순위 처리 후 return 1"을 JudgeType과 무관한 것처럼 적었다. 디컴파일(`mg0912.nro.c` 35521~35680행)을 보면 순위 처리는 **JudgeType 0 && 골 인원 > 2** 분기 안에만 있다. JudgeType ≠ 0이면 CheckGoalPlayer만 보고 순위 처리 없이 return 1이다. 첫 호출 초기화(입력 켜기·SetState(0)·UiIn)도 노트에 없던 것을 더했다.
- JudgeType 값의 뜻과 보통 대전의 값은 **[미확정]**이다.

### 3.6 엔진 타이밍과 dt [판독: 01_core, SHARED]

- 장면 갱신(위 Update)은 CoreSystem 타이밍 0x0E의 SceneModule에서 프레임당 한 번 돈다. PhysX 시뮬레이션은 그 뒤 0x0F(FixUpdate 서브스텝)에서 돈다(SHARED [mgB] 0x7100613f5c = PhysicsModule).
- mg0912는 리듬 장면이 아니다. 그래서 오프라인에서 `GetDeltaTime`은 Variable60 실측값(최대 0.05 s)이다. 온라인 동기 중에는 고정 1/60이다([01_core 4.4](../engine/01_core.md)).
- **액터 적분은 dt를 1/60 서브스텝 n = int(dt·60 + 0.5)회로 나눠 돈다**(6.1). 그래서 이동·점프·중력은 사실상 고정 1/60 스텝이다. 반면 게임 코드의 타이머·과일 낙하·넉백·카메라 lerp는 dt를 그대로 쓴다.
- 컴포넌트 Tick(ComActor 갱신, ComUiTimer 등)과 장면 Update의 같은 프레임 안 순서, 액터 접지 잡과 틱의 순서는 **[미확정]**이다.

→ 정리본: [17_actor.md](../engine/17_actor.md) §3.2, 6.1

### 4.2 GameParam (mg0912_config.csv) [판독 `GameParam::Initialize @0x7100053a90`, 데이터]

- 로더 규칙은 mg0911과 같다(SHARED [mgB]). 각 행 = `값, 형식`. FLOAT 행은 float 벡터에, INT 행은 int 벡터에 **나온 순서대로** 쌓는다. `GetCsvParamF(i)`는 float 벡터의 i번째다.
- mg0912 CSV는 62행이고 **0행만 INT(값 1)**다. 그래서 **F[i] = 0부터 센 CSV 행 i+1**이다. 판독자 D의 "config.csv i+1번째 행"은 0부터 센 행 번호를 뜻한다. 1부터 세면 i+2번째 줄이다.
- **두 노트의 F 인덱스는 같은 체계다** [데이터: `analysis/mgB_params.json` `mg0912.configFI`로 대조]. 표본: F45 = 7.8(CSV 행 46), F11 = 23(행 12), F58 = 80(행 59). 아래 표의 값 39개가 모두 configFI와 맞는다.
- F는 61개, I는 1개(I0 = 1)다. 코드가 실제로 읽는 F는 39개다(GetCsvParamF 호출 57곳, 판독자 C). **I0을 읽는 곳은 없다**(GetCsvParamI 호출 0곳).

```ts
function jumpAccel(vy) {                       // m/s², 음수 = 아래
  if (vy >= 5)   return -150;
  if (vy >= 4)   return -150 + (vy - 5) / (4 - 5) * (-25 + 150);   // 5→4 에서 -150 → -25
  if (vy >= -10) return -25 + (vy - 4) / (-10 - 4) * (-49 + 25);   // 4→-10 에서 -25 → -49
  return -49;
}
factor = jumpAccel(vy) / -9.8;                 // 실제 가속도 = scale·9.8·factor
```

- 점프 계산기가 꺼져 있으면(땅에서 리셋된 뒤) factor = 5.0이다. 즉 **점프 없이 낭떠러지로 걸어 나가면 49 m/s²로 떨어진다.**
- Start 프레임 한 번은 factor 0이다. 조건은 카운터 < holdFrameMax(7)이고 Start한 FrameCount와 지금이 같을 때다.

#### 6.12.5 목표·방향·입력

- `UpdateMoveTarget @0x710001c908`:
  - 회복 중: 목표 = 회복점[idx] + off. 거리² ≤ 0.25면 다음 점, 목록이 끝나면 해제.
  - 과일 목표: 과일 위치.
  - 그 밖: idx = clamp(c+1, 0, n−1). 이전 목표보다 뒤면 이전 점 fail++. 바뀌면 오프셋 재추첨. 목표 = 점 + 오프셋.
  - ComPoint+0x50 = 목표. valid[+0x60] = IsAppropriateTargetPosition && !(회복 중 && IsConflictOtherPlayer). [0x149] = 회복 중 충돌.
- `IsAppropriateTargetPosition`: RollOverRock마다 검사한다.
  - comrocksevasion == 0이면 목표 수평 4.25 m 안에 바위가 있을 때 거짓.
  - 아니면(기본 1) 나→목표 선분과 바위 거리 < 2.75일 때 거짓.
- `IsConflictOtherPlayer`: |dy| < 10 && 거리² < 1.1025인 다른 플레이어 [추정: NEON].
- `UpdateMoveDirection @0x710001ceb0`: [0x149] || [0x14a]이면 0. 아니면 dir = normalize(Σ 유효 IObject.Run(pos)), y = 0. 목표가 유효하고 거리 < 1이면 dir ×= max(거리, 0.5).
- `UpdatePadInput @0x710001d090` [판독: 디스어셈블]:
  - ψ = atan2(−cam[0xa8], −cam[0xa0]) + π/2로 dir를 Y축 회전 → 원하는 스틱.
  - stick[0x160]이 dt·4.0만큼 다가간다.
  - 오버레이 스틱 = (s.x, −s.z), 길이 > 1이면 정규화.
  - Hold = [0x14b] (bit0 A), Trigger = hold & ~prev, Release = prev & ~hold.
- `OnDamage`: 현재 목표점 fail++, 재추첨. `OnReturn`: 회복·과일 해제, target = −1. `OnTrampoline`: 상태 3.
- 호출처 없음: OnFallStage, WeakMovePosRandom, ChangeAIState, ResetPadInput.

→ 정리본: [17_actor.md](../engine/17_actor.md) §6.6, 8.3

### 6.13 난수 — 전부 동기(Sync), async 없음 [판독, 두 노트 합침]

식은 [01_core 6.6](../engine/01_core.md)이다.
- `SyncRandMod(n)` = (u × n) >> 32. n < 2면 소비 없이 0이다.
- `SyncRandModF(x)` = f32(f32(u) × x) × 2⁻³². x ≤ 0이면 0이다.
- **정정**: 판독자 D 노트의 "SyncRandModF float 식은 01_core.md 에 없음 [미확정]"은 틀렸다. 01_core 6.6 표의 sync 열에 있다.

| 1 | CreateMap | `SyncRandModF(frameMax)` ×2 | MoveRoad 시작 프레임 |

| 3 | CreateMap | `SyncRandMod(3)` ×3 | 어드밴티지 지연 셔플 |

**웹에서 대체 구현이 필요한 것** — 근사, 동등성은 사건 수준에서 맞춘다.
- **PhysX 레이캐스트·셰이프캐스트**: `mgB_apx.json`의 정적 메시(attr 4/2/14 등)와 box 트리거(attr 9/10/11/12)를 BVH로 만들어 직접 구현한다. 기하는 같다. 다만 PhysX의 초기 겹침 판정·hit 거리 정밀도·삼각형 경계 처리와 비트 단위로 같을 수 없다.
- **정적 메시와의 접촉 밀어내기**(DetectContactsMap → 평균 밀기): 캡슐-삼각형 침투 벡터를 직접 계산한다. 접촉 생성 방식이 달라 벽 긁힘에서 미세한 차이가 난다.
- **굴러바위 강체**: 구 하나의 적분 + 정적 메시 접촉으로 대체한다. 마찰·반발이 0이라 회전은 무시할 수 있다 [판단]. 궤적은 근사이고, 플레이어 판정은 코드 구라서 궤적 차이가 피격 타이밍 차이로 이어진다.
- **텐텐·뻐끔의 PhysX 형상**: 플레이어 판정은 코드 기하라 그대로다. PhysX 형상은 플레이어 바디 밀어내기에만 쓰이는 것으로 보인다 [추정].
- **CCT**: `charactorcollisionenabled` 기본 0이라 **기본 꺼짐**이다. 웹은 구현하지 않아도 된다(켜는 디버그 옵션만 둘 경우 별도).
- **플레이어끼리 바디 충돌**(main ActorWorld): 세부가 [미확정]이다. 캡슐 A(r 0.9)끼리의 밀어내기로 근사하고 표시한다.
- **애니메이션 구동 요소**: MoveRoad 상자·굴러바위 상승은 fskb 본 트랙을 샘플해야 한다. 모션 프레임 조건(데미지 38, 먹기 13, 뻐끔 26~40, 텐텐 21/41~61)은 클립 프레임 진행 규칙이 필요하다. 프레임 step 출처가 [미확정]이므로(SHARED [mgE]) 우선 `frame += 60·dt·speed`로 두고 표시한다.
- **dt**: 오프라인 원본은 가변 dt(≤ 0.05)지만 웹은 고정 1/60으로 돈다(온라인 원본과 같다). 넉백·카메라처럼 dt 의존 식은 1/60 기준으로 맞는다.

### 9.3 한 step 순서 (권장)

```
1. 입력 → ComActorPad (사람) / ComAI 오버레이는 Player::Update 안에서
2. GameMgr.update():                       // 3.5
     끝 판정 → Npc → PlayerManager.updatePlayer (Player::Update ×4: ComAI → 레이 → 상태 → 먹기 → 넉백 → 거리)
     → 순위 → Map(Stage 마스크 → MoveRoad → RollOverRock → Trampoline → Nut) → Ui → Camera → EffectCulling
3. 액터 틱 ×4 (ExAction → 적분 → 회전)    // 원본 상대 순서 [미확정]: 2 앞인지 뒤인지
4. 접지 잡·맵 밀어내기
5. 굴러바위 강체 스텝 (PhysX 0x0F 대체)
```

3·4의 위치가 원본과 다르면 1프레임 차이가 날 수 있다. 원본 골든이 생기면 맞춘다.
