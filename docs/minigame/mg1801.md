## 1. 기능 개요와 사용자에게 보이는 동작

4인 협력 리듬 미니게임이다. 플레이어 4명이 조리대 앞 의자에 한 줄로 서 있다. 채소가 위에서 박자에 맞춰 한 칸씩 내려오면, Joy-Con을 세로로 쥐고 박자에 맞춰 휘둘러 칼질한다.

- 채소마다 차지하는 자리(레인) 수가 다르다. 긴 채소는 여러 플레이어 앞에 걸쳐 놓이고, 플레이어마다 자기 앞부분을 한 번씩 자른다.
  - 토마토 1칸, 버섯 1칸, 감자 2칸, 가지 3칸, 당근 4칸.
- 판정은 세 가지다: JUST, FAST(빠름), SLOW(늦음).
  - JUST로 자른 조각만 좌우로 갈라져 날아간다(6.8).
  - 점수는 JUST 2점, FAST·SLOW 1점, 놓침 0점이다(6.6).
- 칼을 휘두르면 칼 소리가 난다. 자르면 판정음이 나고, JUST면 **지금 BGM 코드에 맞춘 아르페지오**가 겹친다. 연속 JUST면 아르페지오가 길어진다(7.2).
- 잘린 채소는 아래 물(수프 냄비)로 떨어진다. 조각마다 물보라 이펙트와 소리가 난다.
- BGM은 40초 곡 한 번이다(20마디, 반복 없음). 끝나면 종료 징글이 나오고 결과 연출로 넘어간다.
- 결과 연출: 팀 달성률이 80 % 이상, 40 % 이상, 0 초과, 0인지에 따라 수프 모델 `mg1801_soup03~00` 중 하나가 나온다. 결과 징글은 달성률 40 % 이상이면 GOOD, 아니면 BAD다(6.6).

## 3. 진입점과 전체 호출 흐름

### 3.1 클래스 구성 [판독]

```
mg1801::Scene : ca::rm::RmMgSceneBase : bq::MinigameScene     장면. 리듬 공용 흐름은 기반 클래스가 돈다
  └ MaintainProduct(Impl)    제품 묶음. GetScene / GetPlayerMan / GetObjectMan / GetStageMan
      ├ Product<StageMan>  = MapImpl        무대(배경·NPC·카메라·결과 연출)
      ├ Product<ObjectMan> = ObjectManImpl  채소 풀(5종 × 15개) + 판정
      └ Product<PlayerMan> = PlayerManImpl  플레이어 4명(Player + Player::PadDriver)
  SenderState / StateReceiver   장면 → 제품 상태 알림(채널, 값)
```

`MaintainProductImpl::Initialize @0x710000db00`이 Stage → Object → Player 순서로 만들고, 만든 순서대로 각 제품의 `Initialize`를 부른다. 이어서 `SetupPhase1`과 `SetupPhase2`도 같은 순서로 부른다.

ObjectMan과 PlayerMan의 `Update`는 **파이버**다. 무한 루프 안에서 한 프레임 일한 뒤 `bex::Fiber::Wait()`로 다음 프레임까지 쉰다.
- `ObjectManImpl::Update @0x7100004920`: 모든 Obj의 `Obj::Update`. 등록된 프레임에 바로 한 번 돈다(Obj가 모두 비활성이라 변화 없음).
- `PlayerManImpl::Update @0x710000a9f0`: Player 포인터가 생길 때까지 `Wait()`, 그 뒤 Player 0~3의 `MyUpdate`.
- `MapImpl::Update @0x7100010a70`: `Wait()`만 반복한다.
- `Wait()` = `Wait(1)`: 이번 프레임 실행을 멈추고 **다음 프레임 같은 자리에서** 이어 돈다(main `bex::Fiber::Wait @0x710018cbd8` → `FUN_710018ddb0(impl, 1)`) [판독, [mg1801_core.md](../../../analysis/notes/mg1801_core.md) 4절].

### 3.2 준비 단계

1. `Scene::Scene @0x710000e874`
   - `RmMgSceneBase` 생성자가 돈다. 이 생성자는 다음을 한다.
     - 아카이브 `mg/mg1800`·`libca/mg_common`, 모션 `rhy`·`rc`, 사운드 `sound/subarc_rc_cmn`을 싣게 한다(7.1).
     - **메인 루프를 Fixed60으로 바꾼다**(main `@0x7100440fb8` `FUN_710019642c(MainModule,1)`). 그래서 이 장면 동안 `GetDeltaTime()`은 항상 f32(1/60) = `0x3C888889`다 [판독, mg1801_core.md 1절]. 소멸자 `@0x7100441390`이 원래 모드로 되돌린다.
   - mg1801 생성자는 NPC를 싣게 한다: `LoadSceneNonPlayerCharacter(5,0,1)`. NonPlayerCharacterID 5 = **HEYHO** → `chara/npc002` [판독][데이터, 06_scene_data 1.7].
2. `RmMgSceneBase::SetupGame` (main `@0x71004415a4`)
   - 리듬 공용 매니저를 만든다(RmCmnParamMan, RmFileMan, RmChartDataMan, RmSoundMan).
   - 상태값을 초기화한다: `+0x370` 단계 = 0, `+0x380` = −1, `+0x388` = −1, `+0x428` = −1 등. 전체는 [mg1801_rhythm.md](../../../analysis/notes/mg1801_rhythm.md) 5.1.
3. 장면 구현체 상태 8: 동기 난수 시드를 넣는다(오프라인 `SetSyncRandSeed(RandModule::Rand())`) [판독, mg1801_core.md 3.3]. 같은 상태에서 이어서 `OnStartUpdate` → `SyncedSetupGame`이 돈다.
4. `RmMgSceneBase::SyncedSetupGame` (main `@0x7100443340`)
   - 공용 UI를 만든다: RmUiStatusMan, 텔롭, 타이밍 원, 연습 화살표, 별 이펙트, 결과 연출, RmUiCntWipe.
   - PlayMode 1(미니게임 모드)이면 `RmGameWork+0x20 = RhythmWork.mode ? 2 : 0`으로 둔다(3.2 표).
   - 이어서 가상 함수 +0x2A0 = **`mg1801::Scene::RmSyncedSetupGame @0x710000e914`**를 부른다. 이 함수가 하는 일:
     - `MaintainProduct::Create` → 인터페이스 +0x10 = Initialize(제품 파이버가 여기서 등록된다)
     - `SetMgBgmBeforeOneBeatStart(1,0)`: 4분 박 상태가 마디 마지막 박(4)이 될 때부터 줄 배분을 시작한다(5.3) [판독 `@0x710000e944`]
     - **`SetMainBeatType(1)`**: 채보 한 줄 = 8분음표
     - `SetMainBgmName("SM_BGM_BDCN001_TEST_JMP")`
       - **정정:** 이 이름은 저장만 되고 재생에 쓰이지 않는다. 실제 메인 시퀀스는 `OnGameStartAfter`가 재생하는 `SQ_BGM_RC_MAIN_RHYTHM` + `SQ_BGM_RC_MGCMN_OP`다 [판독 main `@0x7100443fa8` → `FUN_71004263c8`].

   - 돌아온 뒤 채보 경로에 `"chart01."`이 있으면 `+0x470 = 1`로 둔다(BGM `_C`).

### 3.3 게임 진행 (매 프레임) [판독 main `RmMgSceneBase::OnGameMain @0x71004441e8`]

`this+0x370`이 단계 번호다. 단계 0~10 전체는 5.3에 있다. 줄 배분은 OnGameMain 끝의 공통 꼬리에서 한다.

```c
iVar5 = GetBeatState(mainBeatType = 1);           // ceil(G14 * 0.5) = 1..8 (마디 안 몇째 8분)
if (stage < 6) {
  if (beforeOneBeat(+0x420) && stage > 3 &&
      (!useBeat(+0x421) || GetBeatState(+0x424) == BEATS_PER_BAR[+0x424])) goto ENTRY;
} else {
  // Lock 배분: 끝 조건의 기준. mg1801은 Lock 훅(vt+0x330)을 덮어쓰지 않는다
  if (+0x388 != iVar5 && +0x384 < 줄수 && !끝플래그 && !강제종료) { vt+0x330(Data{+0x384, iVar5, 8칸}); +0x388 = iVar5; +0x384++; }
ENTRY:
  +0x378++;                                        // 경과 프레임
  if (+0x380 != iVar5 && +0x37C < 줄수 && !끝플래그 && !강제종료) {
    vt+0x328(OnRmRecieveBeatEntry, Data{+0x37C, iVar5, 1P..4P, OBJ1..4});
    if (+0x428 > 0 && +0x37C + +0x428 < 줄수) vt+0x338(NextEntry, …);   // mg1801: +0x428 = −1, 안 탄다
    +0x380 = iVar5; +0x37C++;
  }
}
```

- 이 꼬리는 단계 0~5에서 조기 반환하지 않은 프레임과, 단계 6 이상인 모든 프레임에서 돈다 [판독].
- `+0x378`(경과 프레임) 증가는 ENTRY 라벨 안에 있다 [판독].
  - 단계 6 이전에는 BeforeOneBeat 조건이 참인 프레임에만 는다. 단계 6부터는 매 프레임 는다.
  - mg1801은 `Scene::GetElapsedFrame`으로 이 값을 읽는다(SyncIdleMot).
- vtable +0x328은 **`mg1801::Scene::OnRmRecieveBeatEntry @0x710000eff0`**이다 [데이터: mg1801 Scene vtable @0x7100037b40, main 기반 vtable 0x71019f1e20의 +0x328 = `RmMgSceneBase::OnRmRecieveBeatEntry`].
  - **정정:** 이전 판은 이 슬롯을 **[추정]**(이름 순서로 짐작)으로 두었다. vtable을 덤프해 [데이터]로 올린다.
- `mg1801::Scene::OnRmRecieveBeatEntry` → 기반 클래스(빈 함수) → **`ObjectManImpl::Entry(Data)`**.
- 박자는 **사운드 시퀀서에 묶여 있다**. 사운드 전역 변수 G14가 바뀌는 프레임에 줄이 나간다.
  - G14 = 마스터 시퀀스 `SQ_BGM_RC_MAIN_RHYTHM`(rc_cmn)의 countTrack이 쓰는 **마디 안 16분음표 위치 1..16**이다(24틱 = 16분음표, timebase 96) [데이터, [04_sound 5.3](../engine/04_sound.md)].
  - 그래서 `GetBeatState(1)`은 홀수 G14에서 바뀐다. BPM 120이면 8분음표 = 0.25 s = **정확히 15프레임**마다 바뀐다 [재구현 계산].
  - **정정:** 이전 판은 "전역 변수 14의 정체와 곡 시작 오프셋은 [미확정]"이라 적었다. 위 내용과 5.4 시각 표로 해소했다. 사운드 → 프레임 관측 지연은 남는다(11.2).
- 끝 조건은 Entry 인덱스(+0x37C)가 아니라 **Lock 인덱스(+0x384)**를 본다. BeforeOneBeat 때문에 mg1801에서는 Entry가 Lock보다 2줄 앞선다 [판독]. 단계 7 이후에도 남은 줄은 계속 배분된다.

### 4.1 열거형 [판독 + 데이터]

`VEGETABLE_ID`: 채보 코드 첫 글자 → 종류. 문자열 표는 `mg1801 Obj::ApplyCutBoneVisible::bone_vegetable_head_name`이다.

| 첫 글자 | ID | 이름 | 자르기 수(=차지 레인) `max_cut_counts` | 등장 x 보정 `offsetX` |
|---|---|---|---|---|
| `S` (및 아래 외 모든 글자) | 0 | tomato | 1 | 0 |
| `M` | 1 | potato | 2 | 1 |
| `L` | 2 | eggplant | 3 | 2 |
| `X` | 3 | carrot | 4 | 3 |
| `Z` | 4 | mushroom | 1 | 0 |

- `max_cut_counts = [1,2,3,4,1]` (`ObjectManImpl::SetupPhase1::max_cut_counts` @0x7100031690)
- `offsetX = [0,1,2,3,0]` (`Obj::Entry::offsetX` @0x71000316b8) [데이터]

`JUDGE_INPUT_TYPE`: 0 = JUST, 1 = FAST, 2 = SLOW, 3 = 없음(창 밖). 뼈 이름 표 `bone_judge_name = ["just","fast","slow"]` [데이터].

`CHANNEL_TYPE`: 0 = 게임 진행, 2 = 결과 캡처 (3.4) [판독].

리듬 모드(`RmGameWork+0x20`): 0 노멀, 1 롱, 2 하드, 3 리믹스 (3.2) [판독][데이터].

### 4.2 박자 계산 [판독 main]

```
GetBeatToSec(type, n)   = (60 / BPM) * n * BEAT_SCALE[type]          @0x7100425d90
GetBeatToFrame(type, n) = (int)(GetBeatToSec(type, n) * 60)          @0x7100425df0
GetBeatState(type)      = (int)ceil(G14 * (type==0 ? 0.25 : type in {1,2} ? 0.5 : 1))   @0x7100425ce0 (frintp)
GetPlayRate()           = BPM / 120                                  @0x7100425e60
BEAT_SCALE    = [1.0, 0.5, 0.5, 0.25, 0.25, 0.125]                   main @0x71015d8dc4 [데이터]
BEATS_PER_BAR = [4, 8, 8, 16, 16, 32]                                main @0x71015d8eb0 [데이터]
```

- **정정:** 이전 판은 `GetBeatState`를 절삭 `(int)(G14*0.25)`로 적었다. 디스어셈블리 `fmul` → **`frintp`(+무한대 쪽 반올림 = 올림)** → `fcvtzs`를 확인했다 [판독 main `@0x7100425d28`]. 디컴파일러가 frintp를 빠뜨린 것이다.
  - G14가 1..16이므로 타입 0은 1..4(마디 안 몇째 박), 타입 1·2는 1..8이다.
  - "상태 == BEATS_PER_BAR"는 마디 **마지막** 박·8분을 뜻한다.

mg1801이 쓰는 값(BPM 120):

| 식 | 뜻 | BPM 120 |
|---|---|---|
| `GetBeatToSec(0,1)` = t1 | 1박 | 0.5 s |
| `GetBeatToSec(0,3)` = t3 | 등장 → 판정 시점 | 1.5 s (90 f) |
| `GetBeatToSec(0,4)` = t4 | 등장 → 물에 닿음 | 2.0 s |
| `GetBeatToSec(1,1)` = tw | 판정 창 반폭, 칼질 쿨다운 | 0.25 s (15 f) |

**BPM** [판독, mg1801_rhythm.md 2절]
- mg1801은 `RmGameWork::GetBpm()`(`RmGameWork+0x30`, `@0x710042a590`)을 쓴다.
- 기본값은 RmGameWork 생성 때 모드워크 기본값 함수 `FUN_7100428720`이 넣는 **120**이다.
- `SetBpm`(`@0x710042a584`)은 main 안에서 호출되지 않는다. import하는 NRO는 `rc_stage01` 하나다.
- 그래서 미니게임 모드·파티 등 리듬 쿠킹이 아닌 경로는 **BPM 120 고정**이다.
- 리듬 쿠킹 롱 모드 후반(코스 index ≥ 게임 수/2)만 `Params.speedup_bpm`(기본 180)이 된다.
- **mg1801 단독 포팅의 원본 BPM은 120이다** [판독].
- **정정:** 이전 판은 "`ResetRmGameModeWork`가 `+0x758`에서 복사하는데 쓰는 곳을 못 찾았다, BPM 120은 가정"이라 적었다.
  - 복사는 `RestartRmGameModeWork @0x7100429490`이 한다. `Reset…`은 핸들 정리만 한다.
  - `+0x758`(백업 BPM)에 쓰는 코드는 생성자의 기본값 초기화뿐이다.
  - 그래서 120은 가정이 아니라 판독 값이다.
- mg1801 `Params.bpm`(기본 120)은 mg1801에서 읽지 않는다 [판독].

| 실행 경로 | BPM |
|---|---|
| 미니게임 모드 프리플레이, 파티 등 | 120 |
| 리듬 쿠킹 노멀/하드/리믹스, 롱 전반 | 120 |
| 리듬 쿠킹 롱 후반 | 180 (rc_stage01 Params 기본) + BGM `_B` |

### 4.7 채보 JSON [데이터 + 판독 `RmChartDataMan::ReadChartData @0x710043ecd0`]

```json
{ "1P":[{"code":""}, …], "2P":[…], "3P":[…], "4P":[…], "OBJ1":[…], "OBJ2":[…], "OBJ3":[…], "OBJ4":[…] }
```

- 키 8개를 순서대로 읽는다. 항목은 32바이트 고정 문자열로 저장한다. 줄 수 = `1P` 배열 길이(`GetDataSize`).
- 키가 없으면 다음 키가 그 열 번호를 차지한다(원본 특이점). 실채보는 8키가 모두 있어 일어나지 않는다 [판독][데이터, 02_rhythm 6.1].
- `nP` 코드: 첫 글자 = 채소(4.1), 둘째 글자 = 항상 `C`(실채보).
  - `ObjectManImpl::Entry`는 둘째 글자 − 'A'를 `Obj::Entry` 첫 인자로 넘긴다. 하지만 `Obj::Entry` 안에서는 이 값을 쓰지 않는다 [판독].
- **열 번호 = 채소가 놓이는 시작 레인**이다. `2P`의 `LC`는 레인 1~3을 차지하는 가지다.
- `OBJ1` 첫 글자가 `L`이고 `RmGameWork::IsOutLineGuideDispEnable()`이면 그 줄에 나온 채소의 외곽선 안내를 켠다.
  - `IsOutLineGuideDispEnable()` = `RmGameWork+0x20 < 2`. 노멀·롱에서 켜고 하드·리믹스에서 끈다 [판독, 02_rhythm 3.2].
  - 이 판정은 `OBJ1`만 본다 [판독 `ObjectManImpl::Entry`의 Data+0x68].
  - `OBJ2~4`와 `C`·`E` 코드는 mg1801에서 읽지 않는다 [판독]. 기반 클래스 박자 함수 3개도 비어 있다.

## 5. 상태 전이와 전체 수명

### 5.1 채소(Obj) 수명 [판독]

```
대기(active=0) ──Entry──▶ 하강(elapsed < t3) ──▶ 판정 시점 통과 ──▶ 낙하(elapsed > t3 + t1/2)
   ▲                                                                        │
   └──────────── Stop (elapsed ≥ t4 + t1) ◀── 물보라(EntrySe, elapsed ≥ t4 − 0.2) ◀┘
```

- **Entry**: 줄의 `nP` 칸에 채소가 있으면 일어난다. 풀에서 같은 종류 중 `active==0`인 첫 번째를 고른다. 없으면 그 칸은 버린다(소리 없음).
  - Entry는 장면 흐름 파이버에서 일어난다. 그래서 등장 프레임에는 Update를 받지 않고 `elapsed = 0`으로 끝난다(9.4).
- 판정(RecieveHit)은 하강·통과 단계 어디서든 창 안이면 들어온다(6.3).
- **Stop**: ObjectMan 인터페이스 +0x20(`PushResultVegetable(type, judge[])`)으로 결과를 남긴다(읽는 곳 없음, 4.4). 그 뒤 모델을 숨기고 `active=0`, `+0x184=0`으로 둔다.
  - 같은 프레임에 Stop된 Obj는 그 프레임 흐름 파이버의 Entry가 바로 다시 쓸 수 있다 [판독, mg1801_core.md 2.3].

### 5.2 플레이어 수명 [판독]

- 생성: 의자 위 (lane·2 − 3, y, −2)에 선다. `rhy_knife_idle00`을 BPM/120 속도로 재생한다.
- `inputEnabled = 1`: 채널(0,1)일 때 = 단계 2의 연습 BGM 시작(마디 A 1박). 그 전에는 MyUpdate가 입력을 보지 않고 모션 요청만 처리한다.
- 모션 전이는 `bq.nx.bea chara/mpat/mg1801_pc.mpat`를 따른다(7.1). 휘두름 중에 다시 휘두르면 swing → swing이고 a = 0이다.
- `Finish`: 채널(0,5) = 단계 7. 입력을 끄고 머리 추적을 끈다.
- `Ending`: 채널(0,6) = `OnGameEndingBefore`. 칼·의자를 숨기고 물리 애니를 켠 뒤 순간 이동한다. MapImpl이 정한 결과 위치·회전을 적용한다.

### 5.4 줄 배분과 소리의 시각 관계 [판독 + 재구현 계산, mg1801_rhythm.md 3.4]

- 마디 A = 단계 2가 시작된 마디, B = A+1 = 게임 BGM이 시작하는 마디다.
- 게임 BGM은 요청 뒤 처음 오는 마디 경계에서 시작한다(시퀀스 핸드셰이크: G13 = 18011 → 다음 마디 첫 틱에 G12 = G13) [데이터, 04_sound 5.3].

| 시점 | 일 |
|---|---|
| A 1박 | 단계 2: PracticeStart(입력 켜기), 게임 BGM 요청(SoundModule::Play — 이때 G13 = 곡 ID, FUN_7100426948), 연습 화살표 |
| A 376틱 | OP가 ENDPLAY_CHECK로 닫힘(G10=1). 다음 마디(B)부터 마스터 킥이 쉰다 [판독][재구현 계산] |
| A 1·2·3·4박 | 카운트 SE `SQ_SE_MG1800_COUNT_STICK` 4회 (3박부터 연습 화살표 숨김) |
| B 1박 | 게임 BGM 0틱, 단계 4 (PracticeFinish) |
| B 3박 | BGM L0 = 1 → IntroStart, 단계 5 |
| B 4박 (G14=13) | **채보 0번 줄** |
| B 4박 + 8분 (G14=15) | 1번 줄 |
| B+1 1박 | 단계 6: 프리셋 `mg1800_cmn`, TopStart, START 텔롭, **2번 줄** |
| 이후 8분마다 | 줄 하나씩 |

- **줄 r의 배분 시각 = B 시작 + (6 + r) × 8분음표**다. BPM 120에서 8분 = 0.25 s = 15프레임이다 [재구현 계산].
- chart00의 첫 채소는 8번 줄(B+1의 4박)이다. 판정 시점(+3박)은 B+2의 3박이다. 채소는 8줄 주기의 0·4번째(4박·2박)에 몰려 있고, 판정은 3박·1박에 온다 [재구현 계산].
- chart00(150줄)의 끝: Lock 146 = Entry 148번 줄 = B+19.25마디에서 종료 BGM을 요청한다. 종료 BGM은 B+20마디 = **BGM 시작 40.000 s 뒤**에 시작한다.
  - 원본 감상용 녹음 `SM_BGM_MG1801_DH`에서 종료 징글이 40.000 s에 시작하는 것과 맞는다 [재구현 계산 + 실행: 자체 렌더 vs 원본 녹음, 04_sound 10절].
- 마디 A가 곡 시작에서 몇 번째 마디인지(단계 0~1 와이프 길이)는 **[미확정]**이다. 줄과 BGM의 상대 관계는 A와 상관없이 위와 같다.

## 6. 계산식·조건·상세 의사코드

- 모든 시간은 초(f32)다. 프레임 변환은 `(int)(sec * 60.0)`(0 쪽 절삭)이다.
- `dt = GetDeltaTime()` = f32(1/60) 고정이다 [판독, 3.2]. 이전 판의 "dt = f32(1/60) 가정"은 판독 값이 됐다.

### 6.1 ObjectManImpl::Entry (줄 하나) [판독 @0x7100003f50]

```ts
for (lane = 0; lane < 4; lane++) {           // 1P, 2P, 3P, 4P 순서
  const code = data.player[lane];
  if (code.length === 0 || code[0] === ' ') continue;
  const type = { L: 2, M: 1, X: 3, Z: 4 }[code[0]] ?? 0;
  const obj = pool.find(o => o.type === type && !o.active);   // 풀 순서 그대로
  if (!obj) continue;
  const guide = data.obj1.length > 0 && data.obj1[0] === 'L' && rmGameWork.mode < 2;   // IsOutLineGuideDispEnable
  obj.entry(code.charCodeAt(1) - 65 /* 쓰이지 않음 */, guide, lane);
}
```

### 6.2 Obj::Entry [판독 @0x7100007bd0]

```ts
본체 모델 표시, 조각 모델 전부 표시, 조각 훅 위치 = 0, 조각 회전 = 0(사인 표 계산 결과 0)
pos = (lane * 2 - 3 + offsetX[type], 7.5, 0); 본체 엔티티 위치 = pos
rot0 = type === 4 ? (0, -π/4, 0) : (-π/2, 0, 0); 본체 회전 = rot0

perm = [0..n]; for (j = n+1; j > 1; j--) swap(perm[j-1], perm[SyncRandMod(j)])           // (2) 동기 난수 n 회  @0x71000081a8 mov w1,w21
for i in 0..n:  splashDelay[i] = F(F(perm[i] * 1.5) / 60)                                // (1)을 덮어씀  @0x710000822c (모두 f32)

```

- (1)에서 뽑은 난수 값은 바로 (2)로 덮어쓴다. 그래도 **동기 난수 소비 순서는 원본대로 남겨야 한다**.
- `SyncRandMod`의 인자는 남은 원소 수 **j = n+1, n, …, 2**다(뒤에서부터 섞는 Fisher–Yates) [판독: `core_mg1801_dis.c`].
- 동기 난수 소비는 Entry 한 번에 **(n+1) + n = 2n+1회**다. 토마토·버섯 3, 감자 5, 가지 7, 당근 9회다.
  - **정정:** 이전 판은 인자를 "k = n, n−1, …, 2", 소비를 "2n−1회"라 적었다. 이것은 코어 메모의 n(= 자르기 수 + 1)을 이 절의 n(= 자르기 수)으로 바꾸지 않고 옮긴 오기였다. 당근 9회는 코어 담당 벡터(`mg1801_entry_carrot_cuts4`, 시드 0 → splashDelay = [0.025, 0, 0.075, 0.05, 0.1] s)와 맞는다 [재구현 계산, 01_core 10절].
- 알고리즘 [판독, mg1801_core.md 3.1]: MT19937.
  - `SyncRandF()` = f32(u)·2⁻³²이다. u ≥ 0xFFFFFF80이면 반올림 때문에 1.0이 된다.
  - `SyncRandMod(k)` = (u·k) >> 32다. k < 2이면 0을 돌려주고 소비하지 않는다.
  - 시드는 장면 시작마다 새로 넣는다(3.2 3번).

`ApplyCutBoneVisible(visible, k, judgeType)`
- 뼈 이름 `"%s%d_%s%02d" % (headName[type], k, judgeName[judgeType], 0)`을 찾는다(예: `potato1_fast00`).
- 조각 k 모델에서 `SetBoneVisible(index, visible)`을 부른다.

### 6.3 판정 ObjectManImpl::JudgeInput(lane) [판독 @0x71000044d0]

```ts
const target = beatToSec(0, 3), win = beatToSec(1, 1);
for (const o of pool) {                                    // 풀 순서. "가장 가까운" 채소가 아니다
  if (!o.active) continue;
  if (!(o.lane <= lane && lane < o.lane + o.cuts)) continue;   // 디스어셈블리 조건. 넘으면 범위 검사 abort
  const k = lane - o.lane;
  if (o.judged[k]) continue;
  const diff = Math.trunc(F(target * 60)) - Math.trunc(F(o.elapsed * 60));   // + = 빨리 휘두름
  if (Math.abs(diff) > Math.trunc(F(win * 60))) continue;
  const type = Math.abs(diff) <= params.JustRangeFrame ? JUST : diff > 0 ? FAST : SLOW;   // cinc x21, x10, le
  return { type, diff, objId: o.id, vegType: o.type };
}
return { type: NONE, diff: 0, objId: 0, vegType: -1 };
```

- 반환 구조는 4.8이다.
- **같은 레인의 두 채소가 동시에 창 안에 있으면 풀 순서가 앞인 쪽이 먼저 잡힌다.**
  - 종류 번호가 작은 쪽이다. 같은 종류면 풀 번호가 작은 쪽이다.
  - BPM 120에서 8분음표 간격은 0.25 s = 창 반폭과 같다. 그래서 연속한 두 줄이 같은 레인이면 일어날 수 있다. 원본 특이점이므로 정리하지 않는다.
- 판정은 이번 프레임 `Obj::Update`가 더한 뒤의 `elapsed`를 읽는다(9.4).

재구현 계산(BPM 120, dt = f32(1/60) 누적, JustRangeFrame 5) [재구현 계산, `analysis/mg1801_calc_bpm120.json`]. "등장 후 f 프레임"은 등장 프레임 N 다음의 N+f 프레임이다. 그 프레임에서 Update를 f번 받은 뒤 판정한다.

- UpdateCpu는 반환값 중 x0(type, diff)만 쓴다 [판독].
- CpuMiss가 꺼져 있으면 계획 값 자리에 `CpuMiss` 바이트 자체(0 = JUST)를 비교한다(레지스터 재사용). 결과는 위 식과 같다 [판독].
- `RandMod(k)`(비동기) = libc++ `uniform_int_distribution(0,k−1)` 기각 표본이다. k < 2이면 0이다 [판독, mg1801_core.md 3.1].
- 비동기 엔진 상태는 부팅 이후 소비 이력을 따른다. 그래서 **원본의 CPU 실수 위치는 재현할 수 없다**. 웹은 시드로 정한다.
- 기본(CpuMiss = 0)이면 CPU는 항상 JUST를 노린다. 판정 시점 diff ≤ 1인 첫 프레임에 휘두른다(BPM 120에서 등장 후 90프레임) [재구현 계산].
- 원본 특이점:
  - 계획 길이는 레인0의 자르기 수다.
  - `cpuNoteIndex`는 "창에 들어갔다 나간 횟수"다. 그래서 실제 채소 수와 어긋날 수 있다.
  - CpuMiss가 켜져 있으면 범위 밖 읽기가 생길 수 있다. 기본값에서는 일어나지 않는다.

### 6.8 조각 분리·회전 Obj::CutObj [판독 @0x71000095f0]

- `CutRotEnable`이고 `cutRotState==0`이며 `elapsed ≥ t3 + tw`이면 한 번만 다음을 한다.
  - JUST로 잘린 자리 k마다 이웃 조각 2개의 회전 방향을 정한다. 가운데보다 왼쪽이면 +1, 오른쪽이면 −1을 `pieceRotDir`에 더한다(조건식은 원본 그대로).
  - 그 밖의 자리는 0으로 둔다.
- 매 프레임 JUST 자리 k마다 조각 i ≤ k는 −0.4, i > k는 +0.4를 x 속도로 더한다. 결과로 `훅.x += dt × 속도`.
- `pieceAngle[i] += dt × pieceRotDir[i] × CutRotSpeed`(도)를 Z축 쿼터니언으로 만든다. 본체 회전의 켤레와 곱해 훅 회전으로 넣는다.
- **FAST·SLOW 자리는 조각이 갈라지지 않는다** [판독, 원본 그대로].

### 6.9 물보라 Obj::EntrySe [판독 @0x7100009060]

### 6.10 외곽선 안내 Obj::UpdateOutlineOnOff [판독 @0x7100008e40]

- 전역 `sm_outline_place[4]`(레인 점유)를 쓴다. Obj 생성자가 0으로 지운다.
- 범위 = `OutlineAloneSize2 && cuts ≥ 2 ? 레인 0..3 전체 : lane..lane+cuts−1`
- 켜기(true): 범위가 모두 비어 있을 때만 점유하고 외곽선을 표시한다.
- 끄기(false): 점유를 풀고 숨긴 뒤 `outlineGuide = 0`으로 둔다.
- 켜는 조건(Entry의 guide)은 `OBJ1 = 'L'` 줄이고 모드 < 2(노멀·롱)일 때다(4.7).

## 8. 다른 기능과의 상호작용

- **박자 ↔ 오디오**: 시계가 둘이다.
  - 줄 배분은 마스터 시퀀스가 쓰는 G14가 바뀌는 프레임에 일어난다(3.3).
  - 채소 이동은 고정 dt 누적이다(6.4).
  - 게임은 G11(BPM)을 쓰고, G12(현재 곡)·G14(16분 위치)를 읽는다. G13·G10은 시퀀스끼리 주고받는다(04_sound 5.4).
  - G14는 사운드 스레드 틱에서 바뀌고 게임은 60 Hz 프레임에서 읽는다. 그래서 등장 프레임이 흔들릴 수 있다. 등장 뒤 움직임은 dt로 간다. 관측 지연의 크기는 **[미확정]**이다.
- **웹 구현(박자 원천)**: 원본처럼 게임이 사운드를 읽는다. 페이지가 스텝마다 그 스텝 시각(오디오 출력 시각 기준)의 G12·G13·G14와 렌더 BGM 핸들 L0을 로직에 넘기고, 단계 2·3·4·6·7은 RmSoundMan 함수대로(FUN_7100426948 요청 시 +0x38 = G12, FUN_7100426b8c 접수 = G14≠16 && G12≠+0x38, FUN_7100426c2c L0==1, FUN_71004269d8/FUN_7100426d24 종료 BGM) 판정한다 [판독]. 관측이 없으면 같은 값을 프레임으로 계산한다. **정정:** 이전 웹은 박자를 자기 프레임 수로 세고 루프가 밀린 시간을 버려, 실측으로 소리보다 0.6~0.7 s 늦고 부하 때 BGM이 한 마디 어긋났다 [실행: tools/sync_measure.ts].
- **입력 차단**: `inputEnabled`가 0이면 휘두름도 CPU도 돌지 않는다. 연습 시작(단계 2) 전과 Finish(단계 7) 뒤가 그렇다. 단계 7 이후에도 남은 줄은 배분되므로, 마지막 채소들은 입력 없이 지나간다 [판독].
- **같은 프레임 순서**: Stage → ObjectMan → PlayerMan → 장면 흐름(9.4) [판독].
  - 판정은 이번 프레임 증가 뒤의 `elapsed`를 읽는다.
  - Player는 흐름 파이버보다 먼저 돈다. 그래서 `SyncIdleMot`는 **앞 프레임까지 센 경과 프레임**을 읽는다.
  - 입력 샘플을 언제 갱신하는지(InputModule 타이밍)는 **[미확정]**이다.
- **풀 고갈**: 같은 종류가 15개 넘게 살아 있으면 새 채소를 버린다. 실채보 최대 동시 수는 토마토·버섯 10이라 일어나지 않는다 [재구현 계산].
- **결과**: 수프·징글·PERFECT는 모두 상태 점수(6.6)로 정한다. `PushResultVegetable`로 쌓은 목록은 아무도 읽지 않는다 [판독].
- **사운드 프리셋**: 장면 단계마다 라벨 치환표가 바뀐다(7.2). 웹은 같은 치환표를 단계에 맞춰 바꾼다.
- **일시정지**: 단계 7에서 UI 일시정지를 막는다. 일시정지 중 시퀀스가 멈추면 G14도 멈춘다 [추정, 04_sound 8절].

### 9.4 초기화와 업데이트 순서 (한 step)

원본 순서 **[판독: 코어 담당, [mg1801_core.md 2절](../../../analysis/notes/mg1801_core.md)]**:

0. 프레임 시작: `dt = F(1/60)`
1. Stage 파이버: `MapImpl::Update`(Wait만)
2. ObjectMan 파이버: Obj 풀 순서대로 `update`
3. PlayerMan 파이버: Player 0~3 `myUpdate` (입력 → 판정 → RecieveHit)
4. 장면 흐름 파이버: `OnGameMain` 단계 처리 → 꼬리(Lock → 박자 바뀌었으면 채보 한 줄 → `objectMan.entry(row)` → `elapsedFrame++`)

- 근거: 제품 셋과 흐름 파이버는 모두 우선순위 0이다. 제품은 `OnStartUpdate`에서, 흐름 파이버는 다음 프레임 첫 `UpdateMain`에서 등록된다. 실행 목록은 안정 정렬이다.
- 3과 4 사이에 `OnStartUpdate`가 만든 0x40 B 파이버가 하나 더 돈다. 하는 일은 **[미확정]**이다.
- **정정(이전 갱신):** 처음 판은 순서를 "박자 → elapsedFrame → PlayerMan → ObjectMan"으로 적었는데, 원본과 반대였다.
  - 판정은 이번 프레임 `Obj::Update` 뒤의 `elapsed`를 읽는다.
  - 이번 프레임에 등장한 채소는 다음 프레임부터 갱신된다.
  - 6.3 판정 프레임 표는 이 순서에서 그대로 성립한다.
  - 웹 회색 박스는 이 순서로 고쳤다(`logic/game.ts`).
