## 1. 기능 개요와 사용자에게 보이는 동작

4인 협력 리듬 미니게임이다. 무대 앞쪽에 플레이어 4명이 한 줄로 서서 스푼을 들고 있고, 맞은편(화면 안쪽)에 펭귄 4마리가 레인마다 한 마리씩 서 있다. 가운데에 파르페 유리컵이 천천히 돈다.

- 펭귄이 박자에 맞춰 과일(재료)을 집어 들고 자기 레인의 플레이어에게 던진다.
- 플레이어는 Joy-Con을 세로로 쥐고 과일이 눈앞에 왔을 때 휘둘러 스푼으로 받아친다. 받아친 과일은 큰 포물선을 그리며 유리컵 안으로 들어가 쌓인다.
- 판정은 JUST·FAST·SLOW 세 가지다. JUST면 정해진 자리에 예쁘게 쌓이고, FAST·SLOW면 어긋난 자리(`_err` 뼈)에 쌓인다. 놓친 과일은 플레이어 뒤로 날아가며 사라진다.
- 점수는 JUST 2점, FAST·SLOW 1점, 놓침 0점이다(공용, 6.7).
- 던지는 방식이 넷이다(채보 `S0`~`S3`): 살짝 튀는 기본, 직선(빠름), 높은 포물선, 바운드. 비행 시간도 셋이다(채보 `T2`·`T4`·`T8` = 8분음표 2·4·8개).
- 빠른 공(`T2`), 바운드 공(`S3`), 마지막 장식(`K7_*`)은 펭귄이 던지기 전에 몸을 돌리거나 흔드는 예고 동작과 `SQ_SE_MG1802_ROLL` 소리를 낸다. 나머지는 `SQ_SE_MG1802_PICK`이다(5.2).
- 채보의 `SC` 줄에서는 휘핑크림 층이 하나 올라간다(최대 4층).
- 마지막 결과: 팀 달성률에 따라 완성 파르페 모델 `ed_obj00`(별 3) / `ed_obj01`(별 2) / `ed_obj02`(별 1) 중 하나가 나온다(별 0이면 없음). 결과 징글은 공용 규칙(별 2 이상 GOOD)이다.

## 3. 진입점과 전체 호출 흐름

### 3.1 클래스 구성 [판독]

mg1801과 달리 "MaintainProduct" 묶음이 아니라 **`Mg1802Sequence`가 매니저 7개를 소유**하고, 상태 번호(STATE)를 한꺼번에 알린다.

```
mg1802::Scene : ca::rm::RmMgSceneBase                 장면(+0x480 = Mg1802Sequence*, +0x478 = Entry 횟수, 읽는 곳 없음)
  └ Mg1802Sequence (싱글턴) → Impl(Fiber, 0x70 B)
      +0x10 Mg1802InfoManager     채보 해석(NOTE_INFO), 시간 누적, JUST 소리 콤보, 레인 "끝" 표시
      +0x18 Mg1802StageManager    무대·유리컵(회전·쌓기 뼈)·크림·배경 펭귄·준비 안내·결과 모델
      +0x20 Mg1802CameraManager   env/post/dirlight 모델, 카메라 모션
      +0x28 Mg1802PlayerManager   PLAYER ×4 (휘두름 입력·CPU·텔롭·점수)
      +0x30 Mg1802NpcManager      Mg1802NpcModel ×4 (던지는 펭귄)
      +0x38 Mg1802ParfaitManager  INGREDIENT ×N (재료 비행·판정·착지) + SHADOW ×8
      +0x40 Mg1802EffectManager   파티클 6종
      +0x50 vector<Mg1802ObjectBase*>  = [Stage, Camera, Player, Npc, Parfait, Effect] (Info 는 빠짐)
      +0x48 현재 STATE, +0x68/+0x69 1회 플래그(util::CheckOne)
```

- 모든 매니저는 싱글턴(`bq::SingletonTemplate<T>::m_InstancePtr`)이다. 서로 전역으로 부른다.
- `Mg1802ObjectBaseImpl::SetState(n)` @0x710000a038은 `+8 = n`을 쓰고 vtable `+0x10 + n·8` 슬롯을 부른다 [판독]. 슬롯 순서는 PlayerManager::Impl vtable(`0x71000450a8`) 덤프로 확인했다 [데이터]:

| STATE | 슬롯 이름 | 부르는 곳 | 덮어쓰는 매니저 |
|---|---|---|---|
| 0 | Setup | `Impl::Setup` (매니저 생성 직후) | Stage(Create), Npc(NpcModel×4 Create), Player(PLAYER×4 생성), Camera, Parfait(빈), Effect |
| 1 | PostSetup | 같은 곳 | Stage(크림 쌓기·회전 초기값·배경 이펙트), Npc(펭귄 훅·PlayerID), Player(StartHook), Parfait(INGREDIENT 생성) |
| 2~7 | Initialize, StartOpeningDemo, SkipOpeningDemo, PreStartTelop, StartGame, StartRound | 부르지 않음 | — |
| 8 | StartPlayer | `TrigRmGameMainBgmPracticeStart`(1회) | Player(입력·CPU 켜기, ResetCom) |
| 9 | EndPlayer | `TrigRmGameMainChartEnd` | Player(입력 끄기) |
| 10, 11 | EndRound, StartFinish | 부르지 않음 | — |
| 12 | StartCapture | `TrigRmGameResultCaptureSetting` | Camera(`captureLong`/`captureNormal`), Stage(회전 0·결과 모델), Player(결과 위치) |
| 13 | StartResult | `TrigRmGameEndingSetting` | Camera(`result`), Stage(결과 회전·배경 펭귄 환호·결과 모델), Player(결과 위치), Npc(환호 모션) |

### 3.2 준비 단계 [판독]

1. `Scene::Scene @0x71000101d8`
   - `RmMgSceneBase` 생성자(공용: 아카이브 `mg/mg1800`·`libca/mg_common`, 모션 `rhy`·`rc`, 사운드 `subarc_rc_cmn`, **Fixed60**) [판독, 02_rhythm 3.1].
   - `util::SetScene(this)`(전역 장면 포인터).
   - NPC 아카이브를 싣게 한다: `LoadSceneNonPlayerCharacter(0x16, 0, 1)`, `(0x4E, 0, 1)`.
     - NonPlayerCharacterID 0x16 = 22 = **PENGUIN** → `chara/npc011`(`npc011_penguin.fmdb`), 0x4E = 78 = **KOPENGUIN** → `chara/npc091` [데이터: `bq.nx.bea common/data/characterlist.json` NPCCharacterData[22]·[78]].
2. 공용 `SetupGame`·`SyncedSetupGame`이 돈다(02_rhythm 5.1, mg1801 3.2와 같다).
3. `SyncedSetupGame` 가운데 vt+0x2A0 = **`Scene::RmSyncedSetupGame @0x7100010520`** [판독 디스어셈블리 `_dis3.c`]:
   1. `RmPracticeArrowMan::SetMgCustomizeModel("mg/mg1802/model/mg1802_arrow00")` — 연습 화살표 모델을 게임 전용으로 바꾼다.
   2. `Scene::SetupRhythm @0x71000105e8`:
      - `SetMainBeatType(1)`(채보 한 줄 = 8분음표).
      - `SetMainBgmName("SM_BGM_BDCN001_TEST_JMP")`(저장만, 재생 안 함 — mg1801 3.2 정정과 같다).
      - `SetGameBgmName(Params+0x21 ? "SQ_BGM_RC_GENERIC" : "SQ_BGM_MG1802_A")`. **Params+0x21은 이름이 `isBeat`인 디버그 bool**이다(getter 이름 `IsDebugBeat`). mg1801의 `isGenericBgm`과 자리·이름이 다르다 [판독].
      - `SetGameBgmFinName("SQ_BGM_MG1802_MG_ENDING")`.
      - `RmChartDataMan::ReadChartData(GetChartJson())`(3.3).
      - `RmUiStatusMan::SetStatusType(2)`.
   3. `SetNextChartDataOffset(2)` → `RmMgSceneBase+0x428 = 2`. **NextEntry 훅이 2줄 앞의 줄을 받는다** [판독 `mov w1,#0x2` @0x7100010564].
   4. `Mg1802Sequence` 생성 → `Mg1802Sequence::Impl::Setup @0x71000115c0`:
      - `Mg1802InfoManager` 생성 → `InfoManager::Setup` = `Impl::SetupNoteInfo`(6.1, 채보 해석·총점·개인 횟수).
      - Stage, Camera, Player, Npc, Parfait, Effect 순서로 생성하고 목록 +0x50에 넣는다.
      - 목록 전부 `SetState(0)`, 이어서 전부 `SetState(1)`. `+0x48 = 1`.
   5. `RmUiStatusMan::SetStarTotalScore(InfoManager::GetMaxScore())` [판독 `_dis3.c` `@0x71000105c8`].
- `SetMgBgmBeforeOneBeatStart`를 **부르지 않는다**(`+0x420 = 0`) [판독: 호출 지점 없음, `rhythm_mg1802_callsite.c`]. 그래서 줄 배분은 단계 6(TopStart)부터다(3.4).
- 공용 `SyncedSetupGame`이 돌아온 뒤 채보 경로에 `"chart01."`이 있으면 `+0x470 = 1`(BGM `_C`), `G11 = GetBpm()` [판독, 02_rhythm].

| `RmCleanupGame`(vt+0x2A8) | Sequence 삭제 | `@0x7100010710` |

- OnGameMain 꼬리의 반환값이 참이면 MinigameFlow가 9 → 10(OnGameEnd)으로 넘어간다(SHARED.md [mgC] 처리기 표). mg1802가 항상 0을 돌려주므로 게임은 단계 10의 직접 반환으로만 끝난다 [판독].
- `Mg1802Sequence::GameFinish @0x7100011e20`(STATE 9)는 호출자가 없다 [판독: 전수 검색].

### 3.5 한 프레임 안 순서 [판독(생성 순서) + 추정(mg1801 규약 적용)]

`bex::Fiber::Fiber(prio 0)`가 생성 때 등록하고, 실행 목록은 우선순위 안정 정렬이다 [판독, 01_core 5.4·mg1801_core 2절]. mg1802의 파이버 생성 순서는 다음과 같다 [판독: 생성자 호출 순서].

```
0. 프레임 시작: dt = f32(1/60)
1. Mg1802Sequence::Impl::Update         Wait 만
2. Mg1802InfoManager::Impl::Update      time(+0x40) += dt
3. Mg1802StageManager::Impl::Update     유리컵 회전, 크림 층 흔들림 카운트, 배경 펭귄 박자 맞춤
4. Mg1802CameraManager::Impl::Update    Wait 만
5. Mg1802PlayerManager::Impl::Update    PLAYER 0..3: 휘두름 입력 → CheckHit → Hit / CPU
6. Mg1802NpcManager::Impl::Update       NpcModel 0..3: 예고 동작, 들기, 던지기(Throw)
   (NpcModel ×4 도 Fiber 파생이라 생성 때 등록되지만 vt+0x20 Update 가 루프가 아니어서 첫 실행 뒤 끝난다 [판독+추정])
7. Mg1802ParfaitManager::Impl::Update   INGREDIENT 순서대로 elapsed += dt → move(판정 반응·놓침·착지), 그림자
8. Mg1802EffectManager::Impl::Update
9. 장면 흐름(FiberLite): OnGameMain 단계 처리 → 꼬리(Lock → Entry(Action) → NextEntry(Ready))
```

- 흐름 파이버가 매니저보다 뒤라는 것은 mg1801과 같은 생성 시점(OnStartUpdate → SyncedSetupGame) 근거다 [추정: mg1801_core 2절 규약을 그대로 적용, mg1802 실행 순서 직접 관측 없음].
- 결과: **Player가 Parfait보다 먼저 돈다.** 휘두른 프레임의 판정은 *앞 프레임까지* 누적된 재료 elapsed로 한다(6.4). mg1801(Obj가 Player보다 먼저)과 반대다.

### 6.1 채보 해석 `Mg1802InfoManager::Impl::SetupNoteInfo @0x7100007c20` [판독 + 디스어셈블리 `_dis1.c`]

`GetItemStr(row, col)` 인자 순서는 디스어셈블리로 확인했다(`w1 = 줄`, `w2 = 열`).

```ts
const size = chart.size;                      // 1P 열 길이
info.totalBeatNum = size;
setupRotate();                                // 6.9
stackIngredient();                            // 아래
let maxScore = 0, slot = info.stackNum, counts = [0,0,0,0];
if (size >= 5) for (let r = 4; r < size; r++) for (let c = 0; c < 5; c++) {   // 1P,2P,3P,4P,OBJ1. 줄 0..3 은 머리말
  const code = chart.item(r, c);
  if (code.length === 0 || code[0] === ' ') continue;
  if (c < 4) counts[c]++;                     // 형식이 틀려도 센다
  const lane = c < 4 ? c : -1;
  const type = findFirst(code, INGREDIENT_TABLE) ?? -1;
  if (type === 11) { notes.push({ row: r, lane, type, throwType: -1, speed: -1, slot: -1 }); continue; }   // SC: 점수 없음, 칸 없음
  maxScore += 2;
  notes.push({ row: r, lane, type,
               throwType: code.length > 1 ? (findFirst(code, THROW_TABLE) ?? 0) : 0,
               speed:     code.length > 1 ? (findFirst(code, SPEED_TABLE) ?? 0) : 0,
               slot: slot++ });
}
info.maxScore = maxScore;
for (const n of notes) n.single = notes.filter(m => m.row === n.row && m.type >= 0 && m.type < 11).length === 1;
players.forEach((pw, i) => statusMan.setPersonalPlayNum(pw.playerId, counts[i]));   // 플레이어 목록 순번 i
```

- `findFirst(code, TABLE)` = 표 순서로 `code.includes(key)` 인 첫 항목(원본 `std::string::find`). 그래서 `L_K7_00…`의 `K7_00`은 `K0`보다 뒤에서 찾지만 `K0`이 부분 문자열이 아니라 문제없다.
- **채보 코드의 `L_`/`R_` 접두는 읽지 않는다** [판독: 해석기는 `K`·`S`·`T` 조각만 찾는다]. 접두의 뜻(던지는 손 등)은 원본 동작에 영향이 없다.
- **OBJ2~OBJ4 열과 줄 4 이후의 OBJ2 값(chart00 줄 4 `2`, chart01 줄 4 `17`)은 아무도 읽지 않는다** [판독: `GetItemStr` 호출은 SetupNoteInfo·SetupRotate·StackIngredient 셋뿐].
- OBJ1 열(`lane = −1`)에 SC가 아닌 코드가 오면 점수에 들어가지만 던져지지 않는 재료가 생긴다(원본 특이점). 실채보 OBJ1은 `SC`뿐이다 [데이터].
- 종류를 못 찾은 코드(type −1)는 점수·칸 번호를 받지만, INGREDIENT 목록은 `type < 11`을 **부호 없는** 비교로 걸러서(−1 제외) 그 뒤 칸 번호가 한 칸씩 어긋난다(원본 특이점) [판독 `GetListIngredientType @0x7100007250`]. 실채보에는 없다 [재구현 계산 `unknownType = []`].

`StackIngredient @0x71000084c0` — 줄 0..3, 열 쌍 (0,1)·(2,3):

for (let r = 0; r < 4; r++) for (const c of [0, 2]) {
  const t = findFirst(chart.item(r, c), INGREDIENT_TABLE); if (t === undefined) continue;

## 8. 다른 기능과의 상호작용

- **박자 ↔ 프레임**: 노트 시각은 공용 G14 줄 배분이 정하고, 그 뒤 투척·비행·판정은 dt 누적이다(mg1801 과 같은 두 시계). 사운드 → 프레임 관측 지연은 공용 미확정.
- **같은 프레임 순서**(3.5): Npc(던짐) → Parfait(elapsed) → 흐름(Ready). Player 는 Parfait 보다 먼저라서 휘두른 프레임 판정은 앞 프레임 elapsed 를 쓴다. 던진 프레임에는 Parfait 가 이미 한 번 갱신한다.
- **입력 차단**: STATE 8 전·STATE 9 뒤에는 사람·CPU 모두 판정하지 않는다. 판정 창 밖에서 휘둘러도 모션은 나오고 쿨다운도 걸린다(다음 16프레임 입력 무시) [판독].
- **겹친 노트**: 같은 레인 노트는 칸 순서가 앞선 것이 먼저 잡힌다(5.3). 같은 레인에서 2줄 안에 다시 Ready 되면 앞 노트가 사라진다(6.2) — 실채보에는 없다.
- **놓친 장식**: 다음 장식의 쌓는 자리를 바꾼다(6.8).
- **JUST 콤보**: 레인 "끝" 표시가 네 레인 모두 찰 때까지 이어진다(6.10). 놓침도 레인 끝으로 센다.
- **모드**: 노멀·롱만 준비 안내(6.2)를 보인다. 하드는 chart01 + BGM `_C`, 리믹스는 리믹스 채보 + 미리 쌓기·채보 회전값.
- **결과**: 별 판정 → 결과 모델·징글(6.12).
