## 1. 기능 개요와 사용자에게 보이는 동작

4인 협력 리듬 미니게임이다. 플레이어 4명이 의자 위에서 꼬치를 들고 한 줄로 서 있다. 멀리 구름 위 김수한무(Lakitu, NPC `JUGEMU`) 4마리가 박자에 맞춰 재료를 던진다. 재료가 눈앞(판정 지점)에 왔을 때 Joy-Con을 세로로 쥐고 찌르면 꼬치에 끼워진다.

- 재료는 칸(레인)을 1·2·3·4칸 차지한다. 2칸 이상 재료는 걸친 플레이어가 각자 한 번씩 찌른다(6.5).
- 판정은 JUST, FAST(빠름), SLOW(늦음) 세 가지다. 점수는 JUST 2점, FAST·SLOW 1점, 놓침 0점이다(6.7).
  - 판정 창은 BPM 120에서 판정 시점 ±7프레임, JUST는 ±3프레임이다. mg1801(±15, JUST ±5)보다 좁다(6.5).
  - FAST·SLOW로 찔러도 재료는 꼬치에 끼워진다. 놓친 재료는 땅에 떨어진다.
- 채보의 재장전 표시(`R`)가 오면 모두 꼬치를 접시(헤이호가 든 판)로 던지고 새 꼬치를 든다. 재장전 동안은 찌를 수 없다(6.6).
- 판정 순간에는 판정 SE, JUST면 `SQ_SE_MG1803_JUST_LAYER`와 BGM 코드에 맞춘 JUST 아르페지오(`SQ_SE_RC_JUST` → 프리셋으로 `SQ_SE_MG1803_JUST_SOUND`)가 겹친다(7.2).
- BGM은 40초 곡 한 번이다(20마디, 반복 없음). 끝나면 종료 징글과 결과 연출(구이 장면, 불 이펙트)로 넘어간다. 결과 징글은 별 판정 2 이상이면 GOOD, 아니면 BAD다(공용, [mg1801 6.6](mg1801.md)).

### 3.2 준비 단계

1. `Scene::Scene @0x7100012d7c` [판독]
   - `RmMgSceneBase` 생성자: 공용 아카이브·Fixed60 등([mg1801 3.2](mg1801.md)).
   - NPC 적재: `LoadSceneNonPlayerCharacter(0x1A,0,1)` = NPC 26 **JUGEMU**(`chara/npc017`), `(5,0,1)` = NPC 5 **HEYHO**(`chara/npc002`) [판독][데이터: characterlist.json NPCCharacterData].

2. 기반 `SetupGame`·장면 상태 8의 동기 난수 시드는 공용과 같다([mg1801 3.2](mg1801.md) 2·3번).

### 3.5 한 프레임 안의 순서 [추정: 01_core 5.4·mg1801_core 2절 규칙을 mg1803 생성 순서에 적용]

- `bex::Fiber` 생성자가 파이버를 대기 목록에 넣고, 같은 우선순위(0)는 안정 정렬로 생성 순서대로 돈다 [판독, 01_core 5.4].
- mg1803의 생성 순서 [판독 RmSyncedSetupGame]: StageMan → NpcMan → Jugemu ×4(NpcMan 생성자) → ObjsMan → PlayerMan → 헤이호 ×4(NpcMan.SetupGame의 SlidePlate) → Player ×4(PlayerMan.SetupGame) → (다음 프레임 상태 9에서) 장면 흐름.
- Jugemu·헤이호 파이버의 본체(vt+0x20)는 루프가 없어서 첫 재개에서 끝난다. 이후 Jugemu::Update는 NpcMan 파이버가 함수로 부른다 [판독: Jugemu vtable +0x20 = `Mg1803NpcJugemu::Update`(Wait 없음), 헤이호 +0x20 = 빈 `bex::Fiber::Update`].

| 순서 | 주체 | 하는 일 |
|---|---|---|
| 1 | StageMan | Wait만 |
| 2 | NpcMan `@0x71000045c0` | Jugemu 0~3 `Update`, SlidePlate 0·1 `Update`, 박자 타이머 `+0x18 += dt` |
| 3 | ObjsMan `@0x7100007590` | `+0x20`(갱신 켬)이면 Obj 0..n−1 `Update`, `UpdateJustLineOp` |
| 4 | PlayerMan | Wait만 |
| 5 | Player 0~3(레인 순) `@0x710000f010` | 상태 함수(OnMove) → Kusi 0~15 `UpdateKusi` |
| 6 | 장면 흐름 | OnGameMain → 줄 배분 → Entry/Lock 훅 |

- 결과: 판정은 이번 프레임 `OnThrow`가 더한 뒤의 비행 시간 `t`를 읽는다. 줄이 배분된 프레임에는 Jugemu가 아직 돌지 않았다(다음 프레임부터 지연 감소).
- 이 순서는 등록 함수(`FUN_710018e68c`)를 mg1803에서 직접 추적하지 않았으므로 **[추정]**이다. 순서가 다르면 6.3의 프레임 수가 ±1 달라진다.

## 5. 상태 전이와 전체 수명

### 5.1 재료(Obj) 수명 [판독]

```
대기(active 0, 숨김) ──Entry(줄 배분)──▶ 손에 들림/머리 위(Jugemu) ──ThrowCountdown──▶ 커짐(0.5→1.0)
   ──카운트다운 ≤ 0: Throw──▶ 비행(t 0→2 s, 판정 대상) ──찔림: RecieveHit──▶ 꼬치에 끼움(hooked)
                                     │                                      └ 재장전 → Kusi 비행 → 접시 → 미끄러져 나감(x > 16) → RemoveHook(숨김)
                                     └ 안 찔림: t ≥ 2 s 뒤 낙하, t > 4 s(GetBeatToSec(1,16)) → 숨김, active 0
```

- 판정 대상 기간: `active && target[lane] && !hit[lane]`인 동안 모두 목록에 든다. 판정 창 밖에서도 목록에는 있다(CPU 조건이 이를 쓴다, 6.8).
- 넓은 재료는 레인마다 `hit[lane]`이 따로다. 첫 레인이 찌르면 그 꼬치에 끼우고, 다음 레인들은 꼬치 끝 위치만 맞춘다(RecieveHit 두 번째 분기) [판독].
- `OnRmGameEnd` → `ObjsMan.GameEnd`가 모든 Obj를 숨기고 상태 함수를 비운다.

### 5.2 Jugemu 수명 [판독 `Ready @0x7100006d08`, `Update @0x71000047f4`, `NextAnim @0x7100004d88`]

```
idle 모션(박자 위상 맞춤) ──Ready(줄 배분 프레임)──▶ 지연 delay = GetBeatToSec(0,1) − 0.36666667 (+ rate>1.1 이면 0.26666668/rate)
  ──delay ≤ 0──▶ throw 모션 재생(속도 playRate) ──애니카운터 ≥ 6──▶ 놓기: ThrowCountdown(0.26666668/rate)
  ──애니카운터 ≥ 22──▶ active 0 ──모션 끝──▶ idle(NextAnim, 위상 맞춤)
```

- 놓기 순간 재료 처리: 손에 드는 재료(type < 3)는 `HookThrow`로 Jugemu `attach_R_hand`에 x 보정만큼 붙인다. 넓은 재료는 Jugemu 위치 + (0, 1.5, 0)에 놓는다 [판독 `Update @0x71000048d0~`].
- `dummy`이면 모션만 하고 ThrowCountdown을 부르지 않는다. 넓은 재료의 오른쪽 레인 Jugemu가 이렇게 같이 던지는 시늉을 한다.
  - 원본 특이점: N(3칸)은 lane+1만 dummy이고 lane+2는 움직이지 않는다. F(4칸)만 +2·+3까지 dummy다 [판독 Obj::Entry].
- `Ready`가 다시 불리면 (활성이고 dummy가 아니고 앞 재료가 손에 드는 종류이면) 앞 재료의 훅을 떼고(RemoveModelHook) 처음부터 다시 시작한다. 놓기(Entry+14프레임) 전에 다음 Ready가 오면 앞 재료는 던져지지 않는다. 실채보는 같은 레인 간격이 최소 2줄(30프레임)이라 일어나지 않는다 [재구현 계산].
- 찔린 레인의 Jugemu는 `NpcJoy` → `Just()`: 지금 모션이 `idle`이면 `joyful`을 한 번 재생한다 [판독 `@0x7100006df8`].

### 5.4 꼬치(Kusi) 수명 [판독 요약]

- `SetThrow(objs, coop)`: 끼운 재료 목록을 복사하고 목표 거리를 정한다. 협동(넓은 재료를 같이 찌른 꼬치가 있음)이면 같이 찌른 다른 레인 꼬치들을 `mg1803KusiLink`로 묶는다.
- `OnThrow`: 중력(9.8·2·BPM/120)으로 접시까지 날아간다. 착지(y < −1.4 기준)에 `SQ_SE_MG1803_FOOD_LAND`, `NpcMan.SetCushion`(접시 0.1 s 출렁임). 착지 뒤 `GetBeatToSec(1,2)`(0.5 s) 지나면 `NpcMan.SetSlide`(접시가 오른쪽으로 나가고 왼쪽 접시가 들어옴). x > 16이면 끼운 재료를 `ObjsMan.RemoveHook`으로 숨긴다.
- SlidePlate: 가운데 접시는 상태 4로 나가 x ≥ 15에서 왼쪽 대기(2)가 되고, 왼쪽 접시는 상태 3으로 들어와 x ≥ 0에서 가운데(1)가 된다. `PlayerMan.IsLast()`면 왼쪽 접시가 들어오지 않는다 [판독 `SetPlateSlide @0x7100006c4c`, `Update @0x7100006e80`].
- 이 부분의 세부 좌표·속도 식은 웹 연출용이다. 판정·점수와 무관하다. 구현할 때 `rcA_mg1803_dis3.c`의 Kusi::OnThrow를 다시 읽는다 **[판독: 요약만, 세부 식 미정리]**.

### 5.6 줄·던짐·판정 시각 (BPM 120) [재구현 계산 `analysis/rcA_mg1803_calc.json`]

B = 게임 BGM이 시작하는 마디(공용 [mg1801 5.4](mg1801.md)). 프레임은 B 시작 = 0 기준이다.

| 일 | 프레임 |
|---|---|
| 줄 r 배분(Entry) = E | 90 + 15r (= B + (6+r)·8분) |
| Lock 줄 r(재장전 `R` 처리) | 120 + 15r |
| Jugemu 던지기 모션 시작 | E + 8 |
| 재료 놓기(ThrowCountdown) | E + 14 |
| Obj::Throw(비행 시작, t = dt) | E + 30 |
| 판정 중심(moveFrame 처음 ≥ 120, d = 0) | **E + 150 = 줄 r + 10의 배분 시각** |
| JUST(\|d\| ≤ 3) | E + 147 ~ E + 153 (7프레임) |
| FAST(4 ≤ d ≤ 7) | E + 143 ~ E + 146 (4프레임) |
| SLOW(−7 ≤ d ≤ −4) | E + 154 ~ E + 157 (4프레임) |
| 재료 숨김(안 찔림) | t > 4 s → 대략 E + 270 |

- 설계상 "줄 배분 → 1박 뒤 던짐 → 1마디(2 s) 비행 → 판정"이다: 지연 0.1333 s + 모션 6/60 s + 카운트다운 0.2667 s = 0.5 s(1박) [재구현 계산].
- 프레임으로는 던짐이 E+30(=1박)에 정확히 맞는다. f32 누적 때문에 Jugemu 지연은 8프레임, 카운트다운은 17번째 감소에서 ≤ 0이 된다.
- `moveFrame`은 f32 누적이라 한 프레임에 1씩만 늘지 않는 곳이 있다(`move_frame_step_always_1: false`). 그래도 JUST 7·FAST 4·SLOW 4프레임이다.

**별 판정·결과 징글·PERFECT**는 공용 그대로다(rate ≥ 80 → 3, ≥ 40 → 2, > 0 → 1; 징글 judge > 1이면 GOOD) [02_rhythm 8.2·8.3](../engine/02_rhythm.md). mg1803 결과 무대는 별 판정에 따라 바뀌지 않는다(StageMan·ObjsMan SetResult가 GetStarAchieve*를 부르지 않는다) [판독: 게임 디컴파일 전수 검색].

기대값: chart00에서 4명 모두 모든 재료를 JUST로 찌르면 플레이어당 21×2 = 42점, 팀 168/168, rate 100, judge 3, GOOD, 전원 PERFECT [재구현 계산].

### 6.8 CPU [판독 디스어셈블리 `OnMove @0x710000f5c4~0x710000f818`, `Player::Player @0x710000e2d8~0x710000e668`]

```ts
// 생성자: 비동기 난수로 실수 계획 21칸 (Params 와 무관하게 항상 만든다)
const a = [0..20];
for (j = 21; j >= 2; j--) { const r = RandMod(j); if (r !== j - 1) swap(a[j-1], a[r]); }   // RandMod(21)…RandMod(2), 20회
missPlan = a.map(v => v <= 3);                     // 21개 중 4개 true. +0x1C8 vector<bool>, 크기 21

cpuDecide(list): boolean {                         // cooldown ≤ 0 && canStab && 꼬치 보임 일 때만
  const cw = F(beatToSec(1, 1) * 60);              // s11. BPM120 = 15.0
  let swing = false;
  for (const o of list) {
    const d = target - o.moveFrame;
    if (params.isComMiss) {
      if (comIndex < missPlan.length && missPlan[comIndex]) {
        if (Math.abs(d) <= cw - 5) { reroll(); comIndex++; swing = true; }          // 실수 칸
      } else if (Math.abs(d) <= cw && o.moveFrame >= target + trunc(comOffset)) { reroll(); comIndex++; swing = true; }
    } else if (params.ComControl === 0) {
      if (Math.abs(d) <= cw && o.moveFrame >= target + trunc(comOffset)) { reroll(); swing = true; }
    } else if (Math.abs(d) <= half) {
      const mode = params.ComControl === 3 ? [JUST, SLOW, FAST][comIndex] : params.ComControl;
      // 0: |d| < 4, 1(FAST): d > 3, 2(SLOW): d < −3. ComControl 3 은 comIndex 0→JUST, 1→SLOW, 2→FAST
      if (cond(mode, d)) { reroll(); comIndex = syncRandRange(0, 3); swing = true; }   // [0,3) → 0..2
    }
  }
  return swing;
}
reroll() { const r = syncRandRangeF(-7, 7); comOffset = comOffsetEnable ? r + (r < 0 ? -1 : 1) * 3 : 0; }   // 항상 0
```

- 기본(isComMiss 0, ComControl 0)이면 CPU는 `moveFrame ≥ 120`인 첫 프레임(d = 0)에 찌른다 → 항상 JUST. 던짐 뒤 120프레임째 = E+150 [재구현 계산].
- isComMiss 1: 처음 21번의 휘두름 중 계획된 4번은 `|d| ≤ 10`(BPM 120)에서 찌른다. 이는 판정 창(±7) 밖이라 **빈 찌르기**다. 16프레임 쿨다운 뒤 d = −6에서 다시 찔러 **SLOW(1점)**가 된다(다음 칸이 실수가 아니면 일반 조건, 실수여도 |d| ≤ 10) [재구현 계산 `cpu_miss_planned`]. 21번 이후는 계획을 넘어 일반 조건만 쓴다.
  - BPM 180이면 `cw − 5 = 5`가 판정 창(±5)과 같아 실수가 d = 5의 **FAST**가 된다 [재구현 계산].
- 실수 계획은 **비동기** 난수(`RandMod`, libc++ uniform_int 기각 표본)라 원본에서 재현할 수 없다. 웹은 시드로 정한다 [판독, 01_core 6.6].
- CPU도 `canStab`·쿨다운·꼬치 보임 조건을 받는다. 재장전 중에는 CPU도 못 찌른다.
- 원본 특이점: `ComControl 3`의 첫 목표는 `comIndex` 초기값 0 = JUST다. 이후 휘두를 때마다 `SyncRandRange(0,3)`으로 다시 고른다.

### 6.11 BPM 180 (리듬 쿠킹 롱 후반) [재구현 계산]

| 값 | BPM 120 | BPM 180 |
|---|---|---|
| 판정 목표 moveFrame | 120 | 80 |
| 판정 창 반폭 | 7 | 5 |
| JUST(\|d\| ≤ 3) / FAST / SLOW 프레임 수 | 7 / 4 / 4 | 7 / 2 / 2 |

## 8. 다른 기능과의 상호작용

- **박자 ↔ 재료 시간**: 줄 배분은 사운드 G14(공용), 재료 비행은 고정 dt 누적이다. 둘은 줄 배분 프레임에서만 이어진다. 관측 지연은 공용 미확정이다.
- **입력 차단**: 단계 2 이전(상태 함수가 빈 함수), 재장전 중(`canStab` 0), 마지막 재장전 뒤(`isLast`), 단계 7 이후(상태 함수 비움). 쿨다운 16프레임(BPM 120).
- **같은 프레임 순서**: NpcMan → ObjsMan → Player → 흐름(3.5). 판정은 같은 프레임 OnThrow 뒤 `t`.
- **넓은 재료**: 레인마다 따로 판정·득점한다. 협동 찌르기·협동 던지기는 화면 연출만 바꾼다.
- **Jugemu 재사용**: 같은 레인 다음 Ready가 놓기(Entry+14) 전에 오면 앞 재료는 던져지지 않는다(5.2). 실채보는 최소 2줄 간격이다.
- **풀 상한**: 채보 음표 128개를 넘으면 범위 밖 쓰기(원본 경계 검사 없음).
- **일시정지**: 공용([mg1801 8](mg1801.md)).
