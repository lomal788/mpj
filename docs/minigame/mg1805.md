## 1. 기능 개요와 사용자에게 보이는 동작

4인 협력 리듬 미니게임이다. 네 명이 버터나이프를 들고 컨베이어 앞에 한 줄로 선다. 박자에 맞춰 빵이 컨베이어를 타고 다가온다.

- 줄마다 나오는 것은 두 종류다.
  - **버터 덩어리**(채보 `SB`/`MB`/`XB`): 휘둘러 버터를 **뜬다(TAKE)**. 뜬 버터의 양은 그 레인에서 이어서 바를 빵 개수다.
  - **빵**(채보 `S`/`M`/`X`): 휘둘러 버터를 **바른다(SPREAD)**. 뜬 버터가 1 이상이어야 바를 수 있다.
- 빵·버터의 폭이 1~4 레인이다(`S` 1, `M` 2, `L` 3, `X` 4). 넓은 것은 여러 플레이어가 각자 자기 레인을 한 번씩 친다.
- 판정은 JUST·FAST·SLOW 세 가지다. 점수는 JUST 2, FAST·SLOW 1, 놓침 0이다. 버터 없이 빵을 치면 점수 없이 헛손질 모션만 나온다.
- 같은 묶음(버터 하나에 딸린 빵들)의 마지막 빵이 지나갈 때 남은 버터는 연기와 함께 사라진다(6.7).
- 결과는 팀 달성률로 정하는 공용 별 판정이다(mg1801과 같다).

## 3. 진입점과 전체 호출 흐름

### 3.1 클래스 구성 [판독]

mg1801과 **같은 틀**이다(MaintainProduct + Product 셋 + SenderState/StateReceiver + Player::PadDriver).

```
mg1805::Scene : ca::rm::RmMgSceneBase           장면. 단계 0~10 은 기반 클래스가 돈다
  └ MaintainProductContent                      제품 묶음. GetScene(+0x20)/GetPlayerMan(+0x28)/GetObjectMan(+0x30)/GetStageMan(+0x38)
      ├ StageContent    (Product<StageMan>)     무대·컨베이어 바닥 스크롤·카메라·결과 배치
      ├ ObjsManContent  (Product<ObjsMan>)      채보 칸마다 Obj(빵·버터) + 판정 정보 + 컨베이어 이동
      └ PlayerManContent(Product<PlayerMan>)    플레이어 4명(Player + Player::PadDriver), 박 비율 시계
```

- `MaintainProductContent::Initialize @0x710000ef80`: 연습 화살표 모델을 `mg/mg1805/model/mg1805_arrow00`으로 바꾸고 Stage → ObjsMan → Player 순서로 만든다 [판독].
- 세 제품의 파이버는 모두 `bex::Fiber(this+0x10, 0, false)`, 우선순위 0이다(`CreateStage @0x7100010c80`, `CreateObjsMan @0x71000087d0`, `CreatePlayer @0x710000a0d0`) [판독]. 01_core의 규칙(오름차순 안정 정렬 + 등록 순)에 따라 한 프레임 순서는 **Stage → ObjsMan → PlayerMan → 장면 흐름**이다. mg1801과 같다 [판독 + 01_core 규칙 적용].
- 장면 생성자 `Scene::Scene @0x710000fd88`은 기반 생성자만 부른다. NPC를 싣지 않는다 [판독].

### 3.5 한 프레임 순서 [판독]

```
1. StageContent::Update  (@0x7100011ee0)  바닥 모델 스크롤, 디버그 카메라
2. ObjsManContent::Update(@0x7100005b60)  Obj 마다 OnUpdate(상태·판정 시계·바르기·토핑) → 외곽선 안내 확인 → UpdateMoveObjs(이동)
3. PlayerManContent::Update(@0x710000a5d0) Player 0~3 MyUpdate(입력 → 판정 → 득점, 지연 적중 등록) → 박 시계 +0x28 += dt
4. 장면 흐름(RmMgSceneBase::OnGameMain)    단계 처리 → 줄 배분 꼬리 → (Entry 훅) Obj::Entry
```

- Obj는 장면 흐름에서 등장한다. 그래서 등장 프레임에는 갱신을 받지 않고, 다음 프레임부터 돈다 [판독, mg1801 9.4와 같은 구조].
- 판정은 같은 프레임 ObjsMan이 늘린 판정 시계를 읽는다.

## 4. 구조체·필드·상수·열거형

### 4.1 열거형 [판독 + 데이터]

채보 1P~4P 칸의 첫 글자 = 종류(폭). 둘째 글자 `B` = 버터(뜨기).

| 첫 글자 | type(`Obj+0x70`) | 폭(레인) `DAT_7100032370` | 비고 |
|---|---|---|---|
| `S`, `Z` | 0 | 1 | SetupObjs 점프표 @0x71000324c8 (기준 `'L'`) |
| `M` | 1 | 2 | |
| `L` | 2 | 3 | 실채보에 없다 |
| `X` | 3 | 4 | 연결 목록(`+0x190`) 대상 |
| 그 밖의 대문자 `N~R`, `T~W`, `Y` | — | — | SetupObjs가 Obj를 만들지 않는다 |
| `' '` 또는 빈 문자열 | — | — | 빈칸 |

- 폭 표 `[1,2,3,4]`는 mg1801의 자르기 수와 같은 뜻이다(시작 레인 = 열 번호, 폭만큼 오른쪽으로 걸친다) [데이터].
- **원본 특이점**: `EntryNext`는 `L→2, X→3, M→1, 그 밖→0`으로 종류를 정한다. `CalcTotalPoint`는 `L, M, X` 외 모든 글자를 폭 1로 센다. SetupObjs는 `S·Z·M·L·X`만 Obj로 만든다. 실채보에는 `S·M·X`만 있어 차이가 드러나지 않는다 [판독][데이터].

`JUDGE_INPUT_TYPE`: 0 JUST, 1 FAST, 2 SLOW, 3 없음(창 밖) — 판정 함수 @0x710000db30 [판독].

플레이어 모션 번호(`Player+0x64`, 이름 표 `@0x7100038b90`) [데이터]: 0 `co_idle00`, 1 `rhy_butter_idle00`, 2 `rhy_butter_miss00`, 3 `rhy_butter_swing00`.

### 5.1 Obj 수명 [판독 `Obj::OnUpdate @0x71000052ec`]


### 5.3 장면 단계와 줄 시각 [판독 02_rhythm 7절 + 재구현 계산]

단계 0~10은 mg1801과 같다([mg1801 5.3](mg1801.md)). mg1805가 다른 것은 BeforeOneBeat 설정 (1,1)뿐이다.

마디 A = 단계 2가 시작된 마디, B = A+1 = 게임 BGM 시작 마디.

| 시점 | 일 |
|---|---|
| A 1박 | 단계 2: (0,2) PracticeStart → 입력 켬, 게임 BGM 요청 |
| B 1박 | 게임 BGM 0틱 |
| B 마지막 8분 (G14=15) | **채보 0번 줄** Entry(단계 5, BeforeOneBeat 조건 `GetBeatState(1)==8`) |
| B+1 1박 | 단계 6: (0,3) TopStart → 컨베이어 이동 시작, START 텔롭, **1번 줄** Entry, **Lock 0번 줄** |
| 이후 8분마다 | Entry 줄 하나, Lock 줄 하나(Lock = Entry − 1) |

- **줄 r의 Entry 시각 = B + (7 + r) × 8분**이다. BPM 120에서 8분 = 15프레임 [재구현 계산].
- 줄 r의 판정 중심(diff = 0) = Entry + 9×8분 = **B + 2마디 + r×8분** [재구현 계산]. 첫 내용 줄(8번)은 B+3마디다.
- 종료: Lock ≥ 줄수 − 4. chart00·01(136줄)은 Lock 132 = B + 140×8분 = B + 17.5마디에 종료 BGM을 요청한다. 종료 BGM과 단계 7(ChartEnd)은 **B+18마디(36 s)**다 [재구현 계산].
- 마지막 내용 줄 120의 판정 중심 = B + 136×8분 = B+17마디 < B+18 → 모든 칸을 판정할 수 있다 [재구현 계산].
- 게임 BGM `SQ_BGM_MG1805_A`의 0번 트랙은 19마디(ENDPLAY 확인 19회)다. 계산상 마지막 1마디는 종료 BGM으로 바뀐다 [데이터 + 재구현 계산]. 원본 녹음 대조는 하지 않았다 [미확정, 11.2].

### 6.4 판정 [판독 `FUN_710000db30`, 감싸개 `FUN_710000e8f0`]

```ts
function judgeOne(info, out, lane, isCpu, minDist): boolean {
  if (info.closed) return false;
  const w = Math.max(WIDTH[info.type], 1);
  if ((lane - info.lane) >>> 0 > w - 1) return false;          // 덮지 않는 레인
  out.objIdx = info.index; out.pos = info.pos;
  if (objsMan.isHitPlayerNo(info.index, lane)) return false;   // 이미 이 레인 적중 등록
  const diff = info.frame - Math.trunc(F(GetBeatToSec(0,4) * 60));   // + = 늦음
  if (!isCpu) {
    const [J, S] = info.covers[lane] ? [P.JustFrame2, P.Frame2] : [P.JustFrame1, P.Frame1];   // 실제로는 늘 (6, 15)
    if (-J <= diff && diff <= J) { out.type = JUST; return true; }
    if (0 <= diff && diff <= S)   { out.type = SLOW; return true; }
    if (-S <= diff && diff <= 0)  { out.type = FAST; return true; }
  } else {
    const J = P.JustFrame1, S = P.Frame1;                      // (3, 6)
    if (-J <= diff && diff <= J) { out.type = JUST; return diff >= 0; }
    if (0 <= diff && diff <= S)  { out.type = SLOW; return false; }
    if (-S <= diff && diff <= 0) { out.type = FAST; return false; }
  }
  out.type = NONE;
  const d = Math.abs(diff) - P.Frame2; if (d >= 0) minDist.v = Math.min(minDist.v, d);
  return false;
}
function judge(lane, isCpu) {                                  // FUN_710000e8f0
  const out = { type: NONE, objIdx: 0, dist: 0 }; const minDist = { v: 1000 };
  const infos = objsMan.collectActive();                       // 활성 Obj 를 vector 순서로
  for (const i of infos) if (judgeOne(i, out, lane, isCpu, minDist)) break;
  if (infos.length === 0 || out.type === NONE) out.dist = minDist.v;
  return out;
}
```

- 덮는 레인은 SetupObjs가 늘 `covers[lane]=1`로 둔다. 그래서 **사람 판정 창은 항상 (JUST ±6, 성공 ±15)**이다. (±3, ±6) 쌍은 CPU 경로만 쓴다 [판독].
- 사람 경로는 처음 걸린 Obj에서 멈춘다(채보 앞쪽 우선). CPU 경로는 JUST(diff ≥ 0)만 멈추고, FAST/SLOW/없음은 다음 Obj가 결과를 덮어쓸 수 있다(원본 특이점) [판독].

판정 프레임 표 — Entry 프레임 = 0, 그 프레임 다음부터 갱신 [재구현 계산: f32 누적 모사]:

| BPM | 판정 시계 시작 | FAST | JUST | SLOW | 창 닫힘 | CPU 휘두름(diff 0) |
|---|---|---|---|---|---|---|
| 120 | 15 | 120~128 | 129~141 | 142~150 | 151 | 135 |
| 180 | 10 | 75~83 | 84~96 | 97~100 | 101 | 90 |

BPM 180(리듬 쿠킹 롱 후반)에서는 창이 9×8분에 닫혀 SLOW 쪽이 4프레임으로 줄어든다 [재구현 계산].

## 8. 다른 기능과의 상호작용

- **박자 ↔ 판정**: 줄 배분은 사운드 시계(G14)를 따르고, 판정 시계는 Obj마다 dt 누적이다. 같은 프레임 안에서 등장 → 다음 프레임부터 시계가 돈다(mg1801과 같다).
- **입력 차단**: `inputEnabled`가 0이면 휘두름·CPU·적중 등록이 모두 멈춘다. 차트 끝(0,6) 뒤에는 Obj도 비활성이라 판정이 없다.
- **버터 의존**: 버터를 놓치면(뜨기 실패) 그 묶음의 빵은 모두 점수 0이다. 총점에는 들어가 있으므로 달성률이 그만큼 깎인다 [판독 + 재구현 계산].
- **적중 지연**: 적중은 5프레임 뒤 등록된다. 그동안 같은 칸의 판정은 계속 열려 있지만 같은 플레이어는 `hitPending`으로 막힌다.
- **조기 마감**: 덮는 레인이 모두 JUST로 등록되면 판정이 바로 닫히고 CheckMiss가 돈다.
- **외곽선 안내**: 노멀·롱(모드 < 2)에서 (0,2) 때 데모 Obj(`+0x98`, SetupPhase 가 만든 버터 1개)의 저스트 라인을 켜고(`SetVisibleJustLineDemo(true)`), 매 프레임 `groupLast`이고 index > 6인 활성 Obj가 시작 레인 기준 JUST 창에 있으면(PlayerMan +0x10 = `@0x710000a574`) `OffJustOutLine`(ObjsMan +0x18, `SetVisibleJustLineDemo(false)`)으로 끈다. SetupPhase 끝에서도 한 번 끈다(@0x7100008e54) [판독: 디스어셈블].
- **결과**: 별 판정·징글·PERFECT는 공용 점수로 정한다. ObjsMan의 결과 기록(+0x68)과 Obj::SetResult는 결과 배치 표현이다(소비자 일부 [미확정]).

스텁·검증하지 않은 범위:
- 줄 배분은 "8분 = 15프레임 고정"으로 둔다. 사운드 → 프레임 관측 지연은 0으로 둔다.
- 계산은 판정·득점 로직만이다. 표현(토핑·재질·이동 위치)은 계산하지 않았다.
- 판정 프레임 표는 f32 누적을 모사한 값이다. 원본 프레임과 대조하지 않았다.

웹 구현 뒤 기대값(같은 전제, 재구현 계산):
- chart00 전원 CPU(기본): 모든 칸 JUST → 플레이어당 48점, 팀 192/192, rate 100, judge 3, 징글 GOOD, 전원 PERFECT.
- 채보 0번 줄 Entry = 게임 BGM 시작 + 105프레임(7×15), 8번 줄(첫 버터)의 CPU 휘두름 = BGM 시작 + 225 + 135 = 360프레임(B+3마디).
- 사람이 Entry 뒤 129~141프레임에 휘두르면 JUST, 120~128 FAST, 142~150 SLOW.
- 버터를 뜨지 않고 빵을 치면 점수 0, 헛손질 모션(2).
