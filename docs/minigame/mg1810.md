## 1. 기능 개요와 사용자에게 보이는 동작

4인 협력 리듬 미니게임이다. 플레이어 4명이 밭이랑 4줄(레인)을 따라 나란히 걸어가며, 박자에 맞춰 Joy-Con을 휘둘러 모종삽으로 채소를 파낸다.

- 박자 시계는 BGM이다. 채소는 채보 한 줄(8분음표)마다 정해진 자리에 묻혀 있고, 그 줄의 박자가 오는 순간이 "JUST"다.
- 채소 다섯 종류(4.1):
  - 당근 `NJ`, 고구마 `SI`: 한 레인, 한 번 판다.
  - 양파 `TM`: 두 레인에 걸친다. 두 사람이 2번씩 판다(채보 OBJ1).
  - 무 `RD`: 네 레인 전체. 네 사람이 4번씩 판다.
  - 큰 순무 `KB`: 네 레인 전체, 마지막 연타. 20 8분 동안 마구 휘두른다(채보 OBJ1·OBJ2).
- 여러 칸 채소(TM·RD·KB)가 나오면 카메라 이동이 멈추고 플레이어가 채소 둘레에 선다(6.9).
- 판정은 JUST / FAST(빠름) / SLOW(늦음) 세 가지다. 점수는 JUST 2, FAST·SLOW 1, 큰 순무 연타 1회 1이다(6.5).
- 한 칸 채소는 **JUST로 판 경우만 "성공"**이다. FAST·SLOW로 파면 실패(NG) 모양으로 뽑힌다(6.4). 여러 칸 채소는 맡은 사람 모두의 타격 점수 합이 70 % 이상이어야 성공이다.
- 결과 화면은 공용 별 판정(팀 달성률 80/40/0)으로 결과 징글을 고르고, 채소 종류별 "파낸 비율"로 샐러드 모형의 등급 뼈(rank_c/b/a/s)를 고른다(6.6).

### 3.2 준비: `RmSyncedSetupGame @0x7100028804` (vt+0x2A0) [판독]

공용 `RmMgSceneBase::SyncedSetupGame`이 가운데에서 부른다(02_rhythm 5절). 하는 일 순서:

1. StageMan → ObjsMan → (조건부) Mg1810AudienceManager → PlayerMan → EffectMan 생성.
   - 관객 매니저 조건: `Params+0x4F(isDispStage) && Params+0x50(isDispAudienceNpc)` (둘 다 기본 1).
2. `SetMainBeatType(1)` — 채보 한 줄 = 8분음표.
   - **`SetMgBgmBeforeOneBeatStart`·`SetNextChartDataOffset`을 부르지 않는다.** 그래서 줄 배분 꼬리는 단계 6부터, Entry와 Lock이 같은 줄을 같은 프레임에 낸다(02_rhythm 7.2) [판독: 호출 지점 0건, `rhythm_mg1810_callsite.c`].
3. `SetMainBgmName("SM_BGM_BDCN001_TEST_JMP")`(저장만, 재생에 안 쓰임 — mg1801과 같다), `SetGameBgmName("SQ_BGM_MG1810_A")`, `SetGameBgmFinName("SQ_BGM_MG1810_MG_ENDING")`.
   - `Params.isGenericBgm`은 읽지 않는다. mg1801과 달리 GENERIC BGM 분기가 없다 [판독].
4. 채보 고르기(아래 표) → `RmChartDataMan::ReadChartData`.
5. `RmUiStatusMan::SetStatusType(2)`, `CalcTotalPoint()`(6.6) → `SetStarTotalScore(합계)`.
6. `StageMan::SetupGame`, `ObjsMan::SetupGame`(6.1), 관객 `Setup`+`StartOpeningDemo`, `PlayerMan::SetupGame`.
7. `Params+0x1A(isSkipResult)`이면 `RmMgSceneBase::SetResultSkip` (기본 0).

### 3.4 두 개의 시계 — mg1801과 가장 큰 차이 [판독]

mg1810은 **판정에 공용 박자 시계(G14)를 쓰지 않는다.**

| 시계 | 원천 | 쓰는 곳 |
|---|---|---|
| 공용 줄 배분 | G14(`GetBeatState(1)`), main `OnGameMain` 꼬리 | `OnRmRecieveBeatEntry` → `StageMan::Entry`(카메라 정지·플레이어 목표 변경)만 |
| **StageMan 프레임 카운터** `StageMan::Impl+0xEC` (`GetCurrentFrame @0x710002cd98`) | `StageMan::StartGame`이 설치한 tick 람다(`StageMan::Impl::OnMove @0x710002dcbc`)가 매 프레임 +1. 종료 뒤에는 `TrigGameEnd` 람다(`@0x710002e2c0`)가 계속 +1 | **모든 판정·채소 수명·타이밍 링·연타** |

- 채소의 판정 기준 프레임(just)은 셋업 때 미리 정한다: `just = GetBeatToFrame(1, row)` = (int)(GetBeatToSec(1,row)·60). BPM 120이면 **15·row** [판독 `Obj::SetupGame @0x7100016f7c`].
- 카운터는 TopStart(단계 5, 마디 B+1 첫 박) 다음 StageMan tick부터 센다. 줄 r의 Entry 프레임(F_T + 15r, F_T = TopStart 프레임)과 카운터 15r이 맞물린다 [판독 + 추정: 파이버 순서가 Stage → Objs → Players → 장면 흐름이라는 전제(mg1801 core 판독과 같은 생성 순서 규칙)].
- 그래서 원본에서도 사운드 → 프레임 관측 지연은 **채소 판정에 영향을 주지 않는다.** 카메라 정지 시작만 Entry 프레임을 따른다.
- **원본 특이점:** 판정 시계는 고정 60fps 프레임 수, BGM은 시퀀서다. 둘을 다시 맞추는 코드가 없다. 고정 60fps에서 BPM 120의 8분 = 정확히 15프레임이라 이론상 어긋나지 않는다 [재구현 계산].

### 3.5 한 프레임 순서 [판독 + 추정]

1. `StageMan::Impl::Update`(파이버): tick 람다(OnMove: 카운터 +1, 카메라 이동/정지) → 카메라 모션 프레임 77 넘으면 77에 고정.
2. `ObjsMan::Impl::Update @0x7100016030`(파이버): 창 안의 첫 객체(열 0이거나 4칸 채소)를 "현재 객체"(+0x9C)로 보고, 바뀌면 JUST 수 `+0x98 = 0` → 모든 Obj tick(`Obj::OnMove` 또는 `OnMoveMash`) → 타이밍 링 Update → InstanceObj 5개 Update.
3. 관객 매니저 Update.
4. `PlayerMan::Update @0x7100020cc0`(파이버): Player 0~3 `Update` → 설치된 tick(연습 람다 또는 `Player::OnMove`).
5. 장면 흐름 파이버: `OnGameMain`(단계 처리, 줄 배분 → `StageMan::Entry`).

- 파이버 실행 순서는 생성 순서(우선순위 0)라고 본다 **[추정: mg1801 core 판독 규칙]**. 이 순서 때문에 Obj의 평가(6.4)는 **타격 다음 프레임**에 일어난다.

### 6.2 판정 함수 [판독]

```ts
// GetTimingType(cur, just, jr) @0x7100031930 — d = just − cur (양수 = 일찍)
function timingType(cur, just, jr) {
  const d = just - cur, a = Math.abs(d);
  if (a >= 16) return -1;                 // 창 밖. 16 은 상수(BPM 무관)
  if (a <= jr) return 2;                  // JUST
  return d < 1 ? 1 /*SLOW*/ : 0 /*FAST*/;
}
const isHitTiming = (cur, just, jr) => timingType(cur, just, jr) !== -1;   // @0x7100031960
// GetTimingTypeFromSec(a, sec, jr) @0x71000319a0: d = (int)(sec·60) − a, 같은 규칙 (타이밍 링 연출용)

// ObjsMan::Impl::GetCurrentObjInfo(lane, false) @0x71000153c0 — 레인의 "지금 칠 채소"
for (i = 0; i < info.length; i++) {                          // 줄 → 칸 순서. 첫 번째로 맞는 것
  const e = info[i]; if (e.idx < 0) continue;
  const o = objs[e.idx];
  if (Math.abs(o.just - cur) < 16 && cur < o.end) {
    const col = i & 3;
    if (e.pn === 1 && col !== lane) continue;
    if (e.pn === 2 && col !== lane && col + 1 !== lane) continue;
    return e;                                                // pn 4 는 모든 레인
  }
}
return EMPTY;   // {idx:-1, type:-1, just:-100, …}
```

- **늦은 쪽 끝은 `cur < end`가 자른다.** BPM 120 한 타 채소는 end = just + 15라 늦은 한계가 −14다.

- **성공 기준** = f4 ≥ 1.4·e0. 한 타 채소(e0 = 1)는 **JUST(2점)만 성공**이다. FAST·SLOW(1점)는 실패(NG)다.
- TM(e0 = 4, 기준 5.6): 4타 중 JUST 2개 이상(예 JUST 2 + FAST 2 = 6)이면 성공, JUST 1 + FAST 3 = 5면 실패. RD(e0 = 16, 기준 22.4).
- **`SetDig`(파내기 모양·결과 집계)는 평가가 "모든 타 완료" 때문에 일어났을 때만 불린다.** 마지막 창이 지나서 평가하면 `isHitTiming(prev, just)`가 거짓이라 SetDig가 없다. 그래서 여러 칸 채소는 맡은 사람 중 한 명이라도 한 타를 빠뜨리면 70 %를 넘어도 **파내지지 않는다**(결과 집계에도 안 들어간다) [판독, 원본 그대로].
- `+0xFC`(성공 여부)는 아무도 읽지 않는다 [판독].
- `hitFlag`는 창이 지날 때 **아직 count를 못 채운 레인만** 지운다. 그래서 TM 첫 창이 지나는 프레임에도 "아무도 안 쳤다" 경로(active = 0)를 탄다. active는 판정에 쓰이지 않으므로 다음 창은 그대로 열린다 [판독].
- KB 연타: 레인당 최대 count+1(21)타까지 센다. 팀 합 ≥ 80이면 성공이다.

### 6.7 CPU [판독]

- COM은 매 프레임 `(cur.just − f) ≤ +0x140 && |cur.just − f| < 16`이면 휘두른다. 이미 친 창이면(연타 제외) 안 휘두른다.
- `+0x140`은 생성자에서 0이다. `SetComAttackTiming @0x7100023ffc`이 `Params.ComTiming`(1: RandRange(6,10), 2: −RandRange(6,10), 3: RandRange(0,20)−10)로 바꾸려면 `+0x144`가 참이어야 하는데, **`+0x144`에 0이 아닌 값을 쓰는 명령이 없다**(쓰기 2곳 모두 0, `@0x710001efd4` 등) [판독].
- 그래서 COM은 항상 just 프레임에 정확히 친다 → **전부 JUST**. 여러 타 간격(2·8분 = 30프레임) > 쿨다운(22프레임)이라 놓치지 않는다. KB는 11프레임마다 친다 [재구현 계산].
- COM은 진동 FX를 내지 않는다(JUST·SUCCESS 둘 다 `IsPlayerCom` 검사) — mg1801과 다르다(mg1801은 FAST/SLOW 진동을 COM도 낸다).
- COM은 연습 단계에서 휘두르지 않는다.

### 6.8 난수 [판독]

- mg1810은 **동기 난수(SyncRand*)를 쓰지 않는다.** 가져오는 난수는 비동기 `RandModule::RandRange`(죽은 COM 경로), `RandRangeF`(SetDig 파편 흩어짐 연출), `RandModF`(관객 오프닝 모션 시작 프레임)뿐이다 [판독: import 목록과 호출처].
- 판정·득점·평가는 난수와 무관하게 결정적이다.

### 6.9 걷기·정지 — `StageMan::Impl::Entry @0x710002cac0`, `OnMove @0x710002dcbc` [판독 디스어셈블리]

```ts
// Entry(Data): OnRmRecieveBeatEntry 가 1P..4P 중 코드 있는 줄만 넘긴다
const kb   = lanes.some(c => c === 'KB'), stop = lanes.some(c => c === 'TM' || c === 'RD' || c === 'KB');

playerMan.sendMessageChangeTarget(n, false);                 // 다음 목표까지 걷기 속도 다시 계산

// OnMove (StageMan tick, 매 프레임)
if (state === 0 && stopReq) { camera.speed = 0; stopT = 0; state = 1; }
if (state === 1) {

    stopT += dt;
    if (stopT < stopSec) { frame++; culling(); return; }          // 정지 중
    startCameraMove(); stopReq = 0; playerMan.sendMessageMove();
  }
  state = 0;                                                      // stopSec < 0 이면 바로 0
}
basePosZ += dt * beatDistance * playRate * 4;                     // 8분마다 beatDistance
frame++; culling();
// StartCameraMove: camera 'move' 재생, speed = (100 / (100 / (bd·rate·4))) · dt  (프레임/프레임)
// Update: 카메라 모션 프레임 > 77 이면 77 고정·정지·끝 플래그
```

- 카메라 `env/mg1810_cam00.fsnb`는 100프레임 루프 애니다. 위치 z 10.3 → 110.3, 주시점 z −6.6 → 93.4(프레임당 1.0 m)라 **모션 프레임 = 이동 거리(m)**다 [데이터: `graphics_bfres2gltf dump --keys`]. 속도 bd·rate·4·dt = BPM 120에서 0.04 프레임/프레임 = 2.4 m/s다 [재구현 계산].
- 정지 길이(chart00): TM 0.5 s(OBJ1 2), RD 1.0 s(OBJ1 4), KB 무한 [재구현 계산].
- **원본 특이점(KB):** stopSec < 0이면 매 프레임 "정지 → 바로 상태 0"이 반복된다. 카메라 속도는 0인 채, `basePosZ`는 계속 늘어난다. `basePosZ`를 읽는 코드는 생성되지 않는 NpcMan뿐이라 화면 영향은 없다 [판독].
- 플레이어 목표(`Player::ChangeTargetPos @0x7100020b64`): 다음 채소의 "선 자리"(`StageMan::Impl::GetObjPos`: 한 칸 채소는 채소 z − (halfScale + 0.6), 여러 칸은 objType2/objType4 각도로 둘러섬)까지 거리를 `beatDistance × (다음 줄 − (현재 줄 + n))`로 나눈 값을 걷기 속도 비(+0x100)로 둔다. 목표 z ≤ 0이면 멈춘다. RD·KB 목표면 정지 대상 플래그.
- `Player::CalcMove`(2,824 B)는 걷기·장애물(`GetObstacleList`) 회피·도착 처리를 한다. 세부는 화면 전용이라 이번에 판독하지 않았다 **[미확정]**.
- 무대 컬링: 카메라 z와 경계 표(+0x98)로 `mg1810_map_grp`의 `map_00`~`map_04` 뼈를 켜고 끈다(경계 + 33 m) [판독].

### 6.11 판정 프레임 표 [재구현 계산, `analysis/rcE_mg1810_calc_bpm120.json`의 전제]

BPM 120, JustRangeAbsFrame 5, d = just − cur(양수 = 일찍).

| 대상 | FAST | JUST | SLOW | 근거 |
|---|---|---|---|---|
| 한 타 채소(NJ·SI) | d = +6..+15 (10 f) | −5..+5 (11 f) | −6..**−14** (9 f) | 늦은 쪽은 end = just+15가 자름 |
| 여러 타 1번째 타 | +6..+15 | −5..+5 | −6..−15 | end가 멀다 |

| KB 연타 | — | 창이 끊기지 않음: just−15 ~ end−1 | — | 8분마다 just 이동 |

- BPM 180(리듬 쿠킹 롱 후반): 8분 = 10프레임, 창 ±15는 그대로다. 한 타 채소 늦은 한계는 end = just+10 → −9. 2줄 간격 채소는 앞 채소가 end 전까지 레인을 차지하므로 다음 채소의 이른 창이 +10까지 줄어든다 [재구현 계산 `_bpm180.json`].

## 8. 다른 기능과의 상호작용

- **판정 ↔ 박자**: 판정은 StageMan 카운터, 카메라 정지는 G14 줄 배분. 정지 중에도 카운터는 돈다. 그래서 정지 길이·위치 계산이 틀려도 판정에는 영향이 없다(화면만 어긋난다).
- **입력 차단**: TopStart 전에는 OnMove tick이 없다(연습 tick만). `IsAllEnd()`(모든 채소 end ≤ 카운터)부터는 휘두름 자체가 막힌다. 이동 중 부딪힘(+0x145)도 막는다.
- **같은 프레임 여러 레인**: 플레이어는 PlayerID 순서로 돈다. 레인별 상태(hits·hitFlag)가 분리돼 순서 영향은 평가 프레임에 없다(평가는 다음 프레임 ObjsMan) [판독].
- **창 겹침**: 같은 레인에서 두 채소 창이 겹치면 `GetCurrentObjInfo`가 채보 순서상 앞 줄을 고른다. 앞 채소를 이미 쳤으면(hitFlag) 휘둘러도 무시된다. BPM 120 실채보에서는 겹치지 않는다 [재구현 계산].
- **결과**: ObjsMan::SetResult가 갱신을 멈추고(+0x19) 인스턴스 모델을 숨긴다. 샐러드 등급은 SetDig 수만 본다.
- **일시정지**: 공용(단계 7 UI 일시정지 금지).
